# C#/.NET Concurrency & Synchronization — Practical Tutorial

> **Goal:** Understand what `Wait()`, `Release()`, `Pulse()`, `PulseAll()`, `Signal()`, `Enter()`, etc. actually mean, how they differ, and when to use them.

---

# 1. The Big Picture

| Problem | Typical tool |
|---|---|
| Protect shared data | `lock`, `Monitor`, `Mutex` |
| Allow N threads simultaneously | `SemaphoreSlim`, `Semaphore` |
| One thread waits for another | `Monitor.Wait/Pulse`, events |
| Tell one waiting thread to continue | `AutoResetEvent`, `SemaphoreSlim.Release(1)` |
| Tell all waiting threads to continue | `Monitor.PulseAll()` |
| Wait until N operations finish | `CountdownEvent` |
| Wait until N threads reach a point | `Barrier` |
| Very short lock | `SpinLock` |
| Atomic integer/state update | `Interlocked` |
| Visibility between threads | `volatile`, memory barriers |
| Async waiting | `SemaphoreSlim.WaitAsync()` |
| Coordinate tasks | `Task`, `TaskCompletionSource`, async primitives |

## The most important distinction

> **Mutual exclusion** = "Only one can enter."
>
> **Signaling** = "You can continue now."
>
> **Counting** = "N permits are available."
>
> **Waiting for completion** = "Tell me when this work is finished."

# 2. The Core Mental Model

There are two fundamentally different kinds of operations.

## Acquire / Enter

> "I want permission to proceed."

Examples:

```csharp
lock (obj)
```

```csharp
Monitor.Enter(obj);
```

```csharp
semaphore.Wait();
```

```csharp
mutex.WaitOne();
```

---

## Release / Signal

> "I am done / I am giving permission back / someone else may continue."

Examples:

```csharp
Monitor.Exit(obj);
```

```csharp
semaphore.Release();
```

```csharp
mutex.ReleaseMutex();
```

```csharp
Monitor.Pulse(obj);
```

But:

> **`Pulse()` is NOT the same thing as `Release()`.**

That distinction is extremely important.

# 3. `lock`

The simplest synchronization mechanism:

```csharp
lock (obj)
{
    // only one thread at a time
}
```

Conceptually, `lock` is similar to:

```csharp
Monitor.Enter(obj);

try
{
    // protected code
}
finally
{
    Monitor.Exit(obj);
}
```

Remember:

```text
lock = Enter → work → Exit
```

## Example

```csharp
private readonly object _lock = new();

private int _counter;

public void Increment()
{
    lock (_lock)
    {
        _counter++;
    }
}
```

Without synchronization:

```text
Thread A       Thread B

read 10
               read 10
write 11
               write 11

Expected: 12
Actual:   11
```

With `lock`:

```text
Thread A       Thread B

Enter
increment
Exit
               Enter
               increment
               Exit
```

# 4. `Monitor`

```csharp
Monitor.Enter()
Monitor.Exit()
Monitor.TryEnter()

Monitor.Wait()
Monitor.Pulse()

```

Think:

> **Monitor = Lock + Condition Waiting + Signaling**

# 5. `Monitor.Enter()`

```csharp
Monitor.Enter(obj);
```

Means:

> "Acquire the object's monitor."

If another thread already owns it:

```text
Thread A                 Thread B

Enter
 │
 │                      Enter
 │                        │
 │                        ↓
 │                     WAITING
 │
work
 │
Exit
                         │
                         ↓
                       ENTER
```

Remember:

```text
Enter = acquire ownership
Exit  = release ownership
```

---

# 6. `Monitor.Exit()`

```csharp
Monitor.Exit(obj);
```

Means:

> "I am done with this monitor."

Example:

```csharp
Monitor.Enter(_lock);

try
{
    DoSomething();
}
finally
{
    Monitor.Exit(_lock);
}
```

Always use `finally` when manually using `Enter()`.

---

# 7. `Monitor.TryEnter()`

Instead of waiting forever:

```csharp
if (Monitor.TryEnter(_lock))
{
    try
    {
        DoSomething();
    }
    finally
    {
        Monitor.Exit(_lock);
    }
}
```

You can also specify a timeout:

```csharp
if (Monitor.TryEnter(_lock, TimeSpan.FromSeconds(2)))
{
    try
    {
        DoSomething();
    }
    finally
    {
        Monitor.Exit(_lock);
    }
}
```

Meaning:

> "Try to acquire the lock, but don't wait forever."

---

# 8. The Most Important Part: `Monitor.Wait()`

This is where many developers become confused.

Example:

```csharp
lock (_lock)
{
    while (!_dataAvailable)
    {
        Monitor.Wait(_lock);
    }

    ConsumeData();
}
```

What does `Wait()` actually do?

It does **two important things**:

```text
1. Release the lock
2. Put the thread into a waiting state
```

This is critical.

## Before `Wait()`

```text
Thread A owns _lock

┌───────────────────┐
│ Thread A          │
│ owns lock         │
│                   │
│ Wait()            │
└────────┬──────────┘
         │
         ↓
```

## During `Wait()`

```text
Thread A
   │
   ├── releases lock
   │
   └── waits
```

Now another thread can enter the lock.

---

# 9. `Monitor.Pulse()`

Suppose another thread produces the data:

```csharp
lock (_lock)
{
    _dataAvailable = true;

    Monitor.Pulse(_lock);
}
```

`Pulse()` means:

> **Wake one thread that is waiting on this monitor.**

Visual:

```text
                 Monitor.Wait()
                      │
                      ↓
                ┌───────────┐
                │ WAITING   │
                │ Thread A  │
                │ Thread B  │
                │ Thread C  │
                └─────┬─────┘
                      │
                 Pulse()
                      │
                      ↓
              ONE THREAD WAKES
```

### Important

> `Pulse()` does **not** release the lock.

The signaling thread still owns the lock until it exits the `lock`.

---

# 10. `Monitor.PulseAll()`

```csharp
Monitor.PulseAll(_lock);
```

Means:

> Wake **all threads waiting on this monitor**.

Visual:

```text
                 WAITING
             ┌─────┼─────┐
             ↓     ↓     ↓
             A     B     C

              PulseAll()

             ↓     ↓     ↓
             A     B     C
```

But they do **not** all execute simultaneously inside the lock.

They must compete for the lock.

```text
PulseAll()
    │
    ├── A becomes eligible
    ├── B becomes eligible
    └── C becomes eligible

          ↓

     lock becomes available

          ↓

     A gets lock

          ↓

     A exits

          ↓

     B gets lock

          ↓

     B exits

          ↓

     C gets lock
```

---

# 11. `Wait()` + `Pulse()` = Condition Signaling

One of the most important patterns:

```csharp
lock (_lock)
{
    while (!condition)
    {
        Monitor.Wait(_lock);
    }

    // condition is true
}
```

Another thread:

```csharp
lock (_lock)
{
    condition = true;

    Monitor.Pulse(_lock);
}
```

Think:

```text
WAIT()
"Wake me when something may have changed."

PULSE()
"Something changed. One waiter should check."

PULSEALL()
"Something changed. Everybody should check."
```

### Very important

`Pulse()` does **not** mean:

> "The condition is definitely true."

It means:

> "Something changed; wake up and check."

Therefore use:

```csharp
while (!condition)
{
    Monitor.Wait(_lock);
}
```

rather than:

```csharp
if (!condition)
{
    Monitor.Wait(_lock);
}
```

The `while` is important because the thread must re-check the actual condition after waking.

# 12. Producer / Consumer Example

This makes `Wait()` and `Pulse()` easier to understand.

```csharp
private readonly object _lock = new();

private readonly Queue<int> _queue = new();

public void Produce(int value)
{
    lock (_lock)
    {
        _queue.Enqueue(value);

        Monitor.Pulse(_lock);
    }
}
```

Consumer:

```csharp
public int Consume()
{
    lock (_lock)
    {
        while (_queue.Count == 0)
        {
            Monitor.Wait(_lock);
        }

        return _queue.Dequeue();
    }
}
```

Conceptually:

```text
Consumer

Queue empty?
     │
     YES
     │
   Wait()
     │
     ↓
RELEASE LOCK
     │
     ↓
   WAITING
```

Producer:

```text
Produce item
     │
     ↓
Pulse()
     │
     ↓
Wake one consumer
```

# 13. `Semaphore`

A semaphore is basically a **counter of permits**.

Imagine:

```text
Semaphore = 3 permits

🟢 🟢 🟢
```

Three threads can enter.

```text
Thread A → permit 1
Thread B → permit 2
Thread C → permit 3

Thread D → WAIT
```

When one finishes:

```csharp
semaphore.Release();
```

A permit returns.

```text
🟢
```

Thread D can proceed.

# 15. `SemaphoreSlim` Example

```csharp
var semaphore = new SemaphoreSlim(3);
```

Three concurrent operations are allowed.

```csharp
await semaphore.WaitAsync();

try
{
    await DoWorkAsync();
}
finally
{
    semaphore.Release();
}
```

Visual:

```text
Initial:

[ 🟢 🟢 🟢 ]

A Wait → [ 🔴 🟢 🟢 ]

B Wait → [ 🔴 🔴 🟢 ]

C Wait → [ 🔴 🔴 🔴 ]

D Wait → WAITING
```

A finishes:

```csharp
semaphore.Release();
```

Now:

```text
[ 🟢 🔴 🔴 ]

D can continue
```

# 16. `SemaphoreSlim.Release(n)`

You can release multiple permits:

```csharp
semaphore.Release(3);
```

Meaning:

> Return three permits.

Normally, keep acquisition and release balanced:

```text
Wait() / WaitAsync()
       ↓
      work
       ↓
Release()
```

Use `finally` so an exception doesn't accidentally leave a permit permanently taken:

```csharp
await semaphore.WaitAsync();

try
{
    await WorkAsync();
}
finally
{
    semaphore.Release();
}
```

This is extremely important.

### `lock`

```text

```


### Semaphore

```text
Capacity = N
```

```text

```

```text

```

# 19. Mutex vs Lock

### `lock`

Normally used for synchronization **inside one process**.

### `Mutex`

Can synchronize between **different processes**.

For example:

```text
Process A
   │
   │
   ├──────────┐
              │
           Mutex
              │
   ├──────────┘
   │
Process B
```

This makes `Mutex` useful for cases such as:

> "Only one instance of this application should run."

For most normal in-process C# synchronization, `lock` is simpler and usually preferred.

# 23. `Monitor.Pulse()` vs Event `Set()`

These can look similar but belong to different synchronization models.

### Monitor

```csharp
Monitor.Pulse(lockObject);
```

Means:

> Wake a thread waiting with `Monitor.Wait()`.

### AutoResetEvent

```csharp
event.Set();
```

Means:

> Signal the event; one waiter can proceed.

The important difference is that `Monitor` signaling is tied to the monitor/lock and a condition predicate, while an event has persistent signaled/non-signaled state.

# 24. `Signal()` — What Does It Mean?

You will see `Signal()` in different synchronization APIs.

Generally:

```text
Signal
=
"Tell another thread/task that something happened."
```

There is no universal `Signal()` method across all .NET synchronization primitives.

Examples:

```text
Monitor          → Pulse()
Semaphore        → Release()
AutoResetEvent   → Set()
CountdownEvent   → Signal()
Barrier          → SignalAndWait()
```

So don't memorize:

```text
Signal = one specific .NET operation
```

Instead remember:

> **Signal means "announce progress/event/completion."**

Then learn the API-specific method that performs the signal.

# 25. `CountdownEvent`

This is excellent for understanding `Signal()`.

Imagine you start five workers:

```text
Worker A ────────┐
Worker B ────────┤
Worker C ────────┤
Worker D ────────┤
Worker E ────────┘
```

You want the main thread to wait until **all five finish**.

Create:

```csharp
var countdown = new CountdownEvent(5);
```

Each worker:

```csharp
try
{
    DoWork();
}
finally
{
    countdown.Signal();
}
```

Main thread:

```csharp
countdown.Wait();
```

Visual:

```text
Initial count = 5

A finishes → Signal() → 4
B finishes → Signal() → 3
C finishes → Signal() → 2
D finishes → Signal() → 1
E finishes → Signal() → 0

                     ↓

                   Wait()
                 RELEASED
```

The best way to remember it:

> `CountdownEvent.Signal()` = **"I finished one unit of work."**

---

# 26. `CountdownEvent.Wait()`

```csharp
countdown.Wait();
```

Means:

> "Wait until the counter reaches zero."

So:

```text
Signal() → decrease counter

Wait() → wait until counter == 0
```

# 27. Barrier

`Barrier` is different.

A barrier means:

> **Everybody reaches this point before anybody proceeds.**

Imagine three threads:

```text
Thread A ────────┐
Thread B ────────┤ → BARRIER
Thread C ────────┘
```

Nobody proceeds until everyone reaches the barrier.

```csharp
var barrier = new Barrier(3);
```

Each thread:

```csharp
DoPhase1();

barrier.SignalAndWait();

DoPhase2();
```

Visual:

```text
A ────────────────┐
B ────────────────┤
C ────────────────┘
                  │
               BARRIER
                  │
                  ↓
A ────────────────┐
B ────────────────┤
C ────────────────┘
```

# 30. SpinLock

`SpinLock` is for very short critical sections.

Instead of immediately blocking:

```text
Try lock
   ↓
not available
   ↓
block/sleep
   ↓
wake later
```

a spin lock may repeatedly check:

```text
Try lock
   ↓
not available
   ↓
CPU spins
   ↓
try again
```

This can be useful when the expected wait time is extremely short, but it should not be used casually.

# 36. Memory Model

Modern CPUs and compilers can reorder operations.

Imagine:

```csharp
data = 42;
ready = true;
```

Another thread may not safely observe the intended ordering unless appropriate synchronization is used.

Synchronization primitives therefore do more than prevent simultaneous access.

They also establish **memory-ordering and visibility guarantees**.

---

# 37. Acquire / Release

This is an excellent mental model.

### Release

> "Everything I did before this point is published before the release."

### Acquire

> "After I acquire, I can safely observe what was published before the corresponding release."

Conceptually:

```text
Thread A                         Thread B

data = 42

RELEASE
   │
   └──────────────────────┐
                          │
                       ACQUIRE
                          │
                          ↓
                       read data
                          ↓
                         42
```

In .NET, the exact memory guarantees depend on the synchronization primitive/operation, but `lock`, `Monitor`, `Interlocked`, and other synchronization mechanisms provide the necessary ordering semantics for their intended use.

# 38. `volatile`

Example:

```csharp
private volatile bool _stop;
```

Thread A:

```csharp

```

Thread B:

```csharp

```

The important point:

> `volatile` is primarily about **visibility and ordering**, not making arbitrary compound operations atomic.

```csharp

```


# 41. Threads, Cores, and Time Slicing

A common confusion:

> "I have 8 cores, so I can only have 8 threads."

**Wrong.** Cores limit how many threads **run at the same instant**, not how many threads **can exist**.

```text
8 cores  → 8 threads executing at the same moment
OS       → can host hundreds or thousands of threads
```

The OS **time-slices** threads: each thread runs for a few milliseconds, then gets swapped out for another (a **context switch**).

```text
8 cores, 50 threads:

Core 1: T1 → T9  → T17 → T1 → ...   (switching every few ms)
Core 2: T2 → T10 → T18 → T2 → ...
...
```

So yes, you can create 1000 threads, and the machine runs only 8 at a time, rotating between them.

## Refinement 1: logical processors

With **Hyper-Threading / SMT**, each physical core can run 2 threads at once.

```text
8 cores without HT → 8  simultaneous threads
8 cores with HT    → 16 simultaneous threads
```

`Environment.ProcessorCount` returns the **logical** count. That is the number the thread pool uses.

## Refinement 2: blocked threads don't compete for CPU

The OS only time-slices threads that are **ready to run**. A blocked thread (`Sleep`, waiting on a lock, waiting on I/O, `.Result`) is not scheduled at all.

```text
1000 threads created
 ├─ 990 blocked/sleeping → not scheduled, ~0% CPU, but still about 1 MB stack each
 └─  10 ready to run     → time-sliced across the 8 cores
```

## Why not just create lots of threads?

Each thread costs:

- **About 1 MB of reserved stack** memory
- **Creation/destruction time** (expensive compared to reusing a thread)
- **Context-switch overhead** when many threads want CPU at once

```text
1000 mostly-waiting threads → little CPU, lots of wasted memory   (async fixes this)
1000 CPU-busy threads       → NOT faster than 8; slower due to switching
```

Remember:

```text
Cores = how many run at once
OS    = how many can exist
```

# 42. How the Thread Pool Works

The thread pool is a **set of reusable worker threads** managed by the CLR.

You don't create pool threads. You **queue work**, and the pool decides which thread runs it.

```text
Your code ──queue work item──►  [ Global queue ] + [ per-thread local queues ]
                                         │
                     ┌───────────┬───────┴───┬───────────┐
                  Thread 1    Thread 2    Thread 3    Thread N   ← reused over and over
```

## When are pool threads created?

```text
Pool threads:   0 ──fast──► min ──slow, ~1 per 0.5–1s──► ... ──► max (~32,767)
```

1. **Lazily, on demand.** At startup the pool has few or no threads.
2. **Quickly, up to the minimum.** `ThreadPool.GetMinThreads()` defaults to `Environment.ProcessorCount`. Below this number, a new thread is created **immediately** when work is queued and no thread is free.
3. **Slowly, above the minimum.** When all threads are busy, the pool **injects threads gradually** (roughly one every 0.5–1 second), using a **hill-climbing** algorithm that checks whether more threads actually improve throughput.
4. **Up to a maximum.** `GetMaxThreads()` is very large, so in practice the limit is the slow injection rate, not the maximum.

> The minimum is **not a limit**. The pool can grow past it, just slowly.

You can raise the minimum so the pool ramps up faster:

```csharp
ThreadPool.SetMinThreads(50, 50);
```

This is sometimes used as a band-aid for starvation. The real fix is to stop blocking.

## When are pool threads destroyed?

- After finishing a work item, a thread **doesn't die**. It picks up the next item.
- If a thread stays **idle for a while** (about 20 seconds), the pool retires it.

## Two kinds of pool threads

| Kind | Job |
|---|---|
| Worker threads | Run `Task.Run` work and async continuations |
| I/O completion threads | Receive OS notifications that I/O finished (IOCP on Windows), then hand continuations off to worker threads |

## Thread starvation

Because growth above the minimum is slow, **blocking pool threads is dangerous**:

```text
100 requests each call .Result / Thread.Sleep
        ↓
all pool threads blocked
        ↓
new threads trickle in ~1 per second
        ↓
requests queue up → timeouts
```

.NET 6+ reacts somewhat faster when it detects blocking (for example `.Result` on a task), but it's still not instant.

## `new Thread()` is outside the pool

```csharp
var t = new Thread(() => DoWork());
t.Start();
```

- Creates a **dedicated OS thread**, **not** part of the thread pool.
- Doesn't count toward the pool's minimum, and the pool doesn't manage it.

```text
8 pool threads + new Thread() = 8 pool threads + 1 separate thread
                                (not 9 pool threads)
```

Even a simple console app already has more than one thread: the main thread, GC thread(s), the finalizer thread, background JIT threads, and others.

Use `new Thread` only for special cases: a long-running dedicated loop, a foreground thread, a custom priority, or an STA apartment.

---

# 43. Does `Task.Run` or `Task.FromResult` Create a Thread?

## `Task.Run`: queues to the pool

```csharp
Task.Run(() => DoCpuWork());
```

`Task.Run` **does not create a thread**. It **queues a work item to the thread pool**.

```text
idle pool thread exists?      → it runs the work (no new thread)
all busy, below minimum?      → pool creates a thread immediately
all busy, above minimum?      → work waits in the queue until a thread frees up or is injected
```

So `Task.Run` *may cause* the pool to grow, but it never means "make me a new thread".

## `LongRunning`: the exception

```csharp
Task.Factory.StartNew(() => LongBlockingLoop(), TaskCreationOptions.LongRunning);
```

Usually creates a **dedicated, non-pool thread**, so a long blocking loop doesn't tie up a pool thread.

## `Task.FromResult`: no thread, no pool

```csharp
Task<int> t = Task.FromResult(42);
```

It just allocates a `Task` object that is **already completed** with the value `42`.

- Nothing is scheduled.
- Nothing runs in the background.
- `await` on it continues **synchronously on the same thread**, because the task is already done.

Typical use is returning a known or cached value from a method that must return a `Task`:

```csharp
public Task<User> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out var user))
        return Task.FromResult(user);   // no thread, no async machinery

    return LoadFromDbAsync(id);
}
```

`ValueTask<T>` goes further and avoids even the `Task` allocation in that case.

## Summary table

| API | New thread? | Uses the pool? | What happens |
|---|---|---|---|
| `new Thread(...).Start()` | **Yes** | No | Dedicated OS thread |
| `Task.Run(...)` | No (pool may grow) | **Yes** | Queued to a pool worker |
| `Task.Factory.StartNew(..., LongRunning)` | **Usually yes** | No | Dedicated thread |
| `Task.FromResult(x)` | **No** | **No** | Already-completed task object |
| `await SomeIoAsync()` | **No** | Only for the continuation | No thread waits during I/O |
| `Task.Delay(1000)` | **No** | Only for the continuation | A timer completes the task |

## Interview answer

> "Core count limits how many threads run at the same time, not how many can exist. The OS time-slices ready threads across cores. The thread pool creates threads on demand up to its minimum (one per logical core), then adds more slowly with hill-climbing, and retires idle ones. `Task.Run` queues work to the pool and doesn't create a thread. `Task.FromResult` returns an already-completed task, so no thread or scheduling is involved. `new Thread` creates a separate thread outside the pool."

# 44. `SemaphoreSlim.WaitAsync()`

This is especially useful in ASP.NET Core.

Avoid unnecessary blocking in async code:

```csharp
semaphore.Wait();
```

Prefer:

```csharp
await semaphore.WaitAsync();

try
{
    await DoWorkAsync();
}
finally
{
    semaphore.Release();
}
```

Mental model:

```text
WaitAsync()
    ↓
await permission
    ↓
no thread needs to block
    ↓
permission arrives
    ↓
continue
```

## What "no thread needs to block" means

The **method** is suspended, but the **thread** it was running on is released.

### Blocking version: `Wait()`

If no permit is available:

- The current thread (say, pool thread #7) **stops right there**.
- It can't do anything else. It sleeps until someone calls `Release()`.
- 1000 waiting requests = 1000 stuck threads, about 1 MB of stack each, and the pool runs short (**thread starvation**, see section 42).

### Async version: `await WaitAsync()`

If no permit is available:

1. `WaitAsync()` returns an **incomplete `Task`** straight away.
2. `await` sees the task isn't done. It saves the rest of the method as a **continuation**, and the method returns to its caller.
3. Thread #7 is **free** and goes back to the pool to serve other work.
4. Later, `semaphore.Release()` is called. The semaphore completes the waiting `Task`.
5. The continuation is scheduled on **any available pool thread**, maybe #3, and runs `DoWorkAsync()`.

```text
Thread #7:  [run method] → WaitAsync (no permit) → return to pool → [serves other work...]
                                    ⋮  (nobody is waiting; the method is just a stored continuation)
Release() → Task completes
Thread #3:                                          → [continue: DoWorkAsync()...]
```

| | `Wait()` | `await WaitAsync()` |
|---|---|---|
| The *logical operation* waits? | Yes | Yes |
| An *OS thread* waits? | **Yes** (blocked) | **No** (released) |
| What holds the "waiting" state | A sleeping thread | A `Task` + continuation object in memory |
| Cost per waiter | About 1 MB of stack plus a thread | A few hundred bytes on the heap |

Remember:

```text
Your code waits its turn.
No thread is spent waiting.
```

Interview answer:

> "`WaitAsync` waits asynchronously. The method is suspended but the thread goes back to the pool. When the semaphore is released, the method resumes on a pool thread. So we throttle concurrency without causing thread starvation."

# 47. The Most Important Difference: Release vs Pulse

This deserves special attention.

## `Release()`

Usually means:

> **Give something back.**

Semaphore:

```csharp
semaphore.Release();
```

You return a permit.

```text
[PERMIT]
   ↓
available resource
```

## `Pulse()`

Means:

> **Wake someone who is waiting.**

```csharp
Monitor.Pulse(lockObject);
```

It does not release the monitor.

```text
WAITING THREAD
      ↑
    WAKE UP
```

Remember:

```text
Release = return a resource/permit/ownership

Pulse = wake a Monitor waiter
```

# 48. Why `Monitor.Wait()` Is Special

`Monitor.Wait()` has a very specific lifecycle:

```text
lock
  ↓
condition false
  ↓
Wait()
  ↓
release lock
  ↓
WAITING
  ↓
Pulse()
  ↓
wake
  ↓
reacquire lock
  ↓
Wait() returns
  ↓
check condition again
```

This is the key to understanding `Monitor`.

## Full example

```csharp
lock (_lock)
{
    while (!_dataAvailable)
    {
        Monitor.Wait(_lock);
    }

    ConsumeData();
}
```

Producer:

```csharp
lock (_lock)
{
    _dataAvailable = true;
    Monitor.Pulse(_lock);
}
```

The consumer doesn't simply wake and run immediately.

After `Pulse()`, it must **reacquire the monitor** before `Wait()` returns.

# 56. Final Rule of Thumb

When you see an unfamiliar synchronization API, ask these five questions:

1. **What am I waiting for?**
2. **What resource/state am I acquiring?**
3. **What does the release operation give back?**
4. **What wakes the waiter?**
5. **Does the waiter reacquire a lock before continuing?**

If you can answer those five questions, you understand the synchronization primitive rather than merely memorizing its methods.
