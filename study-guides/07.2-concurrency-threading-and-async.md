# C#/.NET Concurrency & Synchronization — Practical Tutorial

> **Goal:** Understand what `Wait()`, `Release()`, `Pulse()`, `PulseAll()`, `Signal()`, `Enter()`, etc. actually mean, how they differ, and when to use them.

---

# 1. The Big Picture

| Problem | Typical tool |
|---|---|
| Protect shared data | `lock`, `Monitor`, `Mutex` |
| Allow N threads simultaneously | `SemaphoreSlim`, `Semaphore` |
| One thread waits for another | `Monitor.Wait/Pulse`, events |
| Tell one waiting thread to continue | `AutoResetEvent`, `SemaphoreSlim.Release(1)` |
| Tell all waiting threads to continue | `Monitor.PulseAll()` |
| Wait until N operations finish | `CountdownEvent` |
| Wait until N threads reach a point | `Barrier` |
| Very short lock | `SpinLock` |
| Atomic integer/state update | `Interlocked` |
| Visibility between threads | `volatile`, memory barriers |
| Async waiting | `SemaphoreSlim.WaitAsync()` |
| Coordinate tasks | `Task`, `TaskCompletionSource`, async primitives |

## The most important distinction

> **Mutual exclusion** = "Only one can enter."
>
> **Signaling** = "You can continue now."
>
> **Counting** = "N permits are available."
>
> **Waiting for completion** = "Tell me when this work is finished."

# 2. The Core Mental Model

There are two fundamentally different kinds of operations.

## Acquire / Enter

> "I want permission to proceed."

Examples:

```csharp
lock (obj)
```

```csharp
Monitor.Enter(obj);
```

```csharp
semaphore.Wait();
```

```csharp
mutex.WaitOne();
```

---

## Release / Signal

> "I am done / I am giving permission back / someone else may continue."

Examples:

```csharp
Monitor.Exit(obj);
```

```csharp
semaphore.Release();
```

```csharp
mutex.ReleaseMutex();
```

```csharp
Monitor.Pulse(obj);
```

But:

> **`Pulse()` is NOT the same thing as `Release()`.**

That distinction is extremely important.

# 3. `lock`

The simplest synchronization mechanism:

```csharp
lock (obj)
{
    // only one thread at a time
}
```

Conceptually, `lock` is similar to:

```csharp
Monitor.Enter(obj);

try
{
    // protected code
}
finally
{
    Monitor.Exit(obj);
}
```

Remember:

```text
lock = Enter → work → Exit
```

## Example

```csharp
private readonly object _lock = new();

private int _counter;

public void Increment()
{
    lock (_lock)
    {
        _counter++;
    }
}
```

Without synchronization:

```text
Thread A       Thread B

read 10
               read 10
write 11
               write 11

Expected: 12
Actual:   11
```

With `lock`:

```text
Thread A       Thread B

Enter
increment
Exit
               Enter
               increment
               Exit
```

# 4. `Monitor`

Important APIs:

```csharp
Monitor.Enter()
Monitor.Exit()
Monitor.TryEnter()

Monitor.Wait()
Monitor.Pulse()
Monitor.PulseAll()
```

Think:

> **Monitor = Lock + Condition Waiting + Signaling**

# 5. `Monitor.Enter()`

```csharp
Monitor.Enter(obj);
```

Means:

> "Acquire the object's monitor."

If another thread already owns it:

```text
Thread A                 Thread B

Enter
 │
 │                      Enter
 │                        │
 │                        ↓
 │                     WAITING
 │
work
 │
Exit
                         │
                         ↓
                       ENTER
```

Remember:

```text
Enter = acquire ownership
Exit  = release ownership
```

---

# 6. `Monitor.Exit()`

```csharp
Monitor.Exit(obj);
```

Means:

> "I am done with this monitor."

Example:

```csharp
Monitor.Enter(_lock);

try
{
    DoSomething();
}
finally
{
    Monitor.Exit(_lock);
}
```

Always use `finally` when manually using `Enter()`.

---

# 7. `Monitor.TryEnter()`

Instead of waiting forever:

```csharp
if (Monitor.TryEnter(_lock))
{
    try
    {
        DoSomething();
    }
    finally
    {
        Monitor.Exit(_lock);
    }
}
```

You can also specify a timeout:

```csharp
if (Monitor.TryEnter(_lock, TimeSpan.FromSeconds(2)))
{
    try
    {
        DoSomething();
    }
    finally
    {
        Monitor.Exit(_lock);
    }
}
```

Meaning:

> "Try to acquire the lock, but don't wait forever."

---

# 8. The Most Important Part: `Monitor.Wait()`

This is where many developers become confused.

Example:

```csharp
lock (_lock)
{
    while (!_dataAvailable)
    {
        Monitor.Wait(_lock);
    }

    ConsumeData();
}
```

What does `Wait()` actually do?

It does **two important things**:

```text
1. Release the lock
2. Put the thread into a waiting state
```

This is critical.

## Before `Wait()`

```text
Thread A owns _lock

┌───────────────────┐
│ Thread A          │
│ owns lock         │
│                   │
│ Wait()            │
└────────┬──────────┘
         │
         ↓
```

## During `Wait()`

```text
Thread A
   │
   ├── releases lock
   │
   └── waits
```

Now another thread can enter the lock.

---

# 9. `Monitor.Pulse()`

Suppose another thread produces the data:

```csharp
lock (_lock)
{
    _dataAvailable = true;

    Monitor.Pulse(_lock);
}
```

`Pulse()` means:

> **Wake one thread that is waiting on this monitor.**

Visual:

```text
                 Monitor.Wait()
                      │
                      ↓
                ┌───────────┐
                │ WAITING   │
                │ Thread A  │
                │ Thread B  │
                │ Thread C  │
                └─────┬─────┘
                      │
                 Pulse()
                      │
                      ↓
              ONE THREAD WAKES
```

### Important

> `Pulse()` does **not** release the lock.

The signaling thread still owns the lock until it exits the `lock`.

---

# 10. `Monitor.PulseAll()`

```csharp
Monitor.PulseAll(_lock);
```

Means:

> Wake **all threads waiting on this monitor**.

Visual:

```text
                 WAITING
             ┌─────┼─────┐
             ↓     ↓     ↓
             A     B     C

              PulseAll()

             ↓     ↓     ↓
             A     B     C
```

But they do **not** all execute simultaneously inside the lock.

They must compete for the lock.

```text
PulseAll()
    │
    ├── A becomes eligible
    ├── B becomes eligible
    └── C becomes eligible

          ↓

     lock becomes available

          ↓

     A gets lock

          ↓

     A exits

          ↓

     B gets lock

          ↓

     B exits

          ↓

     C gets lock
```

---

# 11. `Wait()` + `Pulse()` = Condition Signaling

One of the most important patterns:

```csharp
lock (_lock)
{
    while (!condition)
    {
        Monitor.Wait(_lock);
    }

    // condition is true
}
```

Another thread:

```csharp
lock (_lock)
{
    condition = true;

    Monitor.Pulse(_lock);
}
```

Think:

```text
WAIT()
"Wake me when something may have changed."

PULSE()
"Something changed. One waiter should check."

PULSEALL()
"Something changed. Everybody should check."
```

### Very important

`Pulse()` does **not** mean:

> "The condition is definitely true."

It means:

> "Something changed; wake up and check."

Therefore use:

```csharp
while (!condition)
{
    Monitor.Wait(_lock);
}
```

rather than:

```csharp
if (!condition)
{
    Monitor.Wait(_lock);
}
```

The `while` is important because the thread must re-check the actual condition after waking.

# 12. Producer / Consumer Example

This makes `Wait()` and `Pulse()` easier to understand.

```csharp
private readonly object _lock = new();

private readonly Queue<int> _queue = new();

public void Produce(int value)
{
    lock (_lock)
    {
        _queue.Enqueue(value);

        Monitor.Pulse(_lock);
    }
}
```

Consumer:

```csharp
public int Consume()
{
    lock (_lock)
    {
        while (_queue.Count == 0)
        {
            Monitor.Wait(_lock);
        }

        return _queue.Dequeue();
    }
}
```

Conceptually:

```text
Consumer

Queue empty?
     │
     YES
     │
   Wait()
     │
     ↓
RELEASE LOCK
     │
     ↓
   WAITING
```

Producer:

```text
Produce item
     │
     ↓
Pulse()
     │
     ↓
Wake one consumer
```

# 13. `Semaphore`

A semaphore is basically a **counter of permits**.

Imagine:

```text
Semaphore = 3 permits

🟢 🟢 🟢
```

Three threads can enter.

```text
Thread A → permit 1
Thread B → permit 2
Thread C → permit 3

Thread D → WAIT
```

When one finishes:

```csharp
semaphore.Release();
```

A permit returns.

```text
🟢
```

Thread D can proceed.

For `SemaphoreSlim`:

```text

 ↓
```

# 15. `SemaphoreSlim` Example

```csharp
var semaphore = new SemaphoreSlim(3);
```

Three concurrent operations are allowed.

```csharp
await semaphore.WaitAsync();

try
{
    await DoWorkAsync();
}
finally
{
    semaphore.Release();
}
```

Visual:

```text
Initial:

[ 🟢 🟢 🟢 ]

A Wait → [ 🔴 🟢 🟢 ]

B Wait → [ 🔴 🔴 🟢 ]

C Wait → [ 🔴 🔴 🔴 ]

D Wait → WAITING
```

A finishes:

```csharp
semaphore.Release();
```

Now:

```text
[ 🟢 🔴 🔴 ]

D can continue
```

---

# 16. `SemaphoreSlim.Release(n)`

You can release multiple permits:

```csharp
semaphore.Release(3);
```

Meaning:

> Return three permits.

Normally, keep acquisition and release balanced:

```text
Wait() / WaitAsync()
       ↓
      work
       ↓
Release()
```

Use `finally` so an exception doesn't accidentally leave a permit permanently taken:

```csharp
await semaphore.WaitAsync();

try
{
    await WorkAsync();
}
finally
{
    semaphore.Release();
}
```

# 17. Semaphore vs Lock

This is extremely important.

### `lock`

```text
Capacity = 1
```

```text
A → enter
B → wait
C → wait
```

### Semaphore

```text
Capacity = N
```

```text
A → permit
B → permit
C → permit
D → wait
```

So:

```text
lock       = one person
semaphore  = N people
```

# 18. Mutex

A `Mutex` also provides mutual exclusion.

```csharp
var mutex = new Mutex();

mutex.WaitOne();

try
{
    // critical section
}
finally
{
    mutex.ReleaseMutex();
}
```

Important APIs:

```text
WaitOne()
ReleaseMutex()
```

Think:

```text
Mutex

WaitOne()
    ↓
"I want ownership"

ReleaseMutex()
    ↓
"I give ownership back"
```

---

# 19. Mutex vs Lock

### `lock`

Normally used for synchronization **inside one process**.

### `Mutex`

Can synchronize between **different processes**.

For example:

```text
Process A
   │
   │
   ├──────────┐
              │
           Mutex
              │
   ├──────────┘
   │
Process B
```

This makes `Mutex` useful for cases such as:

> "Only one instance of this application should run."

For most normal in-process C# synchronization, `lock` is simpler and usually preferred.

# 23. `Monitor.Pulse()` vs Event `Set()`

These can look similar but belong to different synchronization models.

### Monitor

```csharp
Monitor.Pulse(lockObject);
```

Means:

> Wake a thread waiting with `Monitor.Wait()`.

### AutoResetEvent

```csharp
event.Set();
```

Means:

> Signal the event; one waiter can proceed.

The important difference is that `Monitor` signaling is tied to the monitor/lock and a condition predicate, while an event has persistent signaled/non-signaled state.

# 24. `Signal()` — What Does It Mean?

You will see `Signal()` in different synchronization APIs.

Generally:

```text
Signal
=
"Tell another thread/task that something happened."
```

There is no universal `Signal()` method across all .NET synchronization primitives.

Examples:

```text
Monitor          → Pulse()
Semaphore        → Release()
AutoResetEvent   → Set()
CountdownEvent   → Signal()
Barrier          → SignalAndWait()
```

So don't memorize:

```text
Signal = one specific .NET operation
```

Instead remember:

> **Signal means "announce progress/event/completion."**

Then learn the API-specific method that performs the signal.

# 25. `CountdownEvent`

This is excellent for understanding `Signal()`.

Imagine you start five workers:

```text
Worker A ────────┐
Worker B ────────┤
Worker C ────────┤
Worker D ────────┤
Worker E ────────┘
```

You want the main thread to wait until **all five finish**.

Create:

```csharp
var countdown = new CountdownEvent(5);
```

Each worker:

```csharp
try
{
    DoWork();
}
finally
{
    countdown.Signal();
}
```

Main thread:

```csharp
countdown.Wait();
```

Visual:

```text
Initial count = 5

A finishes → Signal() → 4
B finishes → Signal() → 3
C finishes → Signal() → 2
D finishes → Signal() → 1
E finishes → Signal() → 0

                     ↓

                   Wait()
                 RELEASED
```

The best way to remember it:

> `CountdownEvent.Signal()` = **"I finished one unit of work."**

---

# 26. `CountdownEvent.Wait()`

```csharp
countdown.Wait();
```

Means:

> "Wait until the counter reaches zero."

So:

```text
Signal() → decrease counter

Wait() → wait until counter == 0
```

# 27. Barrier

`Barrier` is different.

A barrier means:

> **Everybody reaches this point before anybody proceeds.**

Imagine three threads:

```text
Thread A ────────┐
Thread B ────────┤ → BARRIER
Thread C ────────┘
```

Nobody proceeds until everyone reaches the barrier.

```csharp
var barrier = new Barrier(3);
```

Each thread:

```csharp
DoPhase1();

barrier.SignalAndWait();

DoPhase2();
```

Visual:

```text
A ────────────────┐
B ────────────────┤
C ────────────────┘
                  │
               BARRIER
                  │
                  ↓
A ────────────────┐
B ────────────────┤
C ────────────────┘
```

---

# 28. Barrier APIs

Important:

```csharp
SignalAndWait()
AddParticipant()
RemoveParticipant()
```

The key one:

```csharp
SignalAndWait();
```

Means:

> "I have reached the barrier, and I will wait here until everyone else reaches it."

# 29. CountdownEvent vs Barrier

Very important distinction:

### CountdownEvent

```text
"Wait until everyone finishes."
```

### Barrier

```text
"Wait until everyone reaches this checkpoint."
```

Example:

```text
PHASE 1
   ↓
BARRIER
   ↓
PHASE 2
   ↓
BARRIER
   ↓
PHASE 3
```

A barrier can be reused for multiple phases.

# 30. SpinLock

`SpinLock` is for very short critical sections.

Instead of immediately blocking:

```text
Try lock
   ↓
not available
   ↓
block/sleep
   ↓
wake later
```

a spin lock may repeatedly check:

```text
Try lock
   ↓
not available
   ↓
CPU spins
   ↓
try again
```

This can be useful when the expected wait time is extremely short, but it should not be used casually.

---

# 31. SpinLock APIs

Important:

```csharp
Enter()
TryEnter()
Exit()
```

Example:

```csharp
bool lockTaken = false;

try
{
    spinLock.Enter(ref lockTaken);

    // critical section
}
finally
{
    if (lockTaken)
        spinLock.Exit();
}
```

Memory:

```text
SpinLock

Enter()    → acquire
TryEnter() → try to acquire
Exit()     → release
```


# 34. `CompareExchange`

One of the most important atomic primitives.

Conceptually:

```text
if (value == expected)
{
    value = newValue;
}
```

but performed atomically.

Example:


# 35. Atomicity vs Synchronization

These are not the same.

### Atomicity

```text
"This operation cannot be observed half-done."
```

### Synchronization

```text
"Coordinate multiple threads."
```

Example:

```csharp
Interlocked.Increment(ref counter);
```

provides an atomic increment.

But it does not automatically solve every multi-step synchronization problem.

# 36. Memory Model

Modern CPUs and compilers can reorder operations.

Imagine:

```csharp
data = 42;
ready = true;
```

Another thread may not safely observe the intended ordering unless appropriate synchronization is used.

Synchronization primitives therefore do more than prevent simultaneous access.

They also establish **memory-ordering and visibility guarantees**.

---

# 37. Acquire / Release

This is an excellent mental model.

### Release

> "Everything I did before this point is published before the release."

### Acquire

> "After I acquire, I can safely observe what was published before the corresponding release."

Conceptually:

```text
Thread A                         Thread B

data = 42

RELEASE
   │
   └──────────────────────┐
                          │
                       ACQUIRE
                          │
                          ↓
                       read data
                          ↓
                         42
```

In .NET, the exact memory guarantees depend on the synchronization primitive/operation, but `lock`, `Monitor`, `Interlocked`, and other synchronization mechanisms provide the necessary ordering semantics for their intended use.

---

# 38. `volatile`

Example:

```csharp
private volatile bool _stop;
```

Thread A:

```csharp
_stop = true;
```

Thread B:

```csharp
while (!_stop)
{
    // work
}
```

The important point:

> `volatile` is primarily about **visibility and ordering**, not making arbitrary compound operations atomic.

This is not made atomic simply because the field is volatile:

```csharp
volatile int counter;

counter++;
```

`counter++` is still a read-modify-write sequence.

Use:

```csharp
Interlocked.Increment(ref counter);
```

when you need an atomic increment.

# 44. The Most Important Difference: Release vs Pulse

This deserves special attention.

## `Release()`

Usually means:

> **Give something back.**

Semaphore:

```csharp
semaphore.Release();
```

You return a permit.

```text
[PERMIT]
   ↓
available resource
```

## `Pulse()`

Means:

> **Wake someone who is waiting.**

```csharp
Monitor.Pulse(lockObject);
```

It does not release the monitor.

```text
WAITING THREAD
      ↑
    WAKE UP
```

Remember:

```text
Release = return a resource/permit/ownership

Pulse = wake a Monitor waiter
```

# 45. Why `Monitor.Wait()` Is Special

`Monitor.Wait()` has a very specific lifecycle:

```text
lock
  ↓
condition false
  ↓
Wait()
  ↓
release lock
  ↓
WAITING
  ↓
Pulse()
  ↓
wake
  ↓
reacquire lock
  ↓
Wait() returns
  ↓
check condition again
```

This is the key to understanding `Monitor`.

## Full example

```csharp
lock (_lock)
{
    while (!_dataAvailable)
    {
        Monitor.Wait(_lock);
    }

    ConsumeData();
}
```

Producer:

```csharp
lock (_lock)
{
    _dataAvailable = true;
    Monitor.Pulse(_lock);
}
```

The consumer doesn't simply wake and run immediately.

After `Pulse()`, it must **reacquire the monitor** before `Wait()` returns.

# 53. Final Rule of Thumb

When you see an unfamiliar synchronization API, ask these five questions:

1. **What am I waiting for?**
2. **What resource/state am I acquiring?**
3. **What does the release operation give back?**
4. **What wakes the waiter?**
5. **Does the waiter reacquire a lock before continuing?**

If you can answer those five questions, you understand the synchronization primitive rather than merely memorizing its methods.

## One-line memory summary

```text
Enter  → get ownership
Wait   → stop and wait
Exit   → give ownership back
Release → return permit/resource
Pulse  → wake one Monitor waiter
PulseAll → wake all Monitor waiters
Signal → announce progress/completion
Set    → signal an event
Reset  → unsignal an event
Join   → wait for a thread to finish
SignalAndWait → announce "I'm here" and wait for everyone
Interlocked → perform one atomic operation
volatile → visibility/order semantics, not general atomicity
```
