## C# Interview Notes: Synchronization, Span, Stack, and Queue

#### 1. `lock`, `Monitor`, and `Interlocked`

Covered once, with `Mutex` and `SemaphoreSlim`, in the [synchronization primitives section](#senior-dotnet-async-locking-distributed-guide-md) below.

---

#### 2. `Span<T>` and `Slice()`

`Span<T>` is a lightweight view over contiguous memory. It lets you access a portion of an array or other supported memory without copying the elements.

##### Slice an array

```csharp
int[] numbers = { 10, 20, 30, 40, 50 };

Span<int> span = numbers;
Span<int> middle = span.Slice(1, 3); // 20, 30, 40

middle[0] = 99;

Console.WriteLine(string.Join(", ", numbers));
// 10, 99, 30, 40, 50
```

`Slice(start, length)` uses a **zero-based start index** and a **number of elements**, not an ending index. The slice refers to the original memory, so changes to its elements affect the array.

You can also use range syntax:

```csharp
Span<int> middle = span[1..4]; // indices 1, 2, and 3
```

##### Slice a string without immediately creating a substring

Strings are immutable, so use `ReadOnlySpan<char>` to view their characters.

```csharp
string text = "Hello, World!";
ReadOnlySpan<char> word = text.AsSpan(7, 5);

Console.WriteLine(word.ToString()); // World
```

Calling `ToString()` creates a string. If you can process the span directly, you can avoid that allocation.

##### Important limitations

- A slice must stay within the source span's bounds.
- `Span<T>` and `ReadOnlySpan<T>` are `ref struct` types; they cannot be stored in ordinary class fields or used across `await`/`yield` boundaries in the usual way.
- `ReadOnlySpan<T>` prevents writes through that view; it does not necessarily make the underlying data immutable through other references.

---

#### 3. Stack and Queue in C#

A **stack** is LIFO (last in, first out); a **queue** is FIFO (first in, first out). Use the built-in generic collections unless you specifically need to implement the data structures yourself.

Built-in `Stack<T>` / `Queue<T>` members and `TryPop`/`TryDequeue` are covered in [C# Language → Standard collections](01-csharp-language-and-quality.md#csharp-data-types-and-collections-cheatsheet-md). Below is how you'd build them yourself, which is a common whiteboard question.

##### Custom implementations with a linked list

The following implementations demonstrate the underlying logic. Each operation that adds or removes an item takes **O(1)** time.

```csharp
using System;

public sealed class CustomStack<T>
{
    private sealed class Node
    {
        public T Value { get; }
        public Node? Next { get; set; }

        public Node(T value) => Value = value;
    }

    private Node? _top;
    public int Count { get; private set; }

    public void Push(T item)
    {
        _top = new Node(item) { Next = _top };
        Count++;
    }

    public T Pop()
    {
        if (_top is null)
            throw new InvalidOperationException("Stack is empty.");

        T value = _top.Value;
        _top = _top.Next;
        Count--;
        return value;
    }

    public T Peek() =>
        _top is null
            ? throw new InvalidOperationException("Stack is empty.")
            : _top.Value;
}

public sealed class CustomQueue<T>
{
    private sealed class Node
    {
        public T Value { get; }
        public Node? Next { get; set; }

        public Node(T value) => Value = value;
    }

    private Node? _front;
    private Node? _rear;
    public int Count { get; private set; }

    public void Enqueue(T item)
    {
        var node = new Node(item);

        if (_rear is null)
            _front = _rear = node;
        else
        {
            _rear.Next = node;
            _rear = node;
        }

        Count++;
    }

    public T Dequeue()
    {
        if (_front is null)
            throw new InvalidOperationException("Queue is empty.");

        T value = _front.Value;
        _front = _front.Next;

        if (_front is null)
            _rear = null;

        Count--;
        return value;
    }

    public T Peek() =>
        _front is null
            ? throw new InvalidOperationException("Queue is empty.")
            : _front.Value;
}
```

The custom classes use nullable reference annotations (`Node?`), so enable nullable reference types in the project (for example, `<Nullable>enable</Nullable>` in the project file). They are educational examples and are not thread-safe.

---

#### 4. Complexity summary

| Structure / operation | Typical time |
|---|---:|
| Stack `Push`, `Pop`, `Peek` | O(1) |
| Queue `Enqueue`, `Dequeue`, `Peek` | O(1) |
| `Span<T>` indexing | O(1) |
| `Span<T>.Slice()` | O(1) |

`Span<T>.Slice()` creates a view, not a copy. Creating a stack or queue item, by contrast, stores an element in a collection.

#### 5. Practical guidance

- Prefer `Stack<T>` and `Queue<T>` for normal application code.
- Build custom collections when learning data structures or when requirements call for specialized behavior.
- Use `Span<T>` for efficient processing of buffers, arrays, and character data.
- Use `lock` to guard multi-step changes to shared state and `Interlocked` for simple atomic updates.

## Task Parallelism in C# — Interview Notes

A concise guide to `Task`, `Task.WhenAll`, `Parallel.ForEach`, exception handling, cancellation, and choosing the right approach.

Concurrency vs parallelism vs asynchrony, and thread vs task, are explained in the threading viva section below. This part focuses on the **APIs**.

#### 1. Run one operation with `Task.Run`

```csharp
using System;
using System.Threading.Tasks;

class Program
{
    static async Task Main()
    {
        Console.WriteLine("Start");

        int result = await Task.Run(() => CalculateSquare(12));

        Console.WriteLine($"Result: {result}");
        Console.WriteLine("End");
    }

    static int CalculateSquare(int number) => number * number;
}
```

Use `Task.Run` when you need to move CPU-bound work off a responsive thread, such as a UI thread. In ASP.NET Core, avoid wrapping ordinary synchronous work in `Task.Run` just to make a request handler appear asynchronous.

#### 2. Run independent asynchronous operations with `Task.WhenAll`

This is a common pattern when several I/O operations can happen independently, such as API calls or database queries.

```csharp
using System;
using System.Threading.Tasks;

class Program
{
    static async Task Main()
    {
        Task<string> userTask = FetchUserAsync();
        Task<string> ordersTask = FetchOrdersAsync();
        Task<string> alertsTask = FetchAlertsAsync();

        // All three operations have been started before we await them.
        await Task.WhenAll(userTask, ordersTask, alertsTask);

        Console.WriteLine(await userTask);
        Console.WriteLine(await ordersTask);
        Console.WriteLine(await alertsTask);
    }

    static async Task<string> FetchUserAsync()
    {
        await Task.Delay(500); // Simulates asynchronous I/O
        return "User loaded";
    }

    static async Task<string> FetchOrdersAsync()
    {
        await Task.Delay(700);
        return "Orders loaded";
    }

    static async Task<string> FetchAlertsAsync()
    {
        await Task.Delay(300);
        return "Alerts loaded";
    }
}
```

The simulated operations overlap, so total elapsed time is roughly the duration of the slowest operation, plus overhead—not the sum of all delays. `Task.Delay` is used here instead of blocking with `.Wait()`.

##### Collect results directly

```csharp
Task<int> first = GetNumberAsync(10);
Task<int> second = GetNumberAsync(20);

int[] results = await Task.WhenAll(first, second);
// results: [20, 40]

static async Task<int> GetNumberAsync(int value)
{
    await Task.Delay(100);
    return value * 2;
}
```

`Task.WhenAll` preserves the input task order in its result array; completion order may differ.

#### 3. CPU-bound loops with `Parallel.ForEach`

Use this for independent, CPU-intensive work on collection items—not as a default replacement for asynchronous I/O.

```csharp
using System;
using System.Linq;
using System.Threading.Tasks;

class Program
{
    static void Main()
    {
        int[] numbers = Enumerable.Range(1, 5).ToArray();
        int[] squares = new int[numbers.Length];

        Parallel.ForEach(numbers, (number, state, index) =>
        {
            squares[index] = number * number;
        });

        Console.WriteLine(string.Join(", ", squares));
        // 1, 4, 9, 16, 25
    }
}
```

Each iteration writes to a distinct array index, avoiding shared-write conflicts. The execution order is not guaranteed.

##### Avoid race conditions

This is unsafe because multiple iterations can update `total` at the same time:

```csharp
int total = 0;

Parallel.ForEach(numbers, number =>
{
    total += number; // Race condition
});
```

Use the loop's thread-local accumulation overload instead:

```csharp
int total = 0;

Parallel.ForEach(
    numbers,
    () => 0,                         // Initial local total per worker
    (number, state, localTotal) => localTotal + number,
    localTotal => Interlocked.Add(ref total, localTotal));

Console.WriteLine(total);
```

For simple sums, LINQ's `numbers.Sum()` is usually clearer; parallelism is not automatically faster for small workloads.

#### 4. `Parallel.For`

```csharp
using System;
using System.Threading.Tasks;

class Program
{
    static void Main()
    {
        Parallel.For(1, 6, i =>
        {
            Console.WriteLine($"{i} squared = {i * i}");
        });
    }
}
```

The upper bound is **exclusive**, so this loop processes `1` through `5`. Output order can vary.

#### 5. Exceptions

Exceptions from a task are observed when it is awaited. With `Task.WhenAll`, all supplied tasks are allowed to complete; the task returned by `WhenAll` records the failures.

```csharp
Task allTask = Task.WhenAll(
    Task.Run(() => throw new InvalidOperationException("First failed")),
    Task.Run(() => throw new ArgumentException("Second failed")));

try
{
    await allTask;
}
catch
{
    if (allTask.Exception is { } aggregate)
    {
        foreach (Exception error in aggregate.Flatten().InnerExceptions)
            Console.WriteLine(error.Message);
    }
}
```

Place this code inside an `async` method. `await` typically throws one underlying exception; inspect `allTask.Exception` when you need all failures.

#### 6. Cancellation with `CancellationToken`

Cancellation is cooperative: the operation must observe the token and stop. Pass the token to the operation and use APIs that support cancellation.

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

class Program
{
    static async Task Main()
    {
        using var cts = new CancellationTokenSource();
        cts.CancelAfter(TimeSpan.FromSeconds(2));

        try
        {
            await ProcessAsync(cts.Token);
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine("Operation canceled.");
        }
    }

    static async Task ProcessAsync(CancellationToken token)
    {
        for (int i = 1; i <= 10; i++)
        {
            token.ThrowIfCancellationRequested();

            Console.WriteLine($"Processing item {i}");
            await Task.Delay(500, token);
        }
    }
}
```

Cancellation does not forcibly kill arbitrary code. CPU-bound loops should periodically check the token; asynchronous APIs should receive it when supported.

#### 7. Quick decision guide

| Situation | Prefer |
|---|---|
| Several independent async API/database/I/O calls | Start each operation, then `await Task.WhenAll(...)` |
| CPU-heavy calculation that can use multiple cores | `Parallel.For` / `Parallel.ForEach`, or `Task.Run` for one offloaded operation |
| Need one operation's future result | `Task<T>` |
| Need to wait for all operations | `Task.WhenAll` |
| Need cancellation | `CancellationToken` / `CancellationTokenSource` |
| Need to process a small collection of simple values | A normal loop or LINQ may be simpler and faster |

#### 8. Interview points to remember

1. `await` does not itself create a new thread.
2. `Task.WhenAll` waits for multiple tasks; it does not start cold, unstarted tasks automatically. Calling async methods usually starts their operations.
3. `Task.Run` is generally for CPU-bound work or deliberately offloading work—not a requirement for asynchronous I/O.
4. `Parallel.ForEach` is synchronous and blocks the caller until the loop finishes.
5. Do not mutate shared state from parallel iterations without synchronization or a thread-safe approach.
6. Do not use `.Wait()` or `.Result` in ordinary async code when `await` is available; blocking can cause thread starvation and, in some contexts, deadlocks.
7. Parallel work has overhead. Measure before using it for small tasks.
8. For database work, use the database driver's asynchronous APIs. Do not run concurrent operations on the same EF Core `DbContext`; use separate contexts when truly running independent EF Core operations concurrently.

## .NET Threading and Async/Await — Senior Developer Viva Preparation

#### 1. The Big Picture

In .NET, **threads**, **tasks**, **concurrency**, **parallelism**, and **asynchronous programming** are related, but they are not the same thing.

- **Thread:** An execution path managed by the operating system.
- **Task:** A .NET representation of an operation that may complete in the future. A task is not itself a thread.
- **Concurrency:** Multiple operations make progress during overlapping periods; they do not have to run at the exact same instant.
- **Parallelism:** Multiple operations execute at the same instant, typically on different CPU cores.
- **Asynchronous I/O:** An operation such as an HTTP request or database call can wait for I/O without occupying a thread for the entire wait.

**Senior-level rule of thumb:** Use `async`/`await` for naturally asynchronous I/O, `Task.Run` for CPU-bound work that should run away from the current thread, and direct `Thread` management only when you genuinely need a dedicated thread or low-level thread controls.

---

#### 2. What Are the Ways to Start Work on Another Thread?

There is no single official count of ways to “create a thread,” because .NET offers several levels of abstraction. These are the common approaches:

##### A. Create a `Thread` directly

```csharp
using System;
using System.Threading;

var thread = new Thread(() =>
{
    Console.WriteLine($"Running on thread {Environment.CurrentManagedThreadId}");
});

thread.Start();
thread.Join();
```

This creates a dedicated operating-system thread. Use it when you need low-level control, such as setting thread priority or managing a dedicated thread's lifetime. Creating threads has more overhead than reusing thread-pool workers.

##### B. Queue work to the `ThreadPool`

```csharp
using System;
using System.Threading;

ThreadPool.QueueUserWorkItem(_ =>
{
    Console.WriteLine($"Running on thread {Environment.CurrentManagedThreadId}");
});
```

The .NET thread pool reuses worker threads, avoiding the cost of creating a new thread for every short operation. It is useful for short-running work, but it does not provide the same direct lifecycle control as `Thread`.

##### C. Use `Task.Run`

```csharp
Task task = Task.Run(() =>
{
    DoCpuBoundWork();
});

await task;
```

`Task.Run` normally queues CPU-bound work to the thread pool. It gives you task composition, exception propagation, cancellation-token support, and APIs such as `Task.WhenAll`. It does **not** mean that every `Task` creates a new thread.

##### D. Use `async`/`await` with an asynchronous API

```csharp
async Task<string> GetDataAsync(HttpClient httpClient, string url)
{
    return await httpClient.GetStringAsync(url);
}
```

This is asynchronous I/O. While the HTTP request is waiting for a response, the application generally does not need to keep a worker thread blocked for that wait. `async`/`await` does not automatically create a new thread.

> **Important distinction:** `new Thread(...)` creates a thread. `Task.Run(...)` schedules work, usually on a thread-pool thread. Calling an asynchronous I/O API starts or represents an asynchronous operation; it does not necessarily create a thread.

---

#### 3. What Do `Start()` and `Join()` Do?

##### `Start()`

`Thread.Start()` asks the runtime to begin executing the thread's entry-point method.

```csharp
var thread = new Thread(() => Console.WriteLine("Worker started"));
thread.Start();
```

Creating a `Thread` object alone does not run its delegate. You must call `Start()`.

##### `Join()`

`Thread.Join()` blocks the calling thread until the target thread finishes.

```csharp
var thread = new Thread(() =>
{
    Thread.Sleep(500);
    Console.WriteLine("Worker finished");
});

thread.Start();
thread.Join(); // The calling thread waits here.
Console.WriteLine("Continue after worker completes");
```

Use `Join()` when synchronous waiting for a particular thread is required. In asynchronous code, prefer task-based coordination such as `await task` rather than blocking with `.Wait()` or `.Result`.

---

#### 4. How Can We Get a Return Value from Work on a Thread?

A `Thread` does not have a built-in return-value mechanism. You can communicate through a shared variable, but you must coordinate access and ensure the worker has completed before reading the result.

```csharp
int result = 0;

var thread = new Thread(() =>
{
    result = 42;
});

thread.Start();
thread.Join();

Console.WriteLine(result); // 42
```

For ordinary application code, a generic task is usually clearer:

```csharp
Task<int> task = Task.Run(() => CalculateValue());

int result = await task;
Console.WriteLine(result);

static int CalculateValue() => 42;
```

`Task<T>` represents an operation that produces a value of type `T`. Awaiting it also propagates exceptions from the operation. Avoid `.Result` in asynchronous code when you can use `await`, because `.Result` blocks the calling thread and can contribute to deadlocks in some synchronization contexts.

---

#### 5. `Thread` vs. `Task`

| Topic | `Thread` | `Task` |
|---|---|---|
| Meaning | An execution thread | A representation of an operation |
| Thread creation | `new Thread(...)` creates a dedicated thread | A task may use a thread pool, an existing thread, or no thread while awaiting I/O |
| Return value | No built-in return value | `Task<T>` supports a result |
| Waiting | `Join()` | Prefer `await`; `.Wait()` and `.Result` block |
| Exceptions | Exceptions escaping the thread entry point are not exposed through a task object | Exceptions are stored in the task and observed when awaited or otherwise inspected |
| Composition | Manual coordination is often needed | Supports `WhenAll`, `WhenAny`, continuations, and cancellation tokens |
| Low-level control | Supports controls such as priority and thread lifetime | Does not provide direct control over a specific worker thread |
| Typical use | Dedicated thread or special low-level requirements | Most application-level asynchronous and concurrent operations |

**Interview answer:** A thread is a mechanism for executing code. A task represents work and its completion. A task may use a thread, but the two are not interchangeable.

---

#### 6. What Is the Role of the Thread Pool?

The .NET thread pool is a runtime-managed collection of reusable worker threads. It helps run short background operations without repeatedly creating and destroying threads.

Common users include `Task.Run`, many task-scheduling operations, and `ThreadPool.QueueUserWorkItem`.

##### Benefits

- Reuses threads and reduces thread-creation overhead.
- Helps the runtime manage worker-thread availability.
- Integrates with the Task Parallel Library.

##### Limitations

- Blocking thread-pool workers for long periods can reduce throughput and delay other work.
- It does not provide a dedicated thread for each task.
- Thread-pool scheduling does not guarantee which thread will run a particular task.

For long-running services in ASP.NET Core, use a hosted service such as `BackgroundService` for lifecycle management rather than creating an unmanaged infinite loop in a request handler. A hosted service still needs an appropriate strategy for CPU-bound work, blocking work, cancellation, and resource management.

---

#### 7. Is a Task Multithreaded?

**No—not necessarily.** A task represents an operation, not a promise that a new or separate thread will be used.

##### Example 1: Asynchronous I/O

```csharp
async Task<string> LoadAsync(HttpClient client, string url)
{
    return await client.GetStringAsync(url);
}
```

The HTTP operation can wait without occupying a thread for the whole wait. The method resumes when the awaited operation completes. Depending on the environment and continuation context, the continuation may run on a different thread.

##### Example 2: CPU-bound work using `Task.Run`

```csharp
Task<int> first = Task.Run(() => Calculate(10));
Task<int> second = Task.Run(() => Calculate(20));

int[] results = await Task.WhenAll(first, second);
```

Both calculations can run concurrently on thread-pool workers, and may run in parallel if resources and scheduling allow. Parallel execution is not guaranteed merely because two tasks were created.

##### Example 3: A task that runs synchronously

```csharp
Task<int> task = Task.FromResult(42);
int result = await task;
```

This task is already completed; it does not need to schedule work on another thread.

---

#### 8. Concurrency vs. Multithreading vs. Parallelism

These terms describe different aspects of execution:

- **Concurrency:** Several operations are in progress over an overlapping period. A single thread can coordinate concurrent asynchronous I/O by starting operations and awaiting their completion.
- **Multithreading:** An application uses multiple threads. Those threads may take turns on one CPU core or run on multiple cores.
- **Parallelism:** Multiple pieces of work execute at the same time, commonly on separate CPU cores.
- **Asynchrony:** The caller can continue without synchronously waiting for an operation to finish. Asynchrony does not automatically mean multithreading or parallelism.

##### Concurrent I/O example

```csharp
async Task<string[]> LoadBothAsync(HttpClient client)
{
    Task<string> first = client.GetStringAsync("https://example.com");
    Task<string> second = client.GetStringAsync("https://example.org");

    return await Task.WhenAll(first, second);
}
```

Both requests are started before the method awaits their combined completion. Their I/O waits overlap; this does not require one dedicated thread per request.

##### Parallel CPU-work example

```csharp
Parallel.For(0, 100, i =>
{
    ProcessItem(i);
});
```

`Parallel.For` is designed for parallel CPU work. It may execute iterations on multiple threads, subject to runtime scheduling and available resources. It is not the default choice for I/O-bound operations.

##### Quick comparison

| Concept | Main idea | Example |
|---|---|---|
| Concurrency | Multiple operations make progress over overlapping periods | Start multiple HTTP requests and await them |
| Multithreading | Multiple threads are used | A worker thread plus the main thread |
| Parallelism | Work executes simultaneously | CPU calculations across multiple cores |
| Asynchrony | Avoid blocking while waiting | `await ReadAsync(...)` |

---

#### 9. When Should a Senior .NET Developer Use Each Approach?

| Scenario | Recommended approach |
|---|---|
| HTTP, database, or file I/O with async APIs | Use the API's async method and `await` |
| CPU-bound work that should not run on the current thread | Consider `Task.Run` where appropriate |
| Parallel CPU calculations over independent items | Consider `Parallel.For`, `Parallel.ForEach`, or suitable task-based parallelism |
| Need explicit control over a dedicated thread | Use `Thread` only when the requirement justifies it |
| Background processing in an ASP.NET Core service | Use `IHostedService` / `BackgroundService` with cancellation and proper lifecycle handling |
| Run several asynchronous operations and await all | Use `Task.WhenAll` |
| Need a result from asynchronous work | Use `Task<T>` and `await` |

##### Two common mistakes to avoid

1. **Wrapping asynchronous I/O in `Task.Run` without a reason.** For example, prefer `await httpClient.GetStringAsync(url)` over `await Task.Run(() => httpClient.GetStringAsync(url))`.
2. **Blocking asynchronous work unnecessarily.** In async call chains, prefer `await task` over `task.Wait()` or `task.Result`.

---

#### 10. Senior-Level Viva Questions and Short Answers

**Q: Does `async` create a thread?**  
A: No. `async` enables a method to use `await`. Whether threads are involved depends on the operation being awaited.

**Q: Does `await` block a thread?**  
A: Normally, `await` suspends the async method when the awaited operation is incomplete and returns control to its caller. It does not synchronously block the current thread while waiting.

**Q: Does every task run on the thread pool?**  
A: No. `Task.Run` normally uses the thread pool, but tasks can represent I/O operations, already-completed results, or work scheduled through other mechanisms.

**Q: Is multithreading always faster?**  
A: No. Thread scheduling, synchronization, contention, and context switching have costs. Parallelism helps mainly when work can be divided effectively and resources are available.

**Q: Can two tasks run on the same thread?**  
A: Yes. Tasks are not permanently bound to distinct threads. A task may execute synchronously, and asynchronous continuations can run on a thread selected by the scheduler or synchronization context.

**Q: What should I use instead of `Thread.Sleep` in async code?**  
A: Use `await Task.Delay(duration, cancellationToken)` when an asynchronous delay is intended. `Thread.Sleep` blocks the current thread.

**Q: What is the difference between `Task.WhenAll` and `Task.WaitAll`?**  
A: `Task.WhenAll` returns a task that completes when all supplied tasks complete and can be awaited without blocking the calling thread. `Task.WaitAll` blocks the calling thread until all tasks complete.

**Q: If a web API needs to call three independent services, should I use three threads?**  
A: Usually no. Start the three asynchronous I/O operations and await them with `Task.WhenAll`, assuming they are independent and the downstream services can handle the concurrent requests.

---

#### Final Takeaway

For most modern .NET application code, **prefer the Task-based model**. Use `async`/`await` for asynchronous I/O, use `Task.Run` or parallel APIs for suitable CPU-bound work, and use `Thread` when you specifically need low-level thread control. Always distinguish the operation (`Task`), the execution resource (`Thread`), overlapping progress (concurrency), and simultaneous execution (parallelism).

## Senior .NET Interview Guide: Async, Threading, and Locking

> A consolidated reference for senior .NET developer and solution architect interviews. Repeated explanations have been removed; related topics are grouped together.

#### 1. Core mental models

- **`async`/`await` is not automatically multithreading.** It is a way to compose asynchronous operations without blocking a thread while an operation is incomplete.
- **I/O-bound work:** use genuinely asynchronous APIs, such as `HttpClient.GetAsync`, EF Core async methods, and `File.ReadAllTextAsync`.
- **CPU-bound work:** consumes CPU while it runs. `async` does not make the calculation faster or remove its CPU cost.
- **`Task` represents an operation**, not necessarily a dedicated thread.
- ASP.NET Core does not normally have a custom request `SynchronizationContext`. Blocking async work is still harmful because it occupies ThreadPool threads and can cause starvation.
- Prefer async end-to-end for I/O. Do not add `Task.Run` merely to make synchronous I/O look asynchronous.

#### 2. `Task`, `async`/`await`, `Task.Run`, and `Task.FromResult`

##### `async`/`await`: compose asynchronous work

```csharp
[HttpGet]
public async Task<IActionResult> Get(CancellationToken cancellationToken)
{
    var data = await _repository.GetAsync(cancellationToken);
    return Ok(data);
}
```

When the awaited task is incomplete, the method suspends and its current thread can do other work. When the operation completes, the method's continuation runs later, possibly on another ThreadPool thread.

##### `Task.Run`: queue CPU work to the ThreadPool

```csharp
[HttpGet("calculation")]
public async Task<IActionResult> GetCalculation()
{
    var result = await Task.Run(() => HeavyCpuCalculation());
    return Ok(result);
}
```

This can be reasonable for a **short, bounded CPU calculation** when the result is needed in the same request and measurements justify moving the calculation off the current request-execution thread. It is not a default ASP.NET Core performance technique: `Task.Run` still consumes ThreadPool capacity and CPU. Under high concurrency, it can worsen contention and latency.

For heavy, lengthy, or high-volume calculations, prefer a bounded worker pool, durable queue, or separately scalable compute service. Return `202 Accepted` with a job ID when the result will be available later.

Do not use `Task.Run` for ordinary asynchronous I/O, and do not fire-and-forget it from a controller:

```csharp
Task.Run(() => DoWork()); // unsafe fire-and-forget in a web request
```

The work may be lost on process shutdown, exceptions may go unobserved, and the application has no durable retry or coordination guarantee.

##### `Task.FromResult`: return an already-known value as a completed task

```csharp
public Task<bool> IsFeatureEnabledAsync()
{
    return Task.FromResult(true);
}
```

Use it when an API contract requires `Task<T>` but the result is already available synchronously, such as a cache hit, simple in-memory result, or test mock. It **does not** run work asynchronously.

Incorrect:

```csharp
return Task.FromResult(DoBlockingWork()); // DoBlockingWork runs before Task.FromResult
```

Use a genuinely asynchronous API for I/O instead.

##### `Task.Run` vs `Task.FromResult`

| Need | Appropriate choice |
|---|---|
| Await database/network/file I/O | Async API + `await` |
| Return a value already available synchronously from a `Task<T>` method | `Task.FromResult(value)` |
| Run CPU work on a ThreadPool thread | `Task.Run`, only when justified |
| Durable, long-running background job | Queue + worker/job system |
| Make blocking I/O “async” | Neither |

#### 3. Synchronization primitives: `lock`, `Monitor`, `Mutex`, `Semaphore`, `SemaphoreSlim`

When several threads touch shared state, synchronization prevents race conditions. Choose based on what you need: **exclusive access**, **signaling** between threads, or a **limit** on how many can enter at once.

| Feature | `lock` | `Monitor` | `Mutex` | `Semaphore` | `SemaphoreSlim` |
|---|---|---|---|---|---|
| Typical scope | One process | One process | One process, or **across processes** when named | One process, or **across processes** when named | One process |
| How many can enter | 1 | 1 | 1 (one owner) | Up to N | Up to N |
| Timeout support | Not directly | Yes (`TryEnter`) | Yes (`WaitOne(timeout)`) | Yes (`WaitOne(timeout)`) | Yes (`Wait`/`WaitAsync(timeout)`) |
| Thread signaling (`Wait`/`Pulse`) | No | Yes | No | No | No |
| Async waiting | No (no `await` inside) | No | No (blocks a thread) | No (blocks a thread) | **Yes**, via `WaitAsync` |
| Owned by the acquiring thread? | Yes | Yes | Yes (same thread must release) | No | No |
| Overhead | Low | Low | Higher (OS kernel object) | Higher (OS kernel object) | Lightweight |

**Common misconception:** `lock` *is* `Monitor` underneath. A `Mutex` is not just a "low-level lock", and a `Semaphore` is not automatically process-wide. Only **named** `Mutex`/`Semaphore` instances coordinate across processes; unnamed ones work within one process.

##### `lock`: one thread at a time in a critical section

```csharp
private readonly object _gate = new();
private int _counter;

public void Increment()
{
    lock (_gate)
    {
        _counter++;
    }
}
```

- If the gate is free, the thread enters.
- If another thread owns it, the contender blocks until it can enter.
- The lock is released automatically when control exits the block, including when an exception is thrown.
- Use a private dedicated object; do not lock on `this`, a string, or a public object.
- All threads must lock on the **same** object; otherwise they don't coordinate at all.
- Keep the critical section short.
- `lock` is reentrant for the owning thread.
- Do not use `await` inside a `lock` block.

##### `Monitor`: `lock` plus explicit coordination

`lock (gate)` is conceptually implemented using `Monitor.Enter` and `Monitor.Exit` in a `try/finally`. Use `Monitor` directly when you specifically need `TryEnter`, `Wait`, `Pulse`, or `PulseAll`.

**1) Acquire with a timeout (`TryEnter`).** `lock` waits forever; `Monitor.TryEnter` lets you give up.

```csharp
private readonly object _sync = new();

public void UpdateWithTimeout()
{
    bool lockTaken = false;

    try
    {
        Monitor.TryEnter(_sync, TimeSpan.FromSeconds(2), ref lockTaken);

        if (!lockTaken)
        {
            Console.WriteLine("Could not acquire the lock in time.");
            return;
        }

        // Critical section
    }
    finally
    {
        if (lockTaken)
            Monitor.Exit(_sync); // only exit if we actually entered
    }
}
```

The `ref bool lockTaken` overload is the safe pattern: even if an exception happens mid-acquire, you know exactly whether to call `Exit`.

**2) Wait for a condition and signal (`Wait` / `Pulse`).** This is the classic producer/consumer:

```csharp
private readonly object _gate = new();
private bool _dataAvailable;

public void WaitForData()
{
    lock (_gate)
    {
        while (!_dataAvailable)
        {
            Monitor.Wait(_gate); // releases gate and waits
        }

        // The condition is true and this thread owns gate again.
        ConsumeData();
    }
}

public void PublishData()
{
    lock (_gate)
    {
        ProduceData();
        _dataAvailable = true;
        Monitor.Pulse(_gate); // wake one waiter
    }
}
```

Important details:

- `Monitor.Wait(gate)` requires the current thread to own the monitor. It releases the monitor and waits.
- `Pulse(gate)` moves one waiting thread toward being eligible to reacquire the monitor; it does **not** immediately transfer ownership.
- `PulseAll(gate)` makes all waiting threads eligible to compete to reacquire the monitor.
- A pulsed thread cannot continue past `Wait` until it reacquires the monitor.
- Always check the condition in a `while`, not an `if`: the condition may no longer be true when the thread reacquires the monitor.
- Signal after updating the shared state, while holding the same monitor.

##### `Mutex`: one owner across processes

```csharp
using var mutex = new Mutex(false, @"Global\MyApplicationJob");

bool ownsMutex = false;
try
{
    try
    {
        ownsMutex = mutex.WaitOne(TimeSpan.FromSeconds(5));
    }
    catch (AbandonedMutexException)
    {
        // The previous owner died. The caller now owns the mutex,
        // but must validate/recover the protected resource.
        ownsMutex = true;
    }

    if (!ownsMutex)
        throw new TimeoutException("Could not acquire the mutex.");

    DoProtectedWork();
}
finally
{
    if (ownsMutex)
        mutex.ReleaseMutex();
}
```

A named mutex can coordinate processes on supported operating systems. `WaitOne` blocks a thread, and ownership is thread-affine: the owning thread must release it. An abandoned mutex indicates that the previous owner terminated without releasing it; protected data may be inconsistent and needs recovery. For web applications, do not use a mutex as a substitute for durable distributed job coordination.

- The `Global\` prefix makes the name visible across user sessions on Windows; behavior and permissions vary by OS, so test in the real deployment environment.
- A mutex is an OS kernel object, so it costs more than an in-process `lock`. Don't use it when `lock` is enough.
- Classic use: **allow only one instance of an app to run** (try to acquire a named mutex at startup; exit if you can't).

##### `Semaphore`: up to N entrants, optionally across processes

A semaphore lets a fixed number of threads in at once. An initial count of `3` means three can enter concurrently and a fourth waits.

```csharp
using var semaphore = new Semaphore(initialCount: 3, maximumCount: 3);

if (semaphore.WaitOne(TimeSpan.FromSeconds(5)))
{
    try
    {
        // Up to three threads can be in this section concurrently.
    }
    finally
    {
        semaphore.Release();
    }
}
else
{
    Console.WriteLine("No slot became available in time.");
}
```

- A **named** `Semaphore` (`new Semaphore(3, 3, "MyApp_Slots")`) can limit concurrency across processes.
- Unlike a mutex, a semaphore has **no owner**: any thread can call `Release`. Release exactly once per successful wait; releasing too often throws `SemaphoreFullException`, and releasing too rarely leaks slots.
- `WaitOne` blocks a thread. Inside one process, and especially in async code, prefer `SemaphoreSlim`.

##### `SemaphoreSlim`: allow up to N concurrent entrants

```csharp
private readonly SemaphoreSlim _slots = new(initialCount: 3, maxCount: 3);

public async Task ProcessAsync(CancellationToken cancellationToken)
{
    await _slots.WaitAsync(cancellationToken);
    try
    {
        await CallDownstreamServiceAsync(cancellationToken);
    }
    finally
    {
        _slots.Release();
    }
}
```

- At most three operations can hold a slot concurrently.
- When the count reaches zero, additional callers wait asynchronously.
- `Release` returns a slot and allows a waiter to proceed.
- Always release in `finally`.
- The count limits concurrency only within this `SemaphoreSlim` instance/process. It does not impose a cluster-wide limit.
- `SemaphoreSlim(1, 1)` can serialize async operations, but it is not owner-thread-affine in the way `Mutex` is.

##### How do you allow more than one thread into a protected region?

Use a semaphore with a count greater than one, such as `SemaphoreSlim(5, 5)`, to permit up to five concurrent entrants. This is a **concurrency limit**, not exclusive mutual exclusion. Ensure the shared resource is safe for concurrent access; a semaphore does not make arbitrary shared state thread-safe.

##### Quick selection guide

| Requirement | Choose |
|---|---|
| Protect a short in-memory update | `lock` |
| Same, but give up after a timeout | `Monitor.TryEnter` |
| Wait for a condition and signal waiters | `Monitor.Wait` / `Pulse` / `PulseAll` |
| Exclusive access across processes on one machine | Named `Mutex` |
| Limit to N concurrent entrants across processes | Named `Semaphore` |
| Limit async operations in one process to N | `SemaphoreSlim(N, N)` |
| Coordinate ownership across multiple servers | Database/queue/distributed coordination pattern |
| Make a long-running job durable | Durable queue or job store, not a lock |

##### `Interlocked`: atomic update of a single value

For one simple counter or flag you don't need a lock. `Interlocked` does it atomically, but it can't protect a multi-step operation.

```csharp
private int _requestCount;

public void RecordRequest() => Interlocked.Increment(ref _requestCount);
```

Other members: `Add`, `Exchange`, `CompareExchange` (compare-and-swap), `Read` (for 64-bit values on 32-bit platforms).

#### 4. Deadlocks and ThreadPool starvation

##### Lock-order deadlock

Thread A acquires lock A and waits for B; thread B acquires B and waits for A. Prevent this by acquiring multiple locks in a consistent global order, keeping lock scopes short, and avoiding unnecessary nested locks.

##### Sync-over-async

```csharp
var result = GetDataAsync().Result; // blocks a ThreadPool thread
```

This may deadlock in environments with a synchronization context and can cause ThreadPool starvation in ASP.NET Core under load. Prefer `await GetDataAsync()` end-to-end. `ConfigureAwait(false)` is useful in many library contexts to avoid capturing a context, but it does not make blocking safe.

##### ThreadPool starvation

Common causes include `.Result`, `.Wait()`, `GetAwaiter().GetResult()`, `Thread.Sleep`, synchronous blocking I/O, and excessive work queued through `Task.Run`.

Typical symptoms: high request latency, growing queues, low-to-moderate CPU despite requests hanging, and slow recovery. Investigate traces, thread-pool counters, blocked stacks, dependency latency, and load tests. Fix the blocking path rather than simply increasing thread counts.

#### Async internals: OS I/O, `SynchronizationContext`, and `ConfigureAwait`

<a id="async-internals"></a>

##### 1. How does the OS kernel handle I/O asynchronously?

A simplified flow:

1. Application requests a network or file operation.
2. The runtime invokes OS facilities appropriate for the platform and operation.
3. The kernel and/or device processes the operation.
4. Completion is reported through OS mechanisms.
5. .NET completes the associated asynchronous operation and schedules its continuation.

The exact mechanism differs by OS and I/O type. Windows uses completion mechanisms such as I/O Completion Ports for many socket and file scenarios. Linux commonly uses readiness notification mechanisms such as `epoll` for sockets; newer APIs such as `io_uring` support other I/O models. Do not state that all .NET I/O always uses one specific OS mechanism.

###### File I/O example

```csharp
public static async Task<string> ReadTextAsync(
    string path,
    CancellationToken cancellationToken)
{
    return await File.ReadAllTextAsync(path, cancellationToken);
}
```

The caller can await the operation without blocking its thread while the asynchronous operation is pending. Actual behavior can vary by OS, filesystem, device, and API; not every operation is guaranteed to be truly asynchronous at the hardware level.

##### 2. Task Scheduler and `SynchronizationContext`

- The **Task Scheduler** is relevant to scheduling `Task` work, especially tasks explicitly scheduled through APIs such as `Task.Run`.
- A **SynchronizationContext** is an abstraction that can direct continuations to a particular environment, such as a UI thread.
- WPF/WinForms commonly have a UI synchronization context. After `await`, code normally returns to that context so it can update UI controls.
- ASP.NET Core does not use the classic ASP.NET synchronization context, so context capture usually is not a concern there.

```csharp
Console.WriteLine($"Before: {Environment.CurrentManagedThreadId}");

await Task.Delay(100);

Console.WriteLine($"After: {Environment.CurrentManagedThreadId}");
```

The thread ID may change across the `await`. Correct asynchronous code should not depend on a particular thread ID unless the framework explicitly requires thread affinity.

##### 3. What does `ConfigureAwait(false)` do, and how can it help?

By default, an `await` may capture the current synchronization context (or a relevant scheduler) so the continuation can return to it. `ConfigureAwait(false)` tells that await not to require resuming on the captured context.

```csharp
public async Task<string> FetchAsync(HttpClient client)
{
    var content = await client
        .GetStringAsync("https://example.com")
        .ConfigureAwait(false);

    return content;
}
```

###### When it matters

- In reusable libraries that must work in UI and other environments, avoiding context capture can prevent unnecessary context switches.
- In WPF/WinForms, it can prevent a library continuation from needing the UI thread when the continuation does not use UI objects.
- In ASP.NET Core, there is normally no classic synchronization context to return to, so it usually provides little or no performance benefit.

###### Important correction

`ConfigureAwait(false)` does **not** mean “always switch to a ThreadPool thread,” and it does not itself make the underlying I/O faster. It means the continuation does not require the captured context. The continuation may run wherever the completion machinery schedules it.

Use it selectively in library code where context affinity is unnecessary. Do not use it in UI code before directly updating UI controls unless you explicitly marshal back to the UI thread.

#### 5. Async in the ASP.NET Core request pipeline

Typical flow:

1. Kestrel accepts and parses the HTTP request.
2. Middleware executes in order.
3. Routing, authentication/authorization, model binding, filters, and the endpoint execute as applicable.
4. Async I/O is awaited without holding a ThreadPool thread for the entire wait.
5. The response is written to the client.

Middleware itself is explained in [.NET and ASP.NET Core → Middleware](03-dotnet-and-aspnetcore.md#aspnetcore-middleware-filters-dotnet8-9-md).

Best practices:

- Use async I/O APIs end-to-end.
- Pass `CancellationToken` (often `HttpContext.RequestAborted`) to cancellable operations.
- Avoid `.Result`, `.Wait()`, synchronous I/O, and unnecessary `Task.Run`.
- Do not start untracked fire-and-forget work in a controller.
- Use `BackgroundService` for in-process hosted work, but remember that in-process work alone is not durable across restarts and is not a cluster-wide singleton.
- Move durable or lengthy work to a queue and worker.

Durable background jobs, distributed locks, and resilience patterns are covered in [System Design → Distributed async processing](08-system-design-and-distributed-systems.md#distributed-async-processing).

#### 6. MCQ and scenario exam

##### Multiple-choice questions

**Q1. What does `async` do by itself?**

A. Creates a new thread  
B. Enables asynchronous method composition and `await`  
C. Makes CPU work parallel  
D. Guarantees better performance  

**Answer: B.** It does not automatically create a thread or parallelize CPU work.

**Q2. What does `await` do when the task is incomplete?**

A. Always blocks the current thread  
B. Suspends the async method and arranges a continuation  
C. Always creates a new thread  
D. Cancels the operation  

**Answer: B.** The current thread can return to other work.

**Q3. What does `Task.FromResult(5)` do?**

A. Runs calculation 5 on another thread  
B. Returns an already-completed `Task<int>` containing 5  
C. Waits five seconds  
D. Starts a background job  

**Answer: B.**

**Q4. Which primitive can asynchronously wait for a concurrency slot?**

A. `lock`  
B. `Monitor.Wait`  
C. `SemaphoreSlim.WaitAsync`  
D. `Mutex.WaitOne`  

**Answer: C.**

**Q5. What does `Monitor.Pulse` guarantee?**

A. The waiter immediately owns the monitor  
B. One waiting thread becomes eligible to compete to reacquire the monitor  
C. All waiting threads enter the critical section  
D. The monitor is released permanently  

**Answer: B.**

**Q6. How can up to five operations enter a region concurrently within one process?**

A. `lock`  
B. `SemaphoreSlim(1, 1)`  
C. `SemaphoreSlim(5, 5)`  
D. `Monitor.PulseAll`  

**Answer: C**, provided the protected resource supports concurrent access.

**Q7. Why is `.Result` dangerous in a web request?**

A. It always causes a deadlock  
B. It blocks a thread and can cause starvation; deadlock is also possible in some contexts  
C. It always starts another process

**Answer: B.**

**Q8. Which option is suitable for durable background work across several application instances?**

A. `Task.Run` in a controller

**Answer: C.**

**Q9. What is the main reason for idempotent message processing?**

A. To make every message execute faster  
B. To safely handle retries and duplicate delivery

**Answer: B.**

##### Scenario questions

**Scenario 1: An API becomes slow under load, with many `.Result` calls and relatively low CPU.**

Expected answer: suspect sync-over-async and ThreadPool starvation. Trace blocking stacks and dependency latency; use async APIs end-to-end and remove blocking calls.

**Scenario 2: Five downstream requests may run concurrently, but no more than five.**

Expected answer: use a shared `SemaphoreSlim(5, 5)` in that process, `WaitAsync` with cancellation, and `Release` in `finally`. Use a distributed limiter or gateway if the limit must apply across all instances.

**Scenario 3: Consumers wait until a producer publishes data.**

Expected answer: use a condition protected by the same monitor, check it in a `while` loop, call `Monitor.Wait` while false, and update the condition before `Pulse`/`PulseAll`.

**Scenario 4: A scheduled job runs on two application replicas.**

Expected answer: prefer queue-based competing consumers or atomic database job claiming. Add idempotency, lease recovery, and retries. A local `lock` cannot coordinate replicas.

**Scenario 5: A controller performs a CPU-intensive report calculation that takes several seconds.**

Expected answer: use a durable queue and worker or separately scalable compute service, return `202 Accepted` with a job ID, and expose status/results. Use `Task.Run` only for bounded, measured cases where immediate response is necessary.

#### 7. Code review checklist

##### Async correctness
- [ ] No `.Result`, `.Wait()`, or `GetAwaiter().GetResult()` in request paths without a compelling, reviewed reason.
- [ ] No `async void` except event handlers.
- [ ] I/O uses true asynchronous APIs.
- [ ] No unnecessary `Task.Run` around I/O or trivial synchronous code.
- [ ] CPU-heavy work is measured and bounded or offloaded.
- [ ] Cancellation tokens are propagated where supported.
- [ ] Exceptions from background work are observed and handled.

##### Locking correctness
- [ ] Lock object is private and dedicated.
- [ ] Critical section is short; no `await` inside `lock`.
- [ ] Nested locks follow a consistent acquisition order.
- [ ] Shared state is actually protected by the same synchronization strategy.
- [ ] `Monitor.Wait` checks its condition in a `while` loop.
- [ ] `Pulse` versus `PulseAll` is chosen intentionally.
- [ ] `SemaphoreSlim.Release()` is in `finally`; configured capacity is correct.
- [ ] Mutex ownership, timeout, abandoned-mutex recovery, and release are handled correctly.

##### Distributed reliability
- [ ] Background jobs are durable if they must survive restarts.
- [ ] Duplicate delivery/retries are safe through idempotency.
- [ ] Retry policy is bounded and distinguishes transient from permanent failures.
- [ ] Queue depth, failures, latency, and dead-letter messages are observable.
- [ ] Any cluster-wide limit/lock is implemented with a distributed-aware mechanism.
- [ ] Long-running jobs have status, cancellation/timeout strategy, and recovery behavior.

#### 8. Interview summary

> “I use async/await to avoid blocking during I/O, not to disguise CPU work. I use `lock` for short in-process critical sections, `Monitor` for condition signaling, `Mutex` for suitable cross-process single-machine coordination, and `SemaphoreSlim` for async concurrency limits. For durable multi-instance background processing, I use queues or job stores, idempotent handlers, bounded retries, and observability.”
