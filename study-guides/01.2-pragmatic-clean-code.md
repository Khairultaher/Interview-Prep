# Chapter 1: Understanding clean code

Working code and clean code are not the same thing. Code is clean when it can be read, understood, tested, and changed without undue effort or risk. Those qualities decide how fast a team can deliver features, how confidently it can fix defects, and how well a system copes as its requirements grow. This chapter establishes the foundation for the rest of the book.

We will cover the following topics:

- Essential vocabulary
- Why clean code matters to projects and businesses
- The cost of poor code quality and technical debt
- The definition of done
- Professional responsibility for code quality
- The characteristics of readable and maintainable code
- A comparison of clean and poorly written code
- Clean code in the age of AI-assisted development

By the end of this chapter, you will be able to explain how code quality affects software delivery, distinguish working code from clean code, describe the definition of done and technical debt, and recognize the role of clean code practices when working with AI-assisted development.

## Why clean code matters

The effect of code quality is easiest to understand through the life of a project. Consider a software company beginning a new application for a client. The team starts with a clean slate, and the first version they deliver is small and quick to ship. The code is covered by tests, defects are rare, and both the company and the client are pleased. A project that starts well As development continues, simple classes become larger and relationships between components become more complicated. The team notices areas that should be refactored, but a release deadline is approaching. Because the application still works, the cleanup is postponed. The next version is delivered, although a few minor defects appear during the demo. By the following release, every change takes longer. Developers must trace unfamiliar dependencies, understand old decisions, and work around code that no longer fits the growing system. Test coverage becomes harder to maintain. The team again intends to refactor, but the pressure to deliver new features leaves little time for it. Eventually, a release arrives late with missing features and serious defects. The client expects the team to recover while also delivering the next set of features. Management compares current productivity with the unusually fast first release and assumes that the same pace should continue. The team responds by working longer hours and reducing the time spent on tests, reviews, and refactoring. This creates more defects and makes the next release even harder.

Complexity requires continuous maintenance A software project is similar to a construction site. At the beginning, the area is clear and the work can progress quickly. As construction continues, unused tools, packaging, and debris accumulate. If nobody removes them, workers must step around the clutter and every task becomes slower and less safe. A growing codebase accumulates its own form of clutter: duplicated logic, obsolete abstractions, inconsistent names, tightly coupled components, and tests that no longer reflect the current design. Complexity does not disappear by itself. Regular refactoring keeps it manageable and protects the team's ability to deliver new work.

## The cost of poor code quality

The project in the previous section did not fail because of one badly written method. It failed because a sequence of short-term decisions gradually removed the team's ability to work safely, while developers and management quietly disagreed about what it actually meant for the work to be done. Key idea: How fast a team builds the first version says little about its long-term delivery speed. As the codebase grows, part of the team's time must go into testing and refactoring to keep existing behavior intact.

Working code is not finished code A common mistake is to treat a feature as complete as soon as it produces the expected result. Working code and good code are not the same. Code is a form of communication: it records the current behavior of a system and explains that behavior to the people who will maintain it. That puts it in the same category as any other document written to be read. We would not call a user manual finished if it held all the right information in a confusing, repetitive, disorganized form. Code deserves the same standard. Every project should have its own definition of done: A shared set of criteria that determines when a piece of work is actually finished, not just functional. It prevents quality activities from being treated as optional work that can be removed whenever a deadline becomes uncomfortable. The exact criteria depend on the organization and the risk of the system, but a practical definition often includes the following: The implementation satisfies the agreed acceptance criteria. Relevant unit, integration, and end-to-end tests pass. The code has been reviewed by the required number of developers. The implementation follows the project's coding and design conventions. Required documentation has been updated. The change has been merged into the shared repository and can be built successfully. A task is finished only when the agreed conditions are met. This does not eliminate every defect, but it makes quality visible and protects the team from repeatedly trading long-term stability for short-term appearance.

## Understanding technical debt

Every team eventually faces a choice between the fast way and the right way. That trade-off has a name borrowed from finance: technical debt. Technical debt describes the future cost created when a team accepts a solution that is faster or easier now but more expensive to maintain later. The analogy with financial debt is useful because both provide an immediate benefit and both create an obligation.

Technical debt Financial debt The team accepts a lower-quality design or postpones necessary cleanup. A person or organization borrows money. Delivery becomes easier in the short term. Spending becomes easier in the short term. The code must later be refactored, retested, or redesigned. The borrowed amount must later be repaid. The longer the debt remains, the more areas depend on it and the harder repayment becomes. Interest increases the total cost of repayment over time.

*Table 1.3: Comparing technical debt with financial debt*

Technical debt can create false confidence about delivery speed. If a team repeatedly skips cleanup to meet dates, management and the client may assume that the resulting pace is sustainable. Future plans are then based on a speed that exists only because necessary work has been deferred. When the debt finally has to be repaid, the team appears to slow down even though it is addressing work that was always part of the real cost. This creates a deadline trap. The team is given more work because earlier features appeared to arrive quickly. The increased workload leaves less time for refactoring, which causes the debt to grow. Each release becomes harder, and the pressure to preserve the old delivery rate becomes stronger. The professional response is not to insist that every imperfection be fixed immediately. It is to make the compromise visible, understand its risk, and agree on when and how it will be addressed. Debt that is acknowledged and managed is very different from debt that quietly becomes the normal design of the system. LeBlanc's law: Later equals never. Work that isn't done now, when the context and motivation are fresh, tends to keep getting deprioritized until it's effectively abandoned. A large refactoring may not be practical immediately before a release, but once the need is identified, it should be recorded and scheduled. Unplanned debt tends to remain until it becomes a crisis.

## Professional responsibility and code quality

It is tempting to place all responsibility for poor quality on project management, especially when developers have asked for time to refactor. However, developers usually understand the technical consequences more clearly than anyone else involved in planning. That knowledge creates a responsibility to communicate risk in terms that non-technical stakeholders can use. Estimates should include the full definition of done. If an estimate accounts only for writing the first version of the code, management may promise a date that leaves no time for tests, review, documentation, or integration. Once that promise is made, quality work is incorrectly presented as additional scope rather than part of completing the feature. Effective communication focuses on outcomes instead of jargon. Saying that a module has technical debt may be meaningful to another developer, but a project manager may need to understand the practical effect: changes in this area take longer, defects are more likely, and each new feature increases the cost of future work. Step How to communicate it Describe the condition Identify the affected area and explain what makes changes difficult or risky. Explain the impact Connect the condition to delivery time, defect risk, support cost, or customer experience. Present options Offer realistic choices, such as a smaller feature scope, a scheduled refactoring task, or additional testing time. Record the decision Document the accepted trade-off so that the debt and its consequences remain visible.

## What makes code clean?

Clean code is written for people. The computer can execute code with poor names, inconsistent formatting, and unnecessary complexity. Developers, however, must read that code to fix defects, add behavior, review changes, and understand why the system works as it does. A deliberately informal measurement One humorous way to describe readability is to count the number of "WTF" moments a reader experiences per minute. The expression is intentionally informal, but the underlying observation is useful: frequent surprise and confusion are signals that the code is hiding its intent. Cleanliness indicator = confusing moments / minute The important part is that the measurement is based on reading, not writing. Developers typically spend more time understanding existing code than typing new code. Even when you are the only developer on a project, you may return to the code several months later without the context you had when you originally wrote it. Readability, therefore, is not a stylistic preference; it directly affects the time and effort required to understand and maintain the code in the future. Practical characteristics of clean code Characteristic What it looks like in practice Readable Names, layout, and structure help the reader follow the code without decoding it. Clear in intent The reason for each operation is clear from the code and is not complicated by vague names or surprising side effects. Simple The implementation avoids unnecessary abstraction, cleverness, and branching. Focused Methods and classes have a clear responsibility and operate at a consistent level of abstraction. Low in duplication A business rule has one authoritative implementation rather than several copies that can diverge. 

Characteristic What it looks like in practice Predictable Behavior matches the names, interfaces, and conventions used by the project. Testable The code's behavior can be verified in isolation, without relying on complex setup or hidden dependencies. Easy to change A developer can locate the relevant code, understand the effect of a change, and modify it with limited risk.

*Table 1.5: Practical characteristics of clean code*

There is no single visual form that all clean code must follow. Two implementations can use different structures and still be high quality. The goal is not to imitate one preferred style mechanically, but to make deliberate choices that reduce the reader's effort and preserve the system's ability to change. Writing clean code is a skill developed through practice. Experienced developers still revise names, split responsibilities, and discover better structures. Refactoring is therefore not evidence that the original developer failed; it is part of adapting the code as understanding improves.

## Comparing clean and poorly written code

The difference between working code and clean code becomes clearer with two implementations of the same behavior next to each other. Both versions of the method below authorize a user to perform an action, and both work. The first makes the reader decode abbreviated names, follow a manual loop, and work out what each block is for. The second one does not.

**Hard to read version:**

```csharp
public AuthorizationResult Auth(
    User u, UserAction ua)
{
    if (_usersRepository
        .GetById(u.Id) == null)
    {
        throw new
            NonExistentUserException(u);
    }
    var perm = _permissionsRepository
        .GetForUser(u.Id);
    if (u.IsSuperUser)
    {
        return AuthorizationResult
            .Authorized;
    }
    foreach (var p in perm)
    {
        if (p.Action == ua)
        {
            return AuthorizationResult
                .Authorized;
        }
    }
    return AuthorizationResult
        .NotAuthorized;
}
```

**Refactored version:**

```csharp
public AuthorizationResult Authorize(
    User user, UserAction action)
{
    if (!_usersRepository
        .DoesExist(user))
    {
        throw new
            NonExistentUserException(user);
    }
    if (user.IsSuperUser ||
        IsUserAuthorizedToPerform(
            action, user))
    {
        return AuthorizationResult
            .Authorized;
    }
    return AuthorizationResult
        .NotAuthorized;
}
private bool IsUserAuthorizedToPerform(
    UserAction action, User user)
{
    var userPermissions =
        _permissionsRepository
        .GetForUser(user.Id);
    return userPermissions.Any(
        permission =>
            permission.Action == action);
}
```

The first method eventually reveals its purpose, but several details slow the reader down. The name Auth does not say whether the method authenticates or authorizes. The parameters u and ua require mental translation. The permissions are retrieved before the super-user check, even though a super user does not need them. Furthermore, the loop asks a simple question— whether any permission matches the requested action—in a fairly verbose way. The refactored version makes the same decision while exposing its intent more directly. The name Authorize describes the operation, and the parameter names identify the information involved. The main method now reads as a sequence of business decisions: confirm that the user exists, then authorize a super user or a user with the required permission. ## Clean code in the age of AI-assisted development

AI coding assistants can generate, explain, and refactor code quickly. This raises a reasonable question: if an AI tool can improve a messy program, do developers still need to learn clean code? Yes, definitely. AI can accelerate the work, but a developer must still decide whether the result is correct, appropriate for the system, and maintainable. When given a hard-to-read method, an AI assistant may improve names, format the code consistently, and simplify redundant logic. It may also add comments to describe each block. Some of these changes are useful; others require judgment. For example, AI tools often add comments that restate what the code already says. Comments like these add nothing, and they go stale as soon as the code around them changes. A well-named method communicates the same intent and stays accurate. The assistant may also miss opportunities that depend on domain knowledge or project conventions. We must also be aware that another run with the same prompt may produce a different result. Generated code is therefore a proposal, not an approved implementation. AI can often help with A developer must still verify Suggesting clearer names and formatting Whether the names match the domain language used by the project Extracting small methods or simplifying local control flow Whether the new structure preserves behavior and fits the surrounding design Generating an initial set of unit tests Whether the tests cover important cases and assert the correct behavior Both versions may pass the same tests. What distinguishes clean code is not its output, but how easily a developer can verify, explain, and change it.

Large language models generate responses from patterns learned during training and from the context supplied in the prompt. Today, that context can be substantial—an entire codebase, relevant documentation, prior commits. But even with that much information available, AI tools still don't have the full picture: the history behind a design decision, the business rules that were never written down, or the reasoning a teammate had in mind but never documented. They can also make mistakes or unintentionally alter behavior while attempting a refactoring. AI tools are especially useful for small, distinct tasks, and they can handle larger ones too, provided they're given enough information about the system to work with. They can help draft tests, explain an unfamiliar API, suggest names, propose a local refactoring, or take a first pass at untangling a messier piece of code. None of that removes the need to understand clean code yourself. Writing sloppy code on the assumption that an AI tool will clean it up later just moves the risk downstream—the tool may miss a business rule that was never written down, or refactor the code in a way that quietly changes its behavior. Clean code remains your responsibility, not a problem to outsource. The tools and their capabilities will continue to change. The durable skill is the ability to recognize clear design, identify defects in a proposed solution, and improve code deliberately. AI can reduce the effort required for some steps, but it cannot remove the need for technical judgment. Review rule: Treat AI-generated code as unreviewed code. Read it, test it, compare its behavior with the original implementation, and evaluate it against the same standards you would apply to a colleague's contribution.

## Why meaningful names matter

Programming involves naming things all the time: variables, methods, parameters, classes, and files. Much of what we read in code consists of names that somebody chose. And remember, code gets read more often than it gets written. That's why readability is so crucial. The listing below is highlighted to show every name its author chose. All of those things could have been named differently, and different names would change how easy the code is to read. That is why good names are the foundation of readable code. They deserve real thought before anything gets settled. It is also why we devote this entire chapter to naming. Now let's compare two implementations of the same filtering operation. Read the first version and try to understand what it does as quickly as possible. A working implementation with weak names:

```csharp
public List<string> Filter(int l, List<string> items)
{
    var res = new List<string>();
    foreach (var i in items)
    {
        if (i.Length < l)
        {
            res.Add(i);
        }
    }
    return res;
}
```

This version works, but it is not obvious at first glance what this code does. Renaming alone exposes the intent of the method without changing its behavior: The same implementation with meaningful names:

```csharp
public List<string> GetWordsShorterThan(int length, List<string> words)
{
    var result = new List<string>();
    foreach (var word in words)
    {
        if (word.Length < length)
        {
            result.Add(word);
        }
    }
    return result;
}
```

How much time did you need to read and understand the method now? Reading the signature alone is enough to know what it does: given a list of strings, it returns only the words shorter than a given length. Even with the signature hidden, the body would be easy to follow. It iterates over a collection of words and adds each word shorter than the given length to the result. Finding good names takes effort at every level of experience. The payoff is code that can be picked up and understood a year later. Time spent thinking about names is repaid every time that code is read.

## Naming fundamentals

We will now explore the fundamental rules of good naming. Most of them hold regardless of the programming language. Naming variables, parameters, and types The first rule is to match the grammatical form of a name to the kind of thing it represents.

Let's start with variables, parameters, and fields. With a few exceptions covered later, they should be named with nouns: person, file, or player. Modifiers can be added when a bare noun is not specific enough, as in textFile, databaseConnection, or userToBeUpdated, but the core of the name stays a noun. Types follow the same rule as variables: they should be named with nouns, such as Point, List, PeopleDataReader, or UserAuthorizer. Here, "type" means any user-defined type, including classes, structs, enums, and interfaces. Most style conventions name types with an initial capital letter and name variables and parameters with a lowercase one. Two of those examples end in -er. That suffix is conventional for types whose job is to do something rather than to carry data, and it states that job directly in the name. Naming methods The names of methods should be built around verbs. A method does something, and that action belongs in the name. Examples of typical method names could be Read, Transform, or Load. Longer names work the same way, with a verb at the core: DecreaseBalance, CountNegativeNumbers, RemoveExcessSpaces.

A special case is a word that works as both a noun and a verb, such as request. When the context makes it clear whether the name refers to a method or to a value, this is rarely a problem. When it does not, the fix is to make the name more specific: SendRequest for the method, request for the variable. Naming Boolean values and methods as questions Booleans are a special case, both as variables and as methods that return them. They should not be named with nouns or verbs. A Boolean name should read as a question that can be answered with yes or no: isShorterThanFiveLetters, hasBeenSavedSuccessfully, canBeDeleted.

Boolean names should also be positive. isEnabled is a good name; isNotEnabled is not. Negation belongs in the code that reads the value, not in the name, and the logical negation operator is there for that.

```csharp
if (user.IsEnabled) { ... }
if (file.HasBeenSavedSuccessfully) { ... }
if (account.CanBeDeleted) { ... }
// Prefer this:
if (!user.IsEnabled) { ... }
// Over this:
if (user.IsNotEnabled) { ... }
```

No style is better than the others in itself. What matters is that code looks familiar to people working in that language. Moving from C# to Python means moving to Python's conventions, not carrying C# habits along. Conventions matter for two reasons. The first is consistency. When all developers follow the same convention, code looks the same no matter who wrote it, and consistent code is easier to read and follow. The second reason is that conventional names carry information beyond what they name. In C#, a field whose name starts with an underscore is private, and that can be read from the name alone, without looking up the declaration. This makes reading code faster. It also makes the code easier to maintain. Teams may add local rules on top of language conventions. Such rules should be written down somewhere the team actually reads, and they should extend the language conventions rather than contradict them. One common example is a rule that unit tests name the object being tested cut, for "class under test". Across a few thousand tests, the subject is always called the same thing, so you know what you're looking at before you read the rest. Writing a convention down is not the same as having it followed. Tooling closes that gap. Formatters apply layout rules on save, so nobody argues about them in review. Static analyzers check naming rules and flag violations while the code is being written. Both can run in the build pipeline, which turns the convention into something the build enforces rather than something a reviewer has to remember. 

## Why developers choose poor names

Nobody picks bad names just to annoy other programmers. Hopefully. The problem is that a name looks fine at the moment we write it, because we know things the future reader will not. After a few hours on the same method, we know the problem, the data, and what every temporary variable holds. None of that is in the code, and none of it survives a few weeks away. Plenty of code that looked clean when it was written turns out to be unreadable a month later, to the person who wrote it. The curse of knowledge This effect is known as the curse of knowledge. Once we know something, it becomes hard to imagine not knowing it. Explanations that feel complete to us turn out to skip the steps we stopped noticing a long time ago, and we misjudge how much of what we said actually landed. Code is where this shows up constantly. A name that reads clearly to its author reads that way because the author knows what sits behind it. Someone opening the file for the first time does not. And neither, in a sense, do we a few months later, once the context has faded. To counter this bias, read your own code as if you did not write it. It helps to have a specific person in mind: a junior developer, or someone who joined the team last week and does not know the codebase yet. What would they ask about? Would they know what a given variable holds, or what a method call does, without asking anyone? Using the rubber duck method Another option is the rubber duck method. Its name needs some explanation. It happens often that we get stuck on a piece of code and call a colleague over to discuss it. Then, halfway through explaining the problem, the solution appears on its own. The colleague has not said a word yet. It turns out that explaining the problem out loud was the whole point, and the listener was optional. Which means we can save a colleague's time and explain the code to a rubber duck, or to anything else that will sit still and listen. The same technique works for readability. Explain the code to the duck, line by line. If the walkthrough needs constant asides—this variable is actually the active customer, this method is called Clear but it only trims trailing whitespace—the code is not speaking for itself, and those asides point to the exact names that need work. If the code can be read as it stands, it is in good shape. Real programmers are better than rubber ducks. Ask the most junior person on the team to read the code and listen to what they ask about. Every question marks a place where the reader needed context that the code did not give them.

Try not to take those questions personally. It is uncomfortable to hear that somebody cannot follow our code, and the easy way out is to decide the reader is not good enough. It is worth resisting that, because this feedback is the fastest way to get better. When somebody who joined last week can read our code without asking a single question, that is as good as it gets.

## Renaming and the Boy Scout rule

Good names often arrive gradually. The first one we pick reflects what we understood about the design at that moment, and as the design becomes clearer, a better name tends to suggest itself. So when a name refuses to come, there is no point in staring at the screen. Give the class a temporary name, write the code, refactor it, and come back to the name once the class does exactly what we want. At that point the right name is usually waiting for us. Renaming is a normal refactoring step, not an admission that the first attempt was a failure. There is a rule worth knowing here, and it comes from scouting rather than from programming. Scouts are told to leave the campsite cleaner than they found it, whether or not they were the ones who made the mess. Applied to software, the Boy Scout rule says to leave the code a little better than we found it. With naming, that can mean fixing one vague variable, replacing an abbreviation, or renaming a class whose responsibility has become clearer since it was written. Small improvements like these are easier to keep up than a large cleanup that may never get scheduled. Modern IDEs rename symbols safely across a whole project, so most of the mechanical cost is gone. Renaming public APIs requires more care Renaming is straightforward inside a codebase you control, but a public API or shared library creates compatibility obligations. Consider Console.WriteLine, one of the most familiar methods in the .NET API for C# developers. It writes a line of text to the console and is commonly encountered in introductory and everyday C# code. Boy Scout rule: Always leave the code you are working on a little bit better than you found it. A large refactoring is easy to postpone, and the longer it waits, the bigger it gets. The Boy Scout rule avoids that trap. Instead of demanding perfect code, it asks for a small cleanup in whatever class or method we happen to be working on. Those small changes add up.

> **Note**

Now imagine its authors decided the name could be better and renamed it. Every one of those programs would stop compiling. The fix would be mechanical, but somebody would have to make it, in every codebase, before anything could be built again. That is why public names deserve more thought than internal ones. An internal name can be changed in a second. A public one is a commitment, and changing it later means deprecation, migration guidance, and usually a new major version.

## When naming is hard, inspect the design

Sometimes the difficulty is not that you have failed to discover a clever name. The construct itself may be doing too much. A precise name becomes awkward because it has to describe several responsibilities at once. In that situation, the naming problem is a design signal. Consider a method named ActivateAccountAndSendNotification. The word And is a warning that two operations have been combined. Splitting the work produces names that are shorter, clearer, and more reusable:

```csharp
ActivateAccount();
SendNotification();
```

Conditional behavior can reveal the same issue. Consider a method called EmptyShoppingCartIfSessionInactive. Instead of hiding the condition inside a long name, separate the question from the action:

```csharp
if (!IsSessionActive())
{
    EmptyShoppingCart();
}
```

Class names can reveal blurred responsibilities as well. Consider a class called EmailManager. What is its job exactly? Sending emails? Or maybe creating accounts in some email service? As it turns out, it does both things:

```csharp
class EmailManager
{
    public void Send() { ... }
    public void Create() { ... }
}
```

Splitting the responsibilities allows more meaningful names:

```csharp
class EmailSender
{
    public void Send() { ... }
}
class AccountCreator
{
    public void Create() { ... }
}
```

Notice that the names became easy once EmailManager was split. When the best name we can find for a class is Manager, Handler, or any other vague word, the difficulty is usually not in our vocabulary. Such a name is often a sign that the class itself is vague, and that it does several unrelated things at once. When a name refuses to get more specific, we should take a close look at the class and consider splitting it into smaller, more focused types.

## Writing expressive names

A good name should make the programmer's intention visible without depending on explanatory comments. Consider a method called Clear that removes whitespace only from the end of a string. The implementation may be correct, but the name is too broad:

```csharp
// Removes whitespace from the end of input.
string Clear(string input) { ... }
```

A better name carries the explanation itself:

```csharp
string RemoveTrailingWhitespaces(string input) { ... }
// Or, using familiar string terminology:
string TrimTrailingWhitespaces(string input) { ... }
```

The same principle applies to types. A class called FileWriter should write to files, and that is all it should offer. A public method that checks whether a file exists would be out of place. Privately, of course, the class can do whatever it needs, and checking that a file exists before writing to it is perfectly reasonable. The difference is that this check is part of how the class does its job, not part of what it offers to the outside. 

A good name shows what the programmer intended, and it does that precisely. Sometimes the intention comes through, but only roughly. Take a GameObject class with a method called Transform that changes the object's position. Movement is a kind of transformation, so the name is not wrong. It is just wider than it needs to be, and a reader has to open the method to find out which kind of transformation this is. Renaming this method to Move would make what it does obvious from the start.

## Choosing an appropriate name length

Short names reduce reading effort only when they preserve meaning. If the choice is between a long, clear name and a short, unclear one, clarity wins. Once the meaning is secure, remove words that add no information.

**For example, a filtered collection might evolve through several possible names:**

```csharp
var onlyPeopleOlderThan18Years = ...;
var peopleOlderThan18Years = ...;
var adultPeople = ...;
var adults = ...;
```

If the domain clearly defines an adult as a person older than 18, adults is both shorter and more expressive. If that assumption does not hold in the application, the longer version may be safer. The surrounding domain decides how much information a name must carry. Some names are necessarily longer because the distinction matters. GetSingleLetterStrings is more precise than GetShortStrings when the method must return only strings of length one. Shortening the name would make the contract less clear. Still, if the only name that fits is a very long one, that usually says something about the code rather than the name. A method may be doing too much, or a variable may be holding something too complicated. Take a method whose only reasonable name is FinalizeOrderAndStartPaymentProcess. The name is not the problem. The method is, and the fix is to split it into FinalizeOrder and StartPaymentProcess. As a rule, a name that needs "and", "or", or "if" is worth treating as a refactoring signal. Very long names can also reveal misplaced responsibilities. Suppose Person contains a method called IsHomeAddressValid:

```csharp
class Person
{
    public Address HomeAddress;
    public bool IsHomeAddressValid() {...}
}
```

The name is long partly because Person is carrying a responsibility that belongs to Address. Moving the validation to Address produces a better code:

```csharp
class Person
{
    public Address HomeAddress;
}
class Address
{
    public bool IsValid() { ... }
}
if (person.HomeAddress.IsValid())
{
    ...
}
```

The overall expression is not dramatically shorter, but each part is easier to read and the responsibility now lives with the object that owns the relevant data. Long test names are often useful Tests are a special case. A useful test name often needs to describe both the scenario and the expected result. When a test fails, its name becomes part of the diagnostic output, so extra length can be justified if it communicates the failure precisely.

```csharp
Play_ShallReturnVictory_IfTheUserGuessesTheNumberOnTheFirstTry
Play_ShallReturnLoss_IfTheUserNeverGuessesTheNumber
Play_ShallReturnLoss_IfTheUserGuessesTheNumberOnTheFourthTry
```

It helps to agree on one naming pattern for tests and stick to it. There is no need to stretch a name beyond what the scenario requires, but shortening it should never cost the information a developer needs when the test fails. 

## Following the principle of least surprise

The principle of least surprise says that code should behave the way a reasonable reader expects it to behave. In other words, the readers of the code should never be surprised by what they see. In naming, that means methods and classes should do what their names say, do that thing consistently, and avoid hidden behavior that contradicts the promise made by the identifier. Following this principle has a practical effect: code can be read and understood without opening the implementation of every method it calls. The names are enough to know what happens. Read the following method and try to understand what it does.

```csharp
public void Run()
{
    var stringBuilder = new StringBuilder();
    var ticketDocuments = _documentsReader.Read(_ticketsFolder);
    foreach (var document in ticketDocuments)
    {
        var lines = ProcessDocument(document);
        stringBuilder.AppendLine(
            string.Join(Environment.NewLine, lines));
    }
    _fileWriter.Write(
        stringBuilder.ToString(),
        _ticketsFolder,
        "aggregatedTickets.txt");
}
```

In the example, reading the method top to bottom tells the whole story: ticket documents are read, then processed, then the aggregated result is written. If some step needs a closer look, the reader can open it. The point is that they choose to, instead of having to. Now imagine that Read secretly deletes files, or Write silently modifies unrelated state. In that case, high-level reading becomes unreliable. The names are useful only when the implementation honors them. Following the principle of least surprise boils down to this: the methods or classes should do what their names say. They should do only this thing, they should do it well, and they should not do anything else.

A method called SaveUser provides a simple counterexample. If it validates the user and saves only when the validation succeeds, the name overstates what the method guarantees:

```csharp
public void SaveUser(User user)
{
    if (user.Email is not null)
    {
        _usersRepository.Save(user);
    }
}
```

Renaming it to SaveUserIfValid would be more honest, but the method would still combine two responsibilities. A cleaner design separates the question from the action:

```csharp
if (IsValid(user))
{
    Save(user);
}
public void Save(User user)
{
    _usersRepository.Save(user);
}
public bool IsValid(User user)
{
    return user.Email is not null;
}
```

Variables should follow the same principle. If a value stores the first even number, firstNumber is misleading; firstEvenNumber communicates the actual meaning. Another common example is a parameter called list that actually holds an array. The name suggests one concrete collection type while the code provides another. That mismatch sends the reader in the wrong direction and may become even more misleading as the implementation changes.

## Maintaining semantic correctness

We have already talked about the principle of least surprise, which is about the code as a whole behaving the way a reader expects. Semantic correctness is the same idea narrowed down to a  single name. It means the meaning a name carries matches what the code behind it actually does. The reason this deserves its own treatment is that certain words carry stronger meaning than others, and they carry it across the entire industry. A Get returns something. A Set changes something. A method starting with Is, Has, or Can answers a yes-or-no question and leaves everything as it found it. Nobody wrote these rules down, and no compiler enforces them, but every developer reads code with them in mind. Reach for one of these words and the promise comes along with it, whether we meant to make it or not. That is what makes breaking them expensive. A GetName method that quietly loads data into a field will be called in a loop by someone who assumed it was cheap. An IsEnabled property that flips a flag while answering will produce a bug that takes hours to find, because the line that caused it looks like a question rather than an instruction. The reader had no reason to check. The name told them there was nothing to check. The fix is not complicated. If a method does more than its name promises, either the name changes or the extra work moves elsewhere. A Get that has to load something can be renamed to Load or Fetch. A property that computes something expensive can become a method, since a method call signals work in a way a property does not. These expectations are conventions rather than compiler-enforced rules, but following them consistently makes names more trustworthy to readers.

## Avoiding ambiguity and inconsistency

A name can be clear on its own and still become confusing when the surrounding code uses ambiguous or inconsistent vocabulary. The following sections look at the most common forms of that problem. Avoiding homonyms Homonyms are words with many meanings. For example, "current" may refer to the present time or the flow of electricity or liquid. "Die" can mean "to stop living", or refer to an item we roll while playing games. Ambiguous words are not automatically bad; context can make them perfectly clear. In a board game, die naturally refers to the object being rolled. In other domains, however, words such as "current" can be ambiguous. It could mean the currently selected device or electrical current. When more than one interpretation is plausible, add enough context to remove the ambiguity:

currentlyChosenDevice and electricCurrent are longer than current, but they prevent different readers from assigning different meanings to the same name.

Using synonyms consistently Synonyms are words with the same or nearly the same meaning, such as quick and fast, or big and large. Consider a repository class that uses synonyms in method names:

```csharp
public class PersonalDataRepository
{
    public DateTime GetDateOfBirth(int personId);
    public string FetchCityOfBirth(int personId);
    public string RetrieveSocialSecurityNumber(int personId);
}
```

This class looks chaotic, and the reason is that the same operation goes by three names: Get, Fetch, and Retrieve. All three mean retrieving data. Nothing distinguishes them, so a reader has to check each method to confirm they do the same kind of thing. This happens easily when several developers work on the same code over time. The fix is to pick one word and use it everywhere. Get is the shortest and the most common, so it is the natural choice here.

```csharp
public class PersonalDataRepository
{
    public DateTime GetDateOfBirth(int personId);
    public string GetCityOfBirth(int personId);
    public string GetSocialSecurityNumber(int personId);
}
```

Now, this code looks much better and it is easier to read. We see right away that those are related operations that read data for a person with the given ID. Different words are appropriate when they represent truly different concepts. If Add combines two objects of the same type but Insert places a new element into an existing collection, the difference in vocabulary helps readers predict the different semantics. 

Matching singular and plural forms Names should reflect whether a value represents one item or a collection. A variable called inactiveUserId suggests one identifier; if it holds several values, the name should make that plurality visible unless the type itself represents one composite identifier.

```csharp
// Misleading: the name implies one ID.
var inactiveUserId = new[] { 4, 12, 16 };
// Clear: the value is a collection.
var inactiveUserIds = new[] { 4, 12, 16 };
// Also clear if CompositeId is a single domain value.
var inactiveUserId = new CompositeId(4, 12, 16);
```

Method names and parameter names should change when the cardinality changes. A refactoring from one vector to many vectors should update both identifiers:

```csharp
Vector NormalizeVector(Vector vector) { ... }
List<Vector> NormalizeVectors(List<Vector> vectors) { ... }
```

Plurality mistakes often appear after refactoring because a type changes while the original name is left behind. Updating the identifier at the same time keeps the code semantically correct. Using natural language in code Readable code often resembles ordinary language. Small words such as than, by, to, and with can make an expression much easier to parse because they turn an identifier into a phrase a reader would naturally say.

```csharp
if (vector.IsShorter(otherVector)) { ... }
if (vector.IsShorterThan(otherVector)) { ... }
var newPoint = point.Transform(1, 2);
var newPoint = point.MoveBy(1, 2);
```

The second version in each pair adds or changes only a small amount of text, but the intent is clearer because the call reads more like a sentence.

Choosing a language for identifiers Many international software projects use English identifiers because programming ecosystems, APIs, documentation, and developer communities commonly use English. Some organizations or regulated projects may require another language. Whatever the project chooses, consistency matters more than mixing languages unpredictably within the same codebase. If a project uses a language other than English for domain identifiers, document that choice and apply it consistently. Avoid switching between languages for equivalent concepts, because readers must then translate both the program logic and the vocabulary at the same time. Avoiding meaningless words Words such as Manager, Handler, Data, and Info are sometimes useful, but they often appear when the author has not identified a more precise responsibility. A class called EmailManager could send messages, manage accounts, validate addresses, or do all three. The word Manager tells the reader almost nothing.

```csharp
class EmailManager { ... }
class EmailHandler { ... }
```

The same goes for the three variables below:

```csharp
var order = ...;
var orderData = ...;
var orderInfo = ...;
```

Data and Info add nothing to order, so a reader looking at all three has no way to tell what actually distinguishes them. If they hold different things, the names should say what those things are. If they hold the same thing, two of them should not exist. The fix is to replace the generic word with whatever the domain actually calls the thing. If those two classes have distinct responsibilities, EmailSender and AccountCreator say what they are. If the three variables hold different parts of an order, itemsInOrder, orderingCustomer, and orderStatus tell the reader what each one contains before they read a single line further. Avoiding overly specific names Names can fail by being too vague, but they can also be too specific. A name should describe the abstraction that callers care about, not an implementation detail that may change later. 

Consider an interface containing a method for reading people records. Naming its method ReadFromSqlDatabase is not the right choice. This name is too specific because it leaks an implementation detail into the abstraction. Callers do not care whether the data comes from a SQL database, a file, or a web service. They need to know that the method returns Person objects. If the storage moves elsewhere later, a name that mentions SQL becomes wrong, and every caller reads a lie until someone renames it. The fix is to make the method name generic: Read. The classes implementing IPeopleReader can then be specific, since their names describe a concrete source rather than an abstraction.

```csharp
public interface IPeopleReader
{
    List<Person> Read();
}
public class PeopleFromSqlDatabaseReader : IPeopleReader
{
    public List<Person> Read() { ... }
}
public class PeopleFromExcelFileReader : IPeopleReader
{
    public List<Person> Read() { ... }
}
```

Avoiding Hungarian notation and type-based names Another way of packing implementation details into a name is Hungarian notation, which encodes the type in the identifier itself and produces names such as intAge or strLastName. The convention made sense in environments with limited tooling, where knowing the type of a variable meant hunting for its declaration. Modern IDEs display that information on hover, so the prefix buys nothing and costs a few characters on every use. It also carries the same risk as ReadFromSqlDatabase. A variable called intCount that has to start holding larger values becomes a long, and its name is now a lie. A variable called numbersList becomes misleading if its type changes to an array. Naming it numbers preserves the meaning across such implementation changes.

```csharp
// Avoid type prefixes
int intAge;
string strLastName;
```

```csharp
List<int> numbersList;
// Prefer domain names
int age;
string lastName;
List<int> numbers;
```

Avoiding confusingly similar names Two names that differ by only one letter or a small grammatical change force readers to remember distinctions that the identifiers themselves do not explain. Classes called UserDataStorage and UsersDataStorage, for example, look as though they should mean the same thing. If they represent duplicate behavior, consolidate them; if they represent different behavior, rename them to expose the difference. The same problem occurs with variables such as ItemsCount and CountOfItems in the same scope, or parameters distinguished only by numbers. Names such as source and target communicate a relationship that parameter1 and parameter2 cannot.

## Using abbreviations carefully

Abbreviations save characters but often increase reading time. addr is less immediate than address, and prod could mean product or production. Source-code size is not a meaningful reason to shorten identifiers; compilers do not need developers to sacrifice readability to save a few characters in source text.

```csharp
var addr = ...;       // Requires interpretation.
var address = ...;    // Immediate meaning.
var prod = ...;       // Product or production?
var product = ...;    // Clear in this context.
```

The same caution applies inside lambda expressions. A single-letter parameter may be common in mathematical code, but a descriptive identifier can make the expression easier to read and easier to search across a codebase:

```csharp
(a) => $"{a.Number} {a.Street} street."
    (address) => $"{address.Number} {address.Street} street."
```

There is one more argument against abbreviations, especially the single-letter ones: they make code hard to search. Searching for "address" returns the handful of places that word appears. 

Searching for "a" returns every word that contains the letter, and finding the parameter among them takes forever. However, some abbreviations are so widely used that expanding them would look odd rather than helpful. ex for an exception in a catch block, i for a loop index, and id for an identifier are read instantly by every developer, and nobody has to stop and work them out. ## Using context effectively

A name does not exist in isolation. The containing type, namespace, project, and call site already provide information, and repeating all of that context makes names longer without making them clearer. Consider a variable called state. Its name gives no context at all. Is it the state of a process, or one of the United States? There is no way to tell without reading the surrounding code, and by then the name has already cost the reader time. A name that shows the purpose right away avoids that. Renaming it to addressState makes clear that this is part of an address and will hold values like Texas or Ohio. Renaming the variable is one way to make its meaning clear. Another is to give it a type that supplies the context. Instead of addressNumber, addressCountry, and addressState sitting next to each other, the three can be bundled into a struct called Address, and the prefixes can go. Address.State says everything addressState said, without saying "address" twice. The type already carries that part, so a State field inside it can only mean California or Florida, not the state of a process.

```csharp
struct Address
{
    public string Number;
    public string State;
    public string Country;
}
```

The same principle applies to methods. A TextFileWriter does not need a method called WriteToTextFile if callers already know the receiver is a text-file writer. Write is enough:

```csharp
class TextFileWriter
{
    public void Write(string content) { ... }
}
```

Project context can remove repetition too. In a project dedicated entirely to an email service, prefixes such as EmailSearchEngine, EmailNotifier, EmailSender, and EmailValidator may make searching noisier without adding meaning. SearchEngine, Notifier, Sender, and Validator can be sufficient if no other domain objects create ambiguity.

## A practical naming review workflow

When reviewing names in your own code, use a repeatable sequence rather than searching randomly for "better words." Read the signature before the implementation. Ask what you expect the construct to do based only on its name. Check whether the name matches the construct: nouns for things, verbs for actions, and question-like names for Boolean answers. Look for ambiguity, inconsistent synonyms, abbreviations, type information, and words that add no domain meaning. Check singular and plural forms and verify that the name still matches the current type after refactoring. Use the surrounding class, namespace, and project context to remove repeated information without creating ambiguity. If the only accurate name is extremely long or contains several responsibilities, inspect the design before forcing a shorter name. ## Method fundamentals

Let's start with the basics. A function is a named block of code that performs a specific task. Functions make code reusable, and they are the basic building block of a program. A function that belongs to a type is called a method. Some languages allow functions to be defined outside any type. C# does not, so every function in C# is a method. That's why this book uses both terms interchangeably. A method can return a value or be void, meaning it doesn't return anything. It can also receive inputs. The names in the declaration are parameters; the concrete values supplied at the call site are arguments. In the following example, a and b are parameters, while 5 and 3 are arguments:

```csharp
var sum = Add(5, 3);
int Add(int a, int b) => a + b;
```

> **Note**
Naming methods Method names should be built around a verb, because methods perform actions. Names like Add, Search, Load, and Modify clearly state what will happen. Methods returning a Boolean are the exception: their names read as yes-or-no questions, such as IsLoaded, CanBeDisabled, or HasBeenModified.

Delegates and lambda expressions In many programming languages, methods can also be treated as values. In C#, delegates provide a type-safe way to store or pass callable behavior. The built-in Func delegates describe methods that return a value, while Action describes methods that return void. For example, the following variable can be assigned any method that accepts two integers and returns a Boolean:

```csharp
Func<int, int, bool> someFunction = IsDivisibleBy;
bool IsDivisibleBy(int number, int divisor) => number % divisor == 0;
```

Lambda expressions provide a concise way to define anonymous functions, which is particularly useful when the behavior is needed only at one call site. The following code uses a lambda predicate to keep only numbers greater than 10:

```csharp
var numbers = new int[] { 1, 7, 19, 4, 20, 0 };
var largeNumbers = numbers.Where(number => number > 10);
```

The parameter appears to the left of the => operator, and the expression that calculates the result appears to the right. Because this lambda answers whether a value satisfies a condition, it acts as a predicate.

## Designing clear method signatures

A method signature is the contract visible to its callers. It includes the method name, return type, parameters, and modifiers. A good signature should make the method's requirements and result clear without requiring the caller to read the implementation. We've already seen how important good method names are. But a method name is not read in isolation. At the call site, it appears together with the arguments, so the complete call should communicate its intent clearly. 

Consider this call:

```csharp
_fileWriter.Save("someString")
```

What does it do? It could save the string to a file, or it could write to a file named someString. The name and the argument together do not settle it. Both cases have better names available. If the string is the content, AppendText says so when existing content is kept.

```csharp
_fileWriter.AppendText("someString")
```

If the original content is not kept, ReplaceContentWith is a better name.

```csharp
_fileWriter.ReplaceContentWith("someString")
```

If the string parameter represents a file name, WriteTo makes that clear.

```csharp
_fileWriter.WriteTo("someString")
```

In each case the call reads as a sentence, and the ambiguity is gone. A good signature carries information even without the name. Consider this one:

```csharp
List<T> ???(List<T>, Func<T, bool>)
```

It takes a list and a predicate over the same type as items in this list, and returns a list of the same type. That is enough to make a reasonable guess: it likely filters the input using the predicate. The guess could be wrong, but the fact that a guess is possible at all is the point. Types carry meaning, and a good name adds to it rather than doing all the work alone. Choosing the right number of parameters How easy a method is to read and to call depends largely on how many parameters it takes. A method with none is the easiest case, since there is nothing for the caller to supply and nothing to get wrong. One parameter is still simple, though it already brings a value the caller can get wrong:

```csharp
var firstNumber = numbers.First(); // impossible to call with an invalid argument
var itemAtIndexZero = numbers.ElementAt(0); // a valid argument is provided
here...
var invalidItem = numbers.ElementAt(-1); // ...but not here
```

As parameter lists grow, callers must remember more information and tests must account for more combinations. A connection method with many separate configuration values illustrates the problem:

```csharp
public void ConnectToDatabase(
    DbType type,
    string databaseName,
    string serverName,
    Cluster serverCluster,
    string userName,
    string password,
    int timeout)
{
    // ...
}
```

A long list does not automatically mean the method is wrong, but it should prompt a design question: do these values expose several responsibilities or groups of data that should be modeled more clearly? Splitting methods to reduce parameters One reason a method accumulates parameters is that it performs more than one task. Consider a SaveGame method that receives game data, a file name, and a file extension. It both constructs the final file name and writes the game data:

```csharp
var finalFileName = BuildFileName(
    saveFileNameWithoutExtension,
    saveFileExtension);
SaveGame(gameData, finalFileName);
```

Separating the file-name construction from the saving gives each method a clearer purpose.

BuildFileName can also be called from anywhere else that needs a file name built the same way, for example a method that reads the file back.

```csharp
public string BuildFileName(
    string fileNameWithoutExtension,
    string extension)
{
    return fileNameWithoutExtension + "." + extension;
}
```

The parameter reduction is a consequence of separating responsibilities rather than the goal by itself. Grouping related parameters Another option to reduce the number of parameters is to group values that naturally belong together. Let's consider a constructor for a Circle type:

```csharp
public Circle(float x, float y, float radius) {...}
```

It takes three parameters. The first two are the coordinates of the circle's center, and the third is its radius. The first two belong together, so they can be aggregated into a Point data structure. That leaves a constructor with two parameters instead of three, and the grouping matches how a circle is actually described: a center and a radius. The Point type is also reusable, and anywhere else in the application that currently passes a loose pair of coordinates can use it.

```csharp
public struct Circle
{
    public Point Center { get; }
    public float Radius { get; }
    public Circle(Point center, float radius)
    {
        Center = center;
        Radius = radius;
    }
}
public record Point(float X, float Y);
```

Let's consider another example. Here is a method that establishes a database connection:

```csharp
public IDatabaseConnection ConnectToDatabase(
    string userName,
    string password,
    string databaseName,
    string databaseServerName,
    string databaseClusterName)
```

It takes five parameters, which is enough to be a problem on its own. The first step is to look for parameters that belong together. Three of them do, and their names are already similar, which is a hint that they describe one thing rather than three. They can be grouped into a DatabaseIdentity type.

```csharp
public struct DatabaseIdentity
{
    public string DatabaseName;
    public string DatabaseServerName;
    public string DatabaseClusterName;
}
```

This is better, but there is one more grouping available. userName and password are both user credentials. Wrapping them in a dedicated type leaves the method with two parameters, each describing one thing.

```csharp
public struct UserCredentials
{
    public string UserName;
    public string Password;
}
```

Now we can use those new types to make the signature of the ConnectToDatabase method much cleaner:

```csharp
IDatabaseConnection ConnectToDatabase(
    UserCredentials userCredentials,
    DatabaseIdentity databaseIdentity);
```

This is useful only when the grouped values form a meaningful concept. A wrapper created only to reduce the parameter count hides the problem instead of fixing it. Using Boolean parameters carefully As noted earlier, methods often take too many parameters because they do too many things. Boolean parameters are a particular case: the method does one thing when the value is true and something else when it is false. Consider the following code:

```csharp
var distance1 = CalculateDistance(point1, point2, true);
var distance2 = CalculateDistance(point1, point2, false);
```

What is the difference between those two results? The call sites do not say, and finding out means opening CalculateDistance.

```csharp
double CalculateDistance(Point point1, Point point2, bool shouldBeAsMiles)
{
    double deltaX = point2.X - point1.X;
    double deltaY = point2.Y - point1.Y;
    var distanceInKm = Math.Sqrt(deltaX * deltaX + deltaY * deltaY);
    if (shouldBeAsMiles)
    {
        const double kilometersToMilesConversionFactor = 0.621371;
        return distanceInKm * kilometersToMilesConversionFactor;
    }
    return distanceInKm;
}
```

Inside, the Boolean turns out to decide whether the result is in kilometers or miles. That is two problems at once. The reader had to leave the call site to understand it, and the method does two things: it calculates a distance and it converts the unit. The fix is to let the method do the first thing only. Renaming it to CalculateDistanceInKilometers puts the unit in the name, where the caller can see it.

```csharp
var distanceInKm = CalculateDistanceInKilometers(point1, point2);
```

**Callers who need miles get a separate method whose only job is the conversion:**

```csharp
var distanceInKm= UnitConverter.KilometersToMiles(distanceInKm);
```

Each method now does one thing, and the Boolean parameter is gone. The call site says what unit it produces, so nothing has to be looked up. Not every Boolean parameter is a problem. A value such as isAdmin can be legitimate when it is simply data used by a single decision rather than a flag that switches the method between unrelated jobs:

```csharp
bool IsAuthorized(string userName, bool isAdmin)
{
    if (isAdmin)
    {
        return true;
    }
    return _authorizedUsers.Contains(userName);
}
```

Avoiding parameter-count anti-patterns Do not cut parameters at any cost. Some operations need several independent values, and no grouping will change that. The DateTime constructor is a good example. It represents a point in time, so it takes a year, a month, a day, an hour, a minute, and a second. Bundling those into another object to bring the count down would add a layer of indirection without making the concept any clearer.

```csharp
var titanicSinkingDate = new DateTime(1912, 4, 15, 2, 20, 0);
```

Likewise, a method that compares two values within a tolerance naturally needs the two values and the tolerance:

```csharp
bool AreEqualWithinTolerance(float a, float b, float tolerance)
{
    return Math.Abs(a - b) <= tolerance;
}
```

A damaging anti-pattern is hiding a former parameter in instance state. The following pure helper exposes all three inputs in its signature, making it explicit and easy to understand:

```csharp
public static decimal CalculateTotalPrice(
    int quantity, decimal unitPrice, decimal tax)
{
    return quantity * unitPrice * (1 + tax);
}
```

Review question: When you see a Boolean parameter, ask whether true and false cause the method to perform different responsibilities. If they do, separate those responsibilities or make the choice explicit in the API.

> **Note**

Someone might see three parameters and decide that moving tax to a field would be an improvement. It would not. The method still depends on three values, and one of them has merely been hidden from the signature. Reading the call no longer tells us what the calculation is based on. The method now depends on instance state, so it cannot be called with a different tax rate without constructing an object first, and testing it in isolation becomes harder than it was.

```csharp
public class OrderPriceCalculator
{
    private readonly decimal _tax;
    public OrderPriceCalculator(decimal tax)
    {
        _tax = tax;
    }
    public decimal CalculateTotalPrice(int quantity, decimal unitPrice)
    {
        return quantity * unitPrice * (1 + _tax);
    }
}
```

Fields exist to hold state that belongs to the object: data it needs to remember between calls because that data is part of what the object is. A list keeps its elements. A database connector keeps the connection details it was given in its constructor and reuses them across Connect and Disconnect. A parameter is different. It is an input to one particular operation, and the object has no reason to remember it afterward. Moving such an input into a field does not remove it from the design; it only removes it from the signature. The method now depends on a value set somewhere else. Before turning a parameter into a field, ask whether the object would still make sense holding that value once the method has returned. If not, it belongs in the signature. Ordering parameters logically The order of parameters should follow a pattern that callers can predict. DateTime is naturally read from larger units to smaller ones: year, month, day, hour, minute, and second. A database location can similarly be described from the broader server cluster to the server and then the database.

```csharp
public void Connect(
    string serverClusterName,
    string serverName,
    string databaseName)
{
    // ...
}
```

Another useful rule is to follow the order suggested by the method name. If a method is called IsPersonPresentInGroup, a person parameter followed by a group parameter matches the sentence the caller reads.

## Keeping methods small and focused

Long methods are difficult to understand because the reader must retain more state, branches, and intermediate values at once. Very large methods are also harder to test and more likely to combine unrelated responsibilities. Small methods reduce that cognitive load and make individual operations easier to name and reuse. A practical heuristic is the size of the screen: if a method runs past roughly 20 lines, or past 120 characters in width, it is worth a second look. Treat these numbers as warning thresholds rather than hard limits. A cohesive 25-line method can be clearer than five artificial helpers, while a six-line method can still mix unrelated responsibilities. Long lines can usually be broken without changing the design. Long methods require a different question: does every part of this method contribute to the same task at the same conceptual level? Giving each method one task A focused method does one coherent job. Some jobs are small computations, such as squaring a number or checking whether a number is even:

```csharp
float Square(float number)
{
    return number * number;
}
bool IsEven(int number)
{
    return number % 2 == 0;
}
```

A single task can also be orchestration. Reading user data from an API may require connecting, retrieving JSON, and deserializing it. A high-level method can coordinate those steps without implementing each detail itself:

```csharp
List<User> ReadUsersData()
{
    var apiConnection = ConnectToApi("https://someApi/", "api/users");
    var usersAsJson = apiConnection.ReadAll();
    return JsonSerializer.Deserialize<List<User>>(usersAsJson);
}
```

The method still has one responsibility: coordinating the process of reading user data. Its sub- steps are delegated to operations at a lower level of abstraction. Recognizing methods that do too much A short method can still contain more than one responsibility. In the following example, SaveToFile writes content and silently adds a .txt extension:

```csharp
void SaveToFile(string fileName, string content)
{
    File.WriteAllText(fileName + ".txt", content);
}
```

String concatenation is a low-level file-name construction detail placed directly beside the higher-level file-writing operation. The path-building logic is also stuck inside this method, so anything else that needs to build the same path has to repeat it. Consider a method that filters empty strings, joins the remaining strings, and writes the result to a file:

```csharp
void SaveToFile(List<string> words, string filePath)
{
    var nonEmptyWords = new List<string>();
    foreach (var word in words)
    {
        if (!string.IsNullOrEmpty(word))
        {
            nonEmptyWords.Add(word);
        }
    }
    string text = string.Join(Environment.NewLine, nonEmptyWords);
    File.WriteAllText(filePath, text);
}
```

Renaming the method to SaveNonEmptyToFile makes the filtering visible but does not remove the mixed responsibilities. Extracting the filter creates a reusable operation and leaves the main method to coordinate the steps:

```csharp
List<string> GetNonEmptyOnly(List<string> words)
{
    var nonEmptyWords = new List<string>();
    foreach (var word in words)
    {
        if (!string.IsNullOrEmpty(word))
        {
            nonEmptyWords.Add(word);
        }
    }
    return nonEmptyWords;
}
void SaveNonEmptyToFile(List<string> words, string filePath)
{
    var nonEmptyWords = GetNonEmptyOnly(words);
    var textToBeSaved = string.Join(Environment.NewLine, nonEmptyWords);
    File.WriteAllText(filePath, textToBeSaved);
}
```

## Maintaining consistent levels of abstraction

Abstraction is a simplified view of something. It shows the idea we need and hides the machinery underneath. We rely on it constantly without thinking about it. Take a method that splits a piece of text into words. To use it, we need to know one thing: text goes in, a collection of words comes out. We do not need to know how the text is stored in memory, how the method walks through it, or where the resulting words are allocated. All of that exists, and all of it is hidden behind the signature. Abstractions come at different levels, and the difference between them is how much detail they hide. Consider a BuildHouse method. It sits at a high level, because one call stands for an enormous amount of work. BuildWalls is one step below it, since building walls is part of building a house. Below that come BuildFoundation, PlaceBricks, BindBricksWithMortar, and CoverWithPlaster. Each step down brings more detail and a narrower view of the whole.

```csharp
public void BuildHouse()
{
    BuildWalls();
    PlaceDoors();
    PlaceWindows();
    InstallElectricity();
}
public void BuildWalls()
{
    BuildFoundation();
    PlaceBricks();
    BindBricksWithMortar();
    CoverWithPlaster();
}
```

A readable method calls operations that sit roughly one level below its own. BuildHouse calls BuildWalls, and BuildWalls calls the steps that make up a wall.

Flattening those lower steps into BuildHouse makes the method harder to read, because the reader keeps switching between scales:

```csharp
public void BuildHouse()
{
    BuildFoundation();
    PlaceBricks();
    BindBricksWithMortar();
    CoverWithPlaster();
    PlaceDoors();
    PlaceWindows();
    InstallElectricity();
}
```

The same principle applies to all operations our code executes. Let's consider the SaveNonEmptyToFile method again.

```csharp
void SaveNonEmptyToFile(List<string> words, string filePath)
{
    var nonEmptyWords = GetNonEmptyOnly(words);
    var textToBeSaved = string.Join(Environment.NewLine, nonEmptyWords);
    File.WriteAllText(filePath, textToBeSaved);
}
```

It reads as an instruction: filter the words, join them, write them to the file. It calls three methods, each one level less abstract than itself, and reading it does not require knowing how any of them work. It is enough that GetNonEmptyOnly returns the non-empty strings, which we can learn from its name alone. How it does that stays out of the way, which is exactly what makes the method readable. In the original version, the filtering loop sat inside the method and distracted from what the method was really doing. Now imagine this method without string.Join and File.WriteAllText, with low-level code in their place: joining the strings character by character, opening a file handle, writing to a  stream, closing it. Following that would be much harder. And when low-level instructions are wrapped in higher-level methods, they can be reused elsewhere. This is why the operations inside a method should sit at a similar level of abstraction. A method that mixes them forces the reader to switch between levels while reading, and that switching is what makes code tiring to follow. Moving the lower-level operations into methods of their own solves more than readability. Once the low-level logic lives in its own method, anything else that needs the same mechanism can call it instead of repeating it.

## Ordering methods for readability

Method order is mainly a reading concern. Language requirements come first, but where the language gives you freedom, arrange methods so that readers encounter the public behavior and high-level flow before implementation details. Place public constructors before ordinary methods; keep constructors grouped together. Place public methods before private implementation helpers. When one method calls another, place the higher-level caller above the lower-level helper where practical. Keep overloads together; ordering them from fewer parameters to more parameters can make the group easier to scan. Treat these as readability guidelines rather than rigid rules.

**For example, MethodA appears before the helpers it delegates to:**

```csharp
void MethodA()
{
    MethodB();
    MethodC();
}
void MethodB()
{
}
```

Practical rule: Within a method, prefer operations that sit at a consistent conceptual level. Delegate lower-level details when exposing them would distract from the method's primary task.

> **Note**
```csharp
void MethodC()
{
}
```

This top-down arrangement allows a reader to understand the main flow and inspect lower- level details only when necessary.

## Keeping methods independent

A method should not depend on an undocumented ritual before it can be called. Suppose a PDF library appears to support the following straightforward usage:

```csharp
var pdfReader = new PdfReader();
string content = pdfReader.ReadFrom("someFile.pdf");
```

If the call fails because the user was expected to invoke Init first, the method contract hides an important prerequisite:

```csharp
var pdfReader = new PdfReader();
pdfReader.Init();
string content = pdfReader.ReadFrom("someFile.pdf");
```

Required setup should be made explicit. Stable configuration can be required in the constructor, while operation-specific data can be required as method parameters. The caller should not have to remember a magic sequence of unrelated calls or global assignments.

## Using pure functions where they fit

One of the best ways of improving your functions is to make them pure. A pure function satisfies two conditions: its result depends only on its input values, and it has no side effects. Given the same arguments, it therefore returns the same result and does not alter state elsewhere in the program.

```csharp
int Max(int a, int b)
{
    return a >= b ? a : b;
}
```

Max is pure because its result is completely determined by a and b.

Now, let's consider another method:

```csharp
class ItemsStorage
{
    private List<Item> _items = new();
    public Item FindItemWithName(string name)
    {
        return _items.FirstOrDefault(item => item.Name == name);
    }
}
```

The FindItemWithName method reads a field, which is what makes it impure. The field can change independently of the arguments, so the same argument may produce a different result on the next call. Likewise, a method that reads DateTime.Now depends on an external value. It will produce a different result every time it is called, which means it is not pure:

```csharp
string GetCurrentTime(string format)
{
    return DateTime.Now.ToString(format);
}
```

Side effects are the other source of impurity. A side effect is any change a function makes outside its return value, such as writing to a field, modifying a collection it was given, or touching a file or a database. An example could be mutating a list supplied by the caller.

```csharp
public void RemoveFirstItem(List<Item> items)
{
    items.RemoveAt(0);
}
```

Why pure functions are easier to work with Pure functions are easy to read, because understanding one requires nothing but its own body. There is no additional context to keep in mind, no state of the surrounding class, no global variables. Everything the function needs is listed in its parameters. The benefit is clearer when set against impure functions. An impure function may reach for anything: fields of its own class, static members of other classes, global state. A method may appear to take two parameters while in fact it also reads two fields from the current class, three from another, and a handful of globals. Its dependencies are not visible in its signature, so understanding it means finding all of them first. Impure functions may also modify state, whether their own parameters, the fields of their class, or objects belonging elsewhere. This makes changes hard to trace. A list passed to an innocent-looking method can come back empty, and nothing at the call site suggested that it might. When any call can change state behind the scenes, no assumption about the state of the program is safe. Pure functions remove both problems. They depend only on their parameters and they change nothing, so a caller knows that nothing else in the program moved while the function ran. They are also unusually easy to test. A test needs no setup, since there is no context to establish, and the same arguments always produce the same result. Calling the function with a few sets of arguments and checking the results is enough. Not every function can be pure. Programs have to talk to users, databases, and other systems, and all of that involves side effects. The practical goal is a codebase split in two: impure functions at the boundaries, where the program meets the outside world, and a core built from pure ones.

Code formatting is the consistent arrangement of source code: indentation, spacing, line breaks, braces, and the visual separation of related statements. ## Applying indentation consistently

Indentation shows what belongs to what. A statement indented under a loop, a condition, a method, or a class is read as part of it. When the indentation is consistent, the structure of the code can be taken in before a single expression is read. Compare an unindented block with the same logic formatted conventionally. ## Structuring code blocks safely

In languages that use braces to delimit code blocks, a useful safety practice is to keep the braces even when the block contains only one statement. Omitting them may save two lines, but it creates an easy path to a bug when another statement is added later. Without braces, only the first statement belongs to the loop:

```csharp
for (int i = 0; i < numbers.Count; i++)
    Console.WriteLine("Do something");
Console.WriteLine("Do something else");
```

If both statements are intended to repeat, the block should be explicit:

```csharp
for (int i = 0; i < numbers.Count; i++)
{
    Console.WriteLine("Do something");
    Console.WriteLine("Do something else");
}
```

The braces make the scope unmistakable and remove the need to remember to add them when the block grows. A second useful signal is block size. If a loop or conditional is so large that its opening and closing braces cannot be seen together on a reasonable screen, the reader must scroll to recover the structure. That usually indicates an opportunity to extract part of the block into a well- named method. The common guideline is 120 characters of width and 20 lines of height, which is roughly what fits on one screen without scrolling in either direction.

## Breaking long lines clearly

The 120‑character limit deserves a closer look, since line length affects readability in its own right. Long lines force horizontal scrolling and make related expressions harder to compare.

Every project can set its own limit, but what matters more than the exact number is breaking lines at points that are meaningful and consistent across the codebase. Consider a condition from a tic-tac-toe implementation:

```csharp
if (gameArray[i, 0] == c && gameArray[i, 1] == c && gameArray[i, 2] == c)
{
    return true;
}
```

Breaking each related condition in the same way makes the comparison easier:

```csharp
if (gameArray[i, 0] == c &&
    gameArray[i, 1] == c &&
        gameArray[i, 2] == c)
{
    return true;
}
```

Parameter lists benefit from the same treatment. When a signature gets crowded, giving each parameter its own line creates a predictable pattern. And it is worth going all the way: either every parameter sits on its own line, or none of them do. Three on one line and two on the next is harder to scan than any consistent choice.

```csharp
bool IsWithinRange(
    int min,
    int max,
    int value,
    bool isInclusive)
```

```csharp
return numbers
    .Where(number => number % 2 != 0)
    .Select(number => number * number)
    .Take(3);
```

## Using vertical space to organize code

Empty lines serve a role similar to paragraph breaks in prose. They separate logical units and help the reader see which statements belong together. Two methods, for example, should normally be visually separated because they are distinct units of behavior.

```csharp
bool AreAllEven(List<int> numbers)
{
    // ...
}
void CountEvenAndOdd(List<int> numbers)
{
    // ...
}
```

Within a single construct, however, unnecessary blank lines can fragment related code. An if and its else branch belong together and should normally remain visually connected. Blank lines are also useful inside a larger method when they mark meaningful stages. The following method becomes easier to scan when declarations, iteration, and final output are separated:

```csharp
void CountEvenAndOdd(List<int> numbers)
{
    int totalEven = 0;
    int totalOdd = 0;
    for (int i = 0; i < numbers.Count; i++)
    {
        Console.WriteLine($"Processing number at index {i}");
        if (numbers[i] % 2 == 0)
        {
            totalEven++;
        }
        else
        {
            totalOdd++;
        }
    }
    Console.WriteLine($"Total even numbers: {totalEven}");
    Console.WriteLine($"Total odd numbers: {totalOdd}");
}
```

The exact placement of blank lines is partly a style decision. Some teams place an empty line before a final return statement in larger methods; others omit it in very small methods. Once again, consistency is more valuable than insisting that one preference is universally correct. One rule worth keeping simple is the number of consecutive blank lines. A single empty line is enough to separate concepts. Multiple empty lines lengthen files without adding more meaning and increase the amount of scrolling required.

# Chapter 5: Applying the Single Responsibility Principle

Classes often grow by accumulation. A class may be written with one clear job, but then a new requirement comes along, and the easiest place to put it is a class that already exists and is roughly related. Nobody makes a decision to give it a second responsibility. It just happens, one small addition at a time, until the class does several unrelated things and a change to one of them can break the others. The Single Responsibility Principle (SRP) provides a practical way to reason about that. Rather than demanding one method per class, SRP asks whether the class serves one coherent purpose and has one meaningful reason to change. This chapter introduces the SOLID principles family and then develops SRP through practical examples. The following chapters cover the remaining four principles one at a time. Chapter 9 then brings all five principles together in a single refactoring case study, showing how they can work together in practice.

## Understanding the Single Responsibility Principle

The Single Responsibility Principle states that a class should have one coherent responsibility. You will also encounter a common formulation: a class should have no more than one reason to change. Both formulations are useful, but the word responsibility needs careful interpretation. A responsibility is the coherent purpose that the class serves. Why combining responsibilities creates problems A simple analogy is to imagine a jacket with a backpack sewn onto it. A jacket keeps you warm; a backpack carries your belongings. You may sometimes use both at the same time, but that does not mean they should be one object. If the weather is warm, you may want the backpack without the jacket. If you need more carrying capacity, you may want a different backpack without replacing the jacket. Combining them removes that flexibility. The same problem appears in software when a class combines unrelated work. Consider a class that reads personal data from a SQL database and also formats a person as text. A client that needs only database access is forced to depend on formatting code as well, and a client that needs only formatting must know about a data-access class. The following class illustrates the problem:

```csharp
public class PersonalDataAccess
{
    private readonly string _connectionString;
    public PersonalDataAccess(string connectionString)
    {
        _connectionString = connectionString;
    }
    public List<Person> GetAll()
    {
        var people = new List<Person>();
        using SqlConnection connection = new SqlConnection(_connectionString);
        connection.Open();
        string query = "SELECT Id, FirstName, LastName, Age FROM People";
        using SqlCommand command = new SqlCommand(query, connection);
        using SqlDataReader reader = command.ExecuteReader();
        while (reader.Read())
        {
            var person = new Person
            {
                Id = reader.GetInt32(0),
                FirstName = reader.GetString(1),
                LastName = reader.GetString(2),
                Age = reader.GetInt32(3)
            };
            people.Add(person);
        }
        return people;
    }
    public string FormatPersonalData(Person person)
    {
        return $"ID: {person.Id}, " +
            $"Name: {person.FirstName} {person.LastName}, " +
                $"Age: {person.Age}";
    }
}
```

The class has two independent responsibilities: obtaining the data and formatting it. That comes at a cost, and one of those costs is worth going back to the jacket and backpack analogy for. Say we want a light jacket, a winter jacket, and a rain jacket, and a small, a medium, and a large backpack. Kept separate, that is six things. Sewn together, every jacket needs a version with each backpack, so we end up with nine, and each new jacket adds three more. Classes behave the same way. Once responsibilities are mixed, the number of classes we need can grow very fast. Table 5.2 summarizes the main design costs of combining these responsibilities. Reduced flexibility Changing SQL access to another source requires modifying the same class that also contains the formatting behavior.

Problem Why it matters More combinations Combining two responsibilities in one class means a separate class for every combination of them, so the number of classes multiplies instead of adding up. Harder maintenance A change to one responsibility marks the whole class as changed and may require broader review, retesting, and redeployment. Hidden interaction risk Methods for unrelated responsibilities can accidentally share state or depend on one another. Less focused tests A test fixture for the class may need to accommodate unrelated behaviors. These problems are not caused by the number of lines in the class. They come from the fact that two independent reasons for change are packaged together. Separating the responsibilities The refactoring is straightforward once the responsibilities are clear. Move the formatting behavior into a dedicated class. To keep the focus on the split, the repeated method bodies are abbreviated below:

```csharp
public class PersonalDataFormatter
{
    public string FormatPerson(Person person)
    {
        // Formatting logic omitted for brevity.
    }
}
```

The original class can then be renamed so that its remaining responsibility is explicit:

```csharp
public class PeopleDataReader
{
    private readonly string _connectionString;
    public PeopleDataReader(string connectionString)
    {
        _connectionString = connectionString;
    }
    public List<Person> GetAll()
    {
        // Data-access logic omitted for brevity.
    }
}
```

The two classes can still be used together when the application needs both operations:

```csharp

var firstPerson = people.First();

    "First person's data: " +
        personalDataFormatter.Format(firstPerson));
```

The important change is not merely that the code has been split. Each new class has a precise name, can be reused independently, can be tested around one purpose, and can change without forcing unrelated behavior to change with it. A single responsibility does not mean a single method Inexperienced developers often assume the Single Responsibility Principle is about counting public methods. If a class exposes two of them, it does two things, so it must be violating the principle. That is not what the principle says. A class can expose many public methods and still have one responsibility, as long as they all serve the same purpose. Data structures can serve as a useful example. Consider the List<T> class in C#, which represents a dynamic collection of items. It has many methods, such as Add, Remove, Clear, and Sort. That does not mean it has more than one responsibility. Its responsibility is to provide a dynamic structure for storing multiple items of the same type, and covering that takes more than one method. A simplified sketch of the relevant API looks like this:

```csharp
public class List<T>
{
    public void Add(T item);
    public void Remove(T item);
    public void Clear();
    public void Sort();
    // and more
}
```

Splitting every operation into its own class would be a terrible idea. It would give us classes such as ListItemsAdder, ListItemsRemover, ListClearer, and ListSorter—four types working on the same data and useless apart from each other. These operations belong together because they all serve the same purpose: managing a list. There is also a practical cost: those classes would need some way to reach and modify the list's state, introducing extra coupling and weakening the collection's control over its own invariants. A repository provides another example. A PeopleRepository may legitimately add, update, delete, and retrieve people because all of those methods serve one responsibility: managing the persistence of Person objects. A simplified repository API could look like this:

```csharp
public class PeopleRepository
{
    public void AddPerson(Person person);
    public void UpdatePerson(Person person);
    public void DeletePerson(int personId);
    public Person GetPersonById(int personId);
    public List<Person> GetAllPeople();
}
```

Orchestration can still be one responsibility Consider a UserAuthorizer class and its IsAuthorized method. Given a user ID and an action type, it reads the user from a repository, reads the list of actions that user can perform, and checks whether any of them matches the requested type. In later chapters, we will decouple  this further using interfaces, but concrete delegation still demonstrates single responsibility at this stage.

```csharp
public class UserAuthorizer
{
    private readonly UsersRepository _usersRepository;
    private readonly ActionsRepository _actionsRepository;
    public UserAuthorizer(
        UsersRepository usersRepository,
        ActionsRepository actionsRepository)
    {
        _usersRepository = usersRepository;
        _actionsRepository = actionsRepository;
    }
    public bool IsAuthorized(int userId, ActionType actionType)
    {
        var user = _usersRepository.GetById(userId);
        var allowedActions = _actionsRepository.GetAllowedFor(user);
        return allowedActions.Any(action => action.Type == actionType);
    }
}
```

One could argue that this class does three things instead of one. It reads a user, it reads actions, and it compares them. Three steps, so some developers may see this as an SRP violation. Not necessarily. The class still has one responsibility, which is deciding whether a user is authorized to perform an action. Getting there takes several steps, but the class does not carry them out itself. Data access is delegated to repositories, and UserAuthorizer only orchestrates the steps. Its responsibility has not changed. This kind of class is an orchestrator. Its methods may invoke several collaborators, but the class still has a clear purpose. SRP asks whether those operations belong to one responsibility, not whether there is only one operation. Using one reason to change as an SRP test The alternative formulation of SRP, that a class should have only one reason to change, can make class boundaries easier to evaluate. The earlier PersonalDataAccess class has at least two independent reasons to change. The way data is read may change, for example from SQL to

Excel, and the way a person is formatted may change, for example by omitting the ID or changing the textual representation.

```csharp
public class PersonalDataAccess
{
    public List<Person> GetAll();
    public string FormatPersonalData(Person person);
}
```

After the refactoring and splitting this type into two independent classes, the problem is gone:

PeopleDataReader changes when data-access requirements change, while PersonalDataFormatter changes when formatting requirements change. Each class now responds to a different axis of change. The same reasoning explains why List<T> can still follow SRP. Improving Add performance or strengthening Remove error handling are both changes to the same responsibility: making the list a better data structure.

UserAuthorizer works the same way. Its responsibility is to check whether a user may perform an action, and to do that it uses a few other classes, such as the users repository and the actions repository. How many reasons to change does it have? One. The flow of the checks may change, for example when we add a verification that the user with the given ID exists, or that the user is an administrator. One could think it has more. What if we switch to a different database? But connecting to a database is the job of the repositories. Changing the database is their reason to change, not the authorizer's, and when that change happens, the code of UserAuthorizer stays exactly as it is. # Chapter 6: Applying the Open-Closed Principle

Software development is a continuous process. It almost never happens that we learn all the requirements before starting a project and that nothing changes along the way. Usually, we get a rough idea of what we are building and detailed requirements for a few basic features. The rest arrives as the work progresses, and some of it replaces what we were told earlier, sometimes reversing a decision completely. Releasing the application does not end the process either. Think about services like YouTube or Instagram. They change constantly. Features are added, bugs are fixed, and interfaces are redesigned. So, change is not an exception we prepare for just in case. It is the normal state of a codebase, and our code has to be ready for it. That is what the Open-Closed Principle (OCP) is about. This principle states that modules, classes, and methods should be open for extension but closed for modification. This chapter starts with a review of abstraction and polymorphism, the two concepts needed to understand the Open-Closed Principle. It then looks at a type that breaks the principle and works through a possible refactoring. It closes with the practical limits of the principle, so that it stays a design aid rather than a rigid rule. In this chapter, we will cover the following topics: Reviewing abstract types and polymorphism Understanding the Open-Closed Principle Recognizing an OCP violation in existing code Refactoring behavior behind an abstraction Containing unavoidable changes in factories and selection logic

Recognizing when an abstraction itself must change Balancing OCP with performance, bug fixes, and major requirement changes Relating the Open-Closed and Single Responsibility Principles By the end of this chapter, you will understand how abstraction and polymorphism make code extensible, be able to recognize when the Open-Closed Principle is being broken, and know how to refactor such code so that new behavior can be added without modifying what already exists. ## Reviewing abstract types and polymorphism

The OCP is easier to apply once we are comfortable with abstract types and polymorphism. Many modern languages let us define abstract types that describe a contract independently of a particular implementation. In C#, an interface is one way to express such a contract. In the simple form used here, the interface declares member signatures, while implementing types provide the corresponding behavior. Code that depends on the interface can work with any

**implementation that satisfies that contract. For example:**

```csharp
public interface SomeInterface
{
    void SomeMethod();
    int SomeOtherMethod(string param);
}
```

A concrete class that implements this interface provides implementations for its declared methods:

```csharp
public class SomeClass : SomeInterface
{
    public void SomeMethod()
    {
        // do something
    }
    public int SomeOtherMethod(string param)
    {
        // do something
        return 0;
    }
}
```

Interfaces are one way C# supports polymorphism: code can work with a common type while each concrete implementation behaves in its own way. Code holding a SomeInterface reference can call SomeMethod and SomeOtherMethod on it without knowing whether the object behind it is a SomeClass or some other implementation. The same applies to interfaces from the standard library. A method that accepts an ICollection<int> works with any collection satisfying that contract. In both cases, code holding a value through the interface can rely only on the operations the interface declares, and not on anything specific to the implementation behind it. This ability to write code against a stable abstraction is central to OCP. New concrete implementations can often be added later without rewriting the code that depends on the abstraction.

## Understanding the Open-Closed Principle

Requirements change throughout the life of an application. New features arrive, existing behavior is refined, and assumptions that once seemed stable turn out not to be. The goal is to C# convention: Interface names conventionally begin with the letter I, as in ICollection, IAccount, or IVideosRepository.

> **Note**
 design the system so that when change comes, its impact stays contained. The Open-Closed Principle states that modules, classes, and methods should be open for extension but closed for modification. In practical terms, you should prefer designs in which new behavior can be introduced by adding new code instead of repeatedly editing code that already works. Modification is not wrong in itself, but it carries risk. Existing code may be used elsewhere in the application, or by consumers outside it, so changing it can introduce defects, surprise developers relying on the current behavior, or break backward compatibility. Automated tests reduce that risk. They do not remove it. Recognizing an OCP violation in account behavior Consider a video-streaming application with free and premium accounts. Premium users can access all videos, while free users can access only videos marked as free. Here is the code implementing this logic:

```csharp
public class User
{
    public AccountType AccountType { get; }
    private readonly IVideosRepository _videosRepository;
    public User(AccountType accountType, IVideosRepository videosRepository)
    {
        AccountType = accountType;
        _videosRepository = videosRepository;
    }
    public List<Video> GetAvailableVideos()
    {
        if (AccountType == AccountType.Premium)
        {
            return _videosRepository.GetAll();
        }
        return _videosRepository
            .GetAll()
            .Where(video => video.IsFree)
            .ToList();
    }
}
public enum AccountType
{
    Free,
    Premium
}
```

Open-Closed Principle: Prefer adding a new implementation behind a stable abstraction when a predictable family of behaviors is expected to grow. Do not interpret the principle as a ban on ever editing existing code.

> **Note**

The design appears manageable until the business introduces a Kids account. Supporting the new account requires modifying the enum, the video data structure, and, crucially, the existing GetAvailableVideos method:

```csharp
public List<Video> GetAvailableVideos()
{
    if (AccountType == AccountType.Premium)
    {
        return _videosRepository.GetAll();
    }
    if (AccountType == AccountType.Kids)
    {
        return _videosRepository
            .GetAll()
            .Where(video => video.IsForKids)
            .ToList();
    }
    return _videosRepository
        .GetAll()
        .Where(video => video.IsFree)
        .ToList();
}
```

Each new account category extends the same conditional. In a larger system, equivalent branching may be repeated in many places. The code is therefore not closed for modification: every new account type pushes another change into existing behavior. 

Refactoring account behavior behind an abstraction A better design makes account behavior polymorphic. Start with an interface that represents the behavior shared by account types:

```csharp
public interface IAccount
{
    AccountType AccountType { get; }
    List<Video> GetAvailableVideos();
}
```

FreeAccount and PremiumAccount can then implement the behavior appropriate to each account type:

```csharp
public class FreeAccount : IAccount
{
    public AccountType AccountType { get; } = AccountType.Free;
    private readonly IVideosRepository _videosRepository;
    public FreeAccount(IVideosRepository videosRepository)
    {
        _videosRepository = videosRepository;
    }
    public List<Video> GetAvailableVideos()
    {
        return _videosRepository
            .GetAll()
            .Where(video => video.IsFree)
            .ToList();
    }
}
public class PremiumAccount : IAccount
{
    public AccountType AccountType { get; } = AccountType.Premium;
    private readonly IVideosRepository _videosRepository;
    public PremiumAccount(IVideosRepository videosRepository)
    {
        _videosRepository = videosRepository;
    }
    public List<Video> GetAvailableVideos()
    {
        return _videosRepository.GetAll().ToList();
    }
}
```

User no longer decides which filtering rule applies. It depends only on IAccount and delegates

the operation:

```csharp
public class User
{
    private readonly IAccount _account;
    public User(IAccount account)
    {
        _account = account;
    }
    public List<Video> GetAvailableVideos()
    {
        return _account.GetAvailableVideos();
    }
}
```

A new KidsAccount can now be added as another implementation of the same abstraction:

```csharp
public class KidsAccount : IAccount
{
    public AccountType AccountType { get; } = AccountType.Kids;
    private readonly IVideosRepository _videosRepository;
    public KidsAccount(IVideosRepository videosRepository)
    {
        _videosRepository = videosRepository;
    }
    public List<Video> GetAvailableVideos()
    {
        return _videosRepository
            .GetAll()
            .Where(video => video.IsForKids)
            .ToList();
    }
}
```

The existing User, FreeAccount, and PremiumAccount classes do not need to change when KidsAccount is introduced. The system is extended by adding a new implementation.

The AccountType enum still needs a localized modification to add Kids, so this design is not completely modification-free. The important improvement is that the account-specific behavior is added through KidsAccount without reopening the existing account implementations. This design also makes account-specific behavior easier to test because each filtering rule has its own focused type. SRP and OCP reinforce one another here: each account class has a clear responsibility, and new account behavior can be introduced through extension.

## Understanding the practical limits of OCP

The Open-Closed Principle is a design goal, not a promise that existing code will never change. Some modifications are unavoidable, and forcing every requirement into an extension-only design can produce more complexity than value. The useful question is where change should be contained and whether the abstraction reflects real variation in the domain. Containing unavoidable changes in a factory Even after introducing IAccount, the application still needs some code that chooses which concrete account type to create. If a user selects an account type during registration, some selection logic must map that choice to a concrete object. A direct conditional might look like this:

```csharp
IAccount CreateAccount(AccountType accountType)
{
    var videosRepository = new VideosRepository();
    if (accountType == AccountType.Free)
    {
        return new FreeAccount(videosRepository);
    }
    if (accountType == AccountType.Kids)
    {
        return new KidsAccount(videosRepository);
    }
    return new PremiumAccount(videosRepository);
}
```

Adding a new account type still requires this selection logic to change. That does not invalidate the broader refactoring. The important improvement is that the unavoidable modification is isolated to one small place instead of being repeated throughout the application. A dedicated factory makes that responsibility explicit:

```csharp
public class AccountsFactory
{
    public IAccount CreateAccount(AccountType accountType)
    {
        var videosRepository = new VideosRepository();
        switch (accountType)
        {
            case AccountType.Free:
                return new FreeAccount(videosRepository);
            case AccountType.Kids:
                return new KidsAccount(videosRepository);
            case AccountType.Premium:
                return new PremiumAccount(videosRepository);
            default:
                throw new ArgumentOutOfRangeException(nameof(accountType));
        }
    }
}
```

Design principle: If some modification cannot be eliminated, contain it. A small, explicit factory is easier to reason about than account-type conditionals scattered through the codebase.

> **Note**

When the abstraction itself must change Another limitation appears when a new requirement changes the contract shared by every implementation. Suppose video availability must now depend on the user's region. The original IAccount contract exposes a parameterless GetAvailableVideos method, so it cannot express the new input.

```csharp
public interface IAccount
{
    AccountType AccountType { get; }
    List<Video> GetAvailableVideos();
}
```

One reasonable response is to change the contract so the region becomes explicit:

```csharp
public interface IAccount
{
    AccountType AccountType { get; }
    List<Video> GetAvailableVideos(string region);
}
```

**Every implementation must then be updated, for example:**

```csharp
public List<Video> GetAvailableVideos(string region)
{
    return _videosRepository
        .GetAll(region)
        .Where(video => video.IsForKids)
        .ToList();
}
```

This is a modification of existing code, so the design is not closed to this particular kind of change. The important lesson is that no abstraction can anticipate every future requirement. Trying to predict all possible variations in advance often creates abstractions that are more complicated than the real problem and may still fail to match the eventual requirement. Instead, design around variations that are currently meaningful and reasonably likely. When a new axis of change appears, modify the design carefully and use the experience to decide whether the abstraction should evolve.

Do not sacrifice performance for formal compliance It may be possible to avoid changing IAccount by loading all videos first and introducing a new VideosFilterer that filters by region afterward. That approach adds new code without modifying existing code, so it appears to satisfy OCP. However, it can be a poor engineering decision if filtering after retrieval causes unnecessary data transfer and slower execution.

```csharp
var youngUser = new User(new KidsAccount(videosRepository));
var availableVideos = youngUser.GetAvailableVideos();
availableVideos = new VideosFilterer()
    .FilterByRegion("Australia", availableVideos);
```

When the repository can translate filtering into a database-side query, applying the region restriction before materializing the data is generally more efficient. Once all data has already been loaded into the application, later filtering occurs in memory and may transfer far more data than necessary. The broader principle is that clean design must serve the software, not the other way around. A design that technically avoids modifying existing code but introduces a significant performance problem is not an improvement. When changing existing code is the right choice Some requirements are so different from the original model that preserving the old abstraction would leave obsolete concepts embedded in the design. If a streaming platform abandons account-based access entirely and moves to free or pay-per-view videos, retaining the previous account hierarchy merely to avoid modification may produce convoluted code. In such cases, redesigning or replacing parts of the system can be the cleaner option, provided the change is planned, tested, and protected by version control. Bug fixes are even clearer. If existing code is wrong, correct it. Do not create a parallel subtype that reproduces the old behavior except for the defect simply to claim that the original implementation remained closed for modification.

## Bringing SRP and OCP together

SRP and OCP address different questions, but they often lead to compatible designs. SRP asks whether a class has one coherent responsibility. OCP asks whether expected variations can be introduced without repeatedly modifying stable behavior. In the streaming example, moving video-selection behavior into separate account classes gives each class a focused purpose and allows new account variants to be added behind IAccount. The principles should not be applied mechanically. Splitting every method into a class would misuse SRP, while creating abstractions for every imaginable future requirement would misuse OCP. Good design comes from identifying real responsibilities, real variation, and the likely cost of change.

# Chapter 7: Applying the Liskov Substitution Principle

When a class derives from another one, it takes on a promise. Whatever the base type says it can do, the derived type says it can do as well. Code written against the base type is entitled to rely on that. The compiler only checks half of it. A subtype can override every method, match every signature, compile without a complaint, and still refuse to do what the base type promised. It throws where the base type returned a value, or rejects inputs the base type accepted. The hierarchy still looks correct from the outside, so the callers are the ones who pay. They start checking what type they actually received, or wrapping calls in try‑catch, or handling one subtype differently from the rest. The Liskov Substitution Principle asks a simple question about every subtype: can it stand in for its base type without anything breaking? This chapter treats inheritance as a contract about behavior rather than about method signatures. We will go through the ways that contract gets broken, and see how to redesign a hierarchy that no longer tells the truth.

In this chapter, we will cover the following topics:

- Understanding the Liskov Substitution Principle as a contract
- Recognizing common LSP violations
- Extracting capabilities into focused interfaces

By the end of this chapter, you will understand what substitutability means, and be able to spot subtypes that do not deliver what their base type promises. You will also know how to fix such a design: how to get rid of the type checks it forces on callers, and how to restructure a hierarchy that puts classes together which do not in fact share the same behavior.

## Understanding the Liskov Substitution Principle

The Liskov Substitution Principle (LSP) states that an object of a derived type should be usable wherever an object of the base type is expected without causing errors, invalid results, or subtype-specific handling. Code written against the base type should not need to know which concrete subtype it received. This idea is easiest to understand as a contract. A base type defines what callers are allowed to assume. A subtype may specialize how the contract is fulfilled, but it must not invalidate the promises made by the base type. A memorable substitutability analogy Imagine we are standing on a tower, in front of a wide open window. I hand you objects one by one, all of them derived from a base Bird type, and your job is to throw them out of the window. Bird defines a Fly method, so every object you get has one. Things go well and the birds fly away, until I hand you an ostrich. The example is silly, but it shows the Liskov Substitution Principle being broken. You are the method here. You accept Bird objects and you handle them according to what that type LSP in practice: Code that consumes a base type should assume nothing beyond what that base type promises, and every subtype must honor those promises and conventions.

promises, which is that they can fly. You do not know their concrete types, and you should not have to. Then one of them fails while being used exactly as the base type said it could be. The fix starts with recognizing that Bird is the wrong parameter type for this job. What you need is not birds but things that fly, so the right abstraction is an IFlyable interface. An ostrich would not implement it. Flying birds would, and so would a kite or a drone, and all of them would have been fine going out of that window. None of this means Bird should not exist. It is a useful type whenever we want to treat different birds uniformly. It just should not define a Fly method, because not every bird can fly. You may encounter another classic illustration of this principle: a Square class inheriting from a Rectangle class. Since a square is mathematically a rectangle with equal sides, it seems natural to model it that way. But if Rectangle exposes independent Width and Height setters, a Square subclass must override them so that setting one also changes the other, to preserve the

"equal sides" invariant. Code that sets width and expects height to remain unchanged, valid for any Rectangle, breaks when given a Square. This is the same substitutability problem you just saw with birds and flight. Recognizing LSP violations An LSP violation can originate in the subtype or in the abstraction it implements. Either way, the symptom is the same: callers can no longer rely on the base type's contract without knowing which concrete subtype they received. The following sections examine these failure modes individually, including subtypes that cannot honor inherited behavior, client code that checks concrete types, abstractions that expose capabilities some types cannot support, and subtypes that accept a narrower range of valid inputs than the base type. When a subtype breaks the base-type contract Consider an abstract Plane type that assumes every plane has fuel. It exposes MaxFuel and RemainingFuel properties and calculates the percentage of fuel remaining. A CargoPlane fits that design, but a ToyPlane does not. Because ToyPlane returns 0 for both fuel values, the inherited calculation divides a floating-point zero by zero and produces an invalid result. The original base type looks like this:

```csharp
public abstract class Plane
{
    public virtual int MaxFuel => 1000;
    public virtual int RemainingFuel => 1000;
    public float PercentOfRemainingFuel()
    {
        return ((float)RemainingFuel / MaxFuel) * 100;
    }
    public abstract string Land();
}
```

A conventional fueled subtype works as expected:

```csharp
public class CargoPlane : Plane
{
    public override int MaxFuel => 2000;
    public override int RemainingFuel => 2000;
    public override string Land()
    {
        return "Land on the airstrip near the cargo terminal";
    }
}
```

The difficulty appears when ToyPlane is forced into the same contract:

```csharp
public class ToyPlane : Plane
{
    public override int MaxFuel => 0;
    public override int RemainingFuel => 0;
    public override string Land()
    {
        return "Just don't hit the floor too hard.";
    }
}
```

Now a caller that only sees the Plane type can receive a ToyPlane and obtain an invalid result from behavior that the base class appears to guarantee. For a ToyPlane, an attempt to calculate the percent of remaining fuel will produce an invalid result. A caller receiving a Plane has the right to assume this method will work fine, yet they will be surprised when the Plane object turns out to actually be a ToyPlane.

```csharp
Plane plane = new ToyPlane();
var remainingFuel = plane.PercentOfRemainingFuel();
Console.WriteLine(remainingFuel);
```

This example of breaking LSP is a typical case of a subtype breaking the base class contract. The ToyPlane violates the contract that the Plane class defines.

There are several possible remedies. You could change the base type so that fuel is no longer part of the general Plane contract, decide that ToyPlane should not derive from Plane, or change the subtype implementation if the domain actually requires every plane in the system to have meaningful fuel values. The right choice depends on the application domain. Extracting capabilities into interfaces If both fueled and non-fueled planes are valid in the application, Plane should contain only behavior that is meaningful for every plane. Move the fuel-specific members into an IFuelable interface so that only types that support that capability implement it:

```csharp
public interface IFuelable
{
    int MaxFuel { get; }
    int RemainingFuel { get; }
}
public abstract class Plane
{
    public abstract string Land();
}
public class CargoPlane : Plane, IFuelable
{
    public int MaxFuel => 2000;
    public int RemainingFuel => 2000;
    public override string Land()
    {
        return "Land on the airstrip near the cargo terminal";
    }
}
public class ToyPlane : Plane
{
    public override string Land()
    {
        return "Just don't hit the floor too hard.";
    }
}
```

ToyPlane now remains a Plane but does not implement IFuelable, so it cannot be passed to code that requires fuel-related behavior. The type system prevents that misuse at compile time instead of allowing an invalid fuel calculation to surface later. Moving shared behavior out of inappropriate subtypes If the same fuel calculation would otherwise be copied into several fuelable classes, place it in a separate service that accepts the capability interface. This avoids duplicating business logic while keeping the abstraction honest:

```csharp
public class FuelCalculator
{
    public float GetPercentOfRemainingFuel(IFuelable fuelable)
    {
        return ((float)fuelable.RemainingFuel / fuelable.MaxFuel) * 100;
    }
}
```

The calculator can now work with a fueled plane, car, boat, or any other object that implements IFuelable. It does not need to know which concrete type it receives. Avoiding subtype checks in client code A common warning sign of an LSP problem is client code that checks for specific subtypes before using a base abstraction. For this example, assume IFuelable also declares an Attach(FuelHose hose) operation. A KeroseneLamp contains fuel, but it cannot accept the same hose as a vehicle. A tempting workaround is to detect KeroseneLamp inside FuelAll and run a special path:

```csharp
void FuelAll(List<IFuelable> fuelables, FuelHose hose)
{
    foreach (var fuelable in fuelables)
    {
        if (fuelable is KeroseneLamp)
        {
            var lamp = fuelable as KeroseneLamp;
            var adapter = new HoseAdapter(lamp);
            adapter.Attach(hose);
        }
        else
        {
            fuelable.Attach(hose);
        }
        hose.Fuel(fuelable);
    }
}
```

The client can no longer rely on the IFuelable abstraction alone; it must know that one concrete subtype behaves differently. That is a sign that the abstraction does not represent all of its implementations uniformly. It also creates an Open-Closed Principle problem because each new exceptional subtype may require another branch in the client. If using an adapter is valid business behavior, move that responsibility into KeroseneLamp so the client can continue to treat every IFuelable uniformly:

```csharp
public class KeroseneLamp : IFuelable
{
    public int MaxFuel => 3;
    public int RemainingFuel => 3;
    public void Attach(FuelHose hose)
    {
        var adapter = new HoseAdapter(this);
        adapter.Attach(hose);
    }
}
FuelAll can then return to the straightforward form promised by its signature:
    void FuelAll(List<IFuelable> fuelables, FuelHose hose)
{
    foreach (var fuelable in fuelables)
    {
        fuelable.Attach(hose);
        hose.Fuel(fuelable);
    }
}
```

When a type should not implement the broader interface If attaching a hose to a kerosene lamp is not valid in the domain, the more accurate design is to stop claiming that every fuel-containing object is hose-fuelable. Split the capabilities:

```csharp
public interface IFuelContainer
{
    int MaxFuel { get; }
    int RemainingFuel { get; }
}
public interface IFuelable : IFuelContainer
{
    void Attach(FuelHose hose);
}
public class KeroseneLamp : IFuelContainer
{
    public int MaxFuel => 3;
    public int RemainingFuel => 3;
}
```

This design preserves the common concept of storing fuel while preventing invalid operations on types that cannot support them. It also foreshadows the Interface Segregation Principle (ISP), where narrower interfaces allow each type to implement only the capabilities that make sense. Avoiding weakened postconditions and strengthened preconditions A subtype inherits the promises its base type made, and there are two main ways to break them. Weakening a postcondition means promising callers less than the base contract promises. If a base type guarantees that Find always returns an object, a subtype that returns null when it finds nothing has broken that guarantee. Callers written against the base type do not check for null, because they were told they never have to.

Strengthening a precondition is the mirror image: requiring more from callers than the base contract requires. Under LSP, a subtype should not introduce such a stricter requirement. Here is what that looks like in practice. Consider a BankAccount whose Withdraw method allows amounts below 10,000 without extra authorization. ChildrenAccount lowers that threshold to 1,000. A caller using a BankAccount reference may therefore expect a withdrawal of 5,000 to proceed without extra authorization, but that expectation no longer holds when the actual object is a ChildrenAccount.

```csharp
public class BankAccount
{
    public virtual void Withdraw(int amount)
    {
        if (amount < 10000)
        {
            Console.WriteLine($"Withdrawing amount: {amount}");
            return;
        }
        Console.WriteLine($"Withdrawing {amount} requires extra authorization");
    }
}
public class ChildrenAccount : BankAccount
{
    public override void Withdraw(int amount)
    {
        if (amount < 1000)
        {
            Console.WriteLine($"Withdrawing amount: {amount}");
            return;
        }
        Console.WriteLine($"Withdrawing {amount} requires extra authorization");
    }
}
```

Here, inheritance is being used only to vary a configuration value. A simpler design is to keep one BankAccount type and supply the threshold as configuration. If the application should  expose only valid account configurations, a static factory method can centralize the permitted values:

```csharp
public class BankAccount
{
    private readonly int _maxWithdrawalWithoutExtraAuthorization;
    private BankAccount(int maxWithdrawalWithoutExtraAuthorization)
    {
        _maxWithdrawalWithoutExtraAuthorization =
            maxWithdrawalWithoutExtraAuthorization;
    }
    public static BankAccount Create(BankAccountType type)
    {
        return type switch
        {
            BankAccountType.Adults => new BankAccount(10000),
            BankAccountType.Children => new BankAccount(1000),
            _ => throw new NotSupportedException("Unsupported account type.")
        };
    }
    public void Withdraw(int amount)
    {
        if (amount < _maxWithdrawalWithoutExtraAuthorization)
        {
            Console.WriteLine($"Withdrawing amount: {amount}");
            return;
        }
        Console.WriteLine(
            $"Withdrawing {amount} requires extra authorization");
    }
}
public enum BankAccountType
{
    Adults,
    Children
}
```

This removes an unnecessary inheritance relationship, and the substitution problem goes with it. Adding a new account type still means changing the factory, but that is where the creation decision belongs. Keeping that decision in one place means the rest of the code does not need subtype-specific knowledge. As discussed in Chapter 6, isolating the selection point is one practical way to contain unavoidable modification while applying the Open-Closed Principle.

# Chapter 8: Applying the Interface Segregation Principle

Interfaces are meant to create useful boundaries, but an interface can become a liability when it collects unrelated operations. Implementers are then forced to provide meaningless members and clients depend on capabilities they never use. The Interface Segregation Principle (ISP) keeps those contracts focused. This chapter examines interfaces as service boundaries, shows how polluted interfaces create artificial dependencies, and refactors broad contracts into smaller capabilities that better match the needs of their clients.

In this chapter, we will cover the following topics:

- Understanding the Interface Segregation Principle
- Thinking of interfaces as client-facing service boundaries
- Recognizing interfaces that force meaningless behavior
- Splitting broad interfaces by capability
- Relating ISP to LSP and SRP
- Avoiding interface pollution and unnecessary dependencies

By the end of this chapter, you will be able to recognize oversized or polluted interfaces, identify which clients actually need each capability, split contracts into focused abstractions, and explain how Interface Segregation complements both substitutability and single- responsibility design.

## Understanding the Interface Segregation Principle

The ISP states that clients of an interface should not be forced to depend on methods they do not use. In practice, this means shaping interfaces around cohesive client needs rather than collecting unrelated operations in one broad contract. Smaller interfaces are often the result, but size is not the goal by itself: an interface should be as broad as necessary to represent one coherent capability or client role. ISP is stated from the client's perspective, but both sides of the relationship matter. A client is code that receives or stores an object through the interface and calls its members; an implementer is the concrete type that fulfills the contract. Client dependencies reveal whether the interface exposes more than a caller needs, while awkward or meaningless implementations can reveal that the contract is too broad. Thinking of an interface as a service boundary A bank provides a useful analogy. A regular customer may interact with a clerk who can open accounts and exchange currencies. If the bank later adds a specialized valuables-storage service, every regular customer should not suddenly need to understand new security procedures. The bank can expose the specialist service through a separate role while keeping the ordinary customer-facing interface unchanged. The software equivalent is to avoid adding unrelated methods to a broadly used interface. Instead, create a second interface for the new capability and let only the appropriate concrete types implement it.

When an interface forces meaningless behavior Say we have an IPersonalDataAccess interface with a single Read method, and two classes implementing it. One reads the data from a text file. The other pulls it from a public census API. Both can do what the interface asks of them:

```csharp
public interface IPersonalDataAccess
{
    string Read(int id);
}
public class TextFilePersonalDataAccess : IPersonalDataAccess
{
    public string Read(int id)
    {
        var peopleLines = File.ReadAllLines("someFile.txt");
        return peopleLines.First(
            line => line.StartsWith($"{id} "));
    }
}
public class CensusPersonalDataAccess : IPersonalDataAccess
{
    // Simplified for brevity.
    // Production code should reuse
    // an injected HttpClient and use async/await.
    public string Read(int id)
    {
        var url = $"https://someCensusApi.gov/residents/{id}";
        var response = new HttpClient().GetStringAsync(url).Result;
        return JsonSerializer.Deserialize<CensusRecord>(response).PersonalData;
    }
}
```

Now the text-file implementation needs to support writing new data. If Write is added to IPersonalDataAccess, every implementation is forced to provide it.

```csharp
public interface IPersonalDataAccess
{
    string Read(int id);
    void Write(int id, string firstName, string lastName);
}
```

The census implementation has nowhere to write to because a public census source is read- only. A common but problematic workaround is to add a stub that throws NotImplementedException. The code then satisfies the interface syntactically, but the concrete type still cannot honor the behavior that the interface promises.

```csharp
public class CensusPersonalDataAccess : IPersonalDataAccess
{
    public string Read(int id)
    {
        var url = $"https://someCensusApi.gov/residents/{id}";
        var response = new HttpClient().GetStringAsync(url).Result;
        return JsonSerializer.Deserialize<CensusRecord>(response).PersonalData;
    }
    public void Write(int id, string firstName, string lastName)
    {
        throw new NotImplementedException();
    }
}
```

Forcing CensusPersonalDataAccess to implement Write causes two problems. The first is a violation of the Liskov Substitution Principle. Anyone holding an IPersonalDataAccess reference may call Write on it, because the interface promises the method is there. If the object behind it is CensusPersonalDataAccess, the call throws an exception. The broader design problem is a violation of the Interface Segregation Principle, and in this example it creates the conditions for the Liskov Substitution Principle failure. The interface bundles reading and writing as if every data source supported both capabilities. Because that assumption is false, one implementation cannot honor the full contract. Splitting the interface by capability The issue is easily solved if we separate reading and writing into focused abstractions:

```csharp
public interface IPersonalDataReader
{
    string Read(int id);
}
public interface IPersonalDataWriter
{
    void Write(int id, string firstName, string lastName);
}
```

The text-file implementation can provide both capabilities, while the census implementation provides only reading:

public class TextFilePersonalDataAccess :

```csharp
IPersonalDataReader, IPersonalDataWriter
{
    private const string FilePath = "someFile.txt";
    public string Read(int id)
    {
        var peopleLines = File.ReadAllLines(FilePath);
        return peopleLines.First(
            line => line.StartsWith($"{id} "));
    }
    public void Write(int id, string firstName, string lastName)
    {
        var newLine = $"{id} {firstName} {lastName}";
        File.AppendAllLines(FilePath, new[] { newLine });
    }
}
public class CensusPersonalDataAccess : IPersonalDataReader
{
    public string Read(int id)
    {
        var url = $"https://someCensusApi.gov/residents/{id}";
        var response = new HttpClient().GetStringAsync(url).Result;
        return JsonSerializer.Deserialize<CensusRecord>(response).PersonalData;
    }
}
```

Interface segregation does not require a separate concrete class for every capability.

TextFilePersonalDataAccess can implement both IPersonalDataReader and IPersonalDataWriter because it supports both. The benefit is that each client can depend only on the focused interface it actually needs. A client that only prints data can now depend on IPersonalDataReader instead of on a larger abstraction:

```csharp
public class PersonalDataPrinter
{
    private readonly IPersonalDataReader _personalDataReader;
    public PersonalDataPrinter(IPersonalDataReader personalDataReader)
    {
        _personalDataReader = personalDataReader;
    }
    public void Print(int id)
    {
        var personalData = _personalDataReader.Read(id);
        Console.WriteLine($"Data of the person with id {id}:");
        Console.WriteLine(personalData);
    }
}
```

The result is more precise. Implementers are no longer forced to provide operations they cannot support, and clients no longer depend on methods they never use. There is also no way for a client to call a method that will fail on them, because a class that cannot write does not have a write method to call in the first place. How ISP relates to LSP and SRP ISP, LSP, and SRP often reinforce one another, but they ask different questions. When an oversized interface forces a type to provide a stub that throws, the broad contract is an ISP problem and the throwing implementation creates an LSP problem because callers cannot safely rely on the interface. An ISP problem can also contribute to an SRP problem if a concrete class is made responsible for unrelated capabilities simply to satisfy a broad contract, but that is not automatic. SRP asks whether responsibilities that change together belong together; ISP asks whether a client depends on operations it does not need. Table 8.1 separates these questions.

A simple stack data structure provides a useful example of how SRP and ISP do not always point in the same direction. A stack class has Push and Pop, and both belong to one responsibility, so SRP has no objection to keeping them together. A client that only ever pushes, however, may benefit from a narrower interface that omits Pop, particularly when different client roles need different capabilities. That does not mean every two-method interface should be split. Segregation has a cost: more abstractions to name, document, and maintain. A split is worthwhile when it clarifies client dependencies or prevents unsupported behavior, not merely to minimize the number of methods in an interface. The point is that SRP and ISP ask different questions, and a design satisfying one can still fall short of the other. # Chapter 9: Applying the Dependency Inversion Principle

Almost no class works in isolation. Classes have dependencies, meaning other types they rely on. A class that presents customer data may depend on a service that fetches customers, another one that manages orders, and yet another that aggregates and formats the data. This is perfectly normal, and it is often the result of good practices: refactoring classes toward a single responsibility and toward being more focused. The problem appears when the relationships between classes become rigid. If our class needs customer data and depends on one very specific class that fetches it, it may cause problems in the future. A relationship this rigid means we cannot swap the implementation easily and safely, either when the requirements change or for the purposes of testing. This is what the Dependency Inversion Principle is about, and it is the subject of this chapter. This principle, abbreviated as DIP, states the following: High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions. That is the official definition, but it may be easier to think of it in a simplified form: do not depend on concrete classes, depend on abstractions instead.

## Understanding the Dependency Inversion Principle

The Dependency Inversion Principle is about the direction of dependencies. High-level code should not be tightly coupled to low-level implementation details. Both should depend on abstractions. Likewise, abstractions should not be shaped by the incidental details of one concrete implementation; the details should conform to the abstraction. Here, high-level code expresses the application's main behavior, while low-level code handles implementation details such as accessing databases, external APIs, or file systems. Replacing a concrete delivery service with an abstraction To understand it better, let's consider a real-life example. DIP in one sentence: Do not depend directly on concrete implementation classes when the behavior may vary; depend on an appropriate abstraction instead.

> **Note**
Imagine that you own a small online bookstore. You sell books to customers in your country, but you don't have your own delivery fleet, so you rely on another company to deliver the orders. You find a company called FastWheels that fits your current needs. They offer decent prices and specialize in delivering small items within your country. In code, your OnlineBookstore class could depend directly on a FastWheels class and call its DeliverSmallItem method to ship books to customers. The problem is that FastWheels is a concrete, low-level dependency. What happens if you expand your business and start shipping internationally? Or if you decide to sell furniture as well as books? FastWheels may no longer meet your needs. The OnlineBookstore class is now tightly coupled to FastWheels. A change in the delivery service becomes a change that you need to make in the bookstore's code as well.

```csharp
class OnlineBookstore
{
    private readonly FastWheels _fastWheelsService;
    public OnlineBookstore(FastWheels fastWheelsService)
    {
        _fastWheelsService = fastWheelsService;
    }
    public void Send(int bookId, int customerId)
    {
        var package = /* create package with book */;
        var address = /* get customer's address */;
        _fastWheelsService.DeliverSmallItem(package, address);
    }
}
```

For example, if we decide to change the FastWheels type to something else, the code calling the DeliverSmallItem method may stop compiling—because the new type's method may be called differently. Adjusting the code in this small class may not be difficult, but imagine it is larger and uses FastWheels in dozens of places. Or even worse, imagine dozens of classes depending on FastWheels, spread across our entire codebase. Replacing references to FastWheels would

 require changes across all of those classes, creating a lot of work and increasing the risk of bugs. We would also need to update dozens or hundreds of tests. So how can we resolve this? To understand it, let's go back to the real-life analogy, which presents a similar problem: a bookstore depending on a very specific delivery company. Instead of working directly with FastWheels, we could use a company called, let's say, AnyDelivery that arranges deliveries for us. We simply tell them what needs to be delivered and where, and they find a suitable delivery company. In other words, they worry about details, and we only need to tell them what we need.

AnyDelivery is an abstraction over the delivery service. We can use the same approach in code.

Instead of depending on the concrete FastWheels type, we can depend on an IDelivery interface. The OnlineBookstore class does not need to know which specific type implements it. Initially, that type can be FastWheels. When our delivery needs change, we can pass a different implementation of IDelivery to the OnlineBookstore constructor. We don't need to change the OnlineBookstore code or its tests.

Only the code that creates the object needs to be adjusted, and that change has a much smaller impact. Let's see it in code:

```csharp
public interface IDelivery
{
    void Deliver(Package package, Address address);
}
class OnlineBookstore
{
    private readonly IDelivery _deliveryService;
    public OnlineBookstore(IDelivery deliveryService)
    {
        _deliveryService = deliveryService;
    }
    public void Send(int bookId, int customerId)
    {
        var package = /* create package with book */;
        var address = /* get customer's address */;
        _deliveryService.Deliver(package, address);
    }
}
```

```csharp
class FastWheels : IDelivery
{
    public void Deliver(Package package, Address address)
    {
        // FastWheels-specific implementation.
    }
}
```

OnlineBookstore now depends on what it needs rather than on who currently provides it.

Another IDelivery implementation can be supplied without modifying OnlineBookstore. Keeping abstractions independent from implementation details The second part of the DIP definition says that abstractions should not depend on details, and details should depend on abstractions. In this context, an abstraction is typically an interface or abstract class that defines what should be done without specifying how. A detail is a concrete implementation that defines how it is done. For example, suppose IPeopleDataReader has two implementations: one reads data from an Excel file, and the other from cloud storage.

```csharp
public interface IPeopleDataReader
{
    List<Person> GetAll();
}
public class CloudSourcedPeopleDataReader : IPeopleDataReader
{
    public List<Person> GetAll()
    {
        // Read from cloud storage.
    }
}
public class ExcelSourcedPeopleDataReader : IPeopleDataReader
{
    public List<Person> GetAll()
    {
        // Read from Excel.
    }
}
```

Suppose the Excel implementation needs a fileName parameter. In that case, we should not add it to the interface. Doing so would also force the cloud implementation to accept a parameter that has no meaning for it. This would be a case where a change in an implementation detail affects the abstraction, which would break DIP. The fileName is a detail specific to the Excel implementation, so it should be handled there. For example, we could pass it to the ExcelSourcedPeopleDataReader constructor instead. The interface should only change when the abstraction itself needs to change, not because one of its implementations has new requirements. Dependency Inversion and Dependency Injection are not the same Dependency Inversion and Dependency Injection sound similar, but they describe different ideas. DIP is a design principle about depending on abstractions. Dependency Injection is a construction pattern in which a class receives its dependencies from outside instead of creating them internally. Let's compare two pieces of code:

```csharp
class OnlineBookstore
{
    private readonly IDelivery _deliveryService;
    public OnlineBookstore()
    {
        _deliveryService = new FastWheels();
    }
}
```

In this code, the OnlineBookstore class creates the dependency it needs itself. This means it must be aware of the implementation details of the FastWheels class, namely how its objects are created. This may seem like a minor problem in this example, but creating real-world objects is often much more complicated. It is not the responsibility of OnlineBookstore to know how to create a FastWheels object.

It's better to use Dependency Injection and inject this object into the class through its constructor.

```csharp
class OnlineBookstore
{
    private readonly IDelivery _deliveryService;
    public OnlineBookstore(IDelivery deliveryService)
    {
        _deliveryService = deliveryService;
    }
}
```

This way, the class simply declares what it needs without concerning itself with the specific type it will receive or how it should be created. If we use Dependency Injection, this class does not need to know about FastWheels or any other type implementing IDelivery. We can modify those implementations independently, as long as they continue to follow the interface. Dependency Injection also allows us to switch between different implementations without modifying the OnlineBookstore class. An application may have several types implementing IDelivery, and we may want to choose between them based on configuration or user decisions. With Dependency Injection, we can provide the appropriate implementation at runtime. It also makes the class easier to test. When testing OnlineBookstore, we can inject a mock of IDelivery instead of using a real delivery service. If the class creates FastWheels itself, we cannot easily replace it with a mock. As a general guideline, inject dependencies instead of creating them inside the class that uses them. To summarize: Dependency Inversion is a principle that says a type should depend on abstractions rather than concrete implementations. Dependency Injection is a technique where a class receives the dependencies it needs instead of creating them itself. They work together well, but they are not the same thing. Creating dependencies only when runtime data is available Constructor injection is usually the clearest way to provide a dependency, but what if the dependency cannot be created until runtime? Consider a WeatherDataPrinter class that asks the user to select a country and then retrieves the weather for that country. The WeatherDataAccess class requires the country in its constructor, so we cannot create it upfront and inject it into WeatherDataPrinter's constructor. The required value simply is not available yet.

```csharp
public class WeatherDataPrinter
{
    public void Print()
    {
        Console.WriteLine("Please select a country:");
        var country = Console.ReadLine();
        var weatherDataAccess = new WeatherDataAccess(country); //we need country
        to create this
            var weatherData = weatherDataAccess.GetCurrentWeather();
        Console.WriteLine($"The weather in {country} is: {weatherData}");
    }
}
```

In the code above, we create WeatherDataAccess directly inside the Print method, but this makes WeatherDataPrinter depend on the concrete WeatherDataAccess type, which violates the Dependency Inversion Principle. We still need to create the dependency inside the method, because this is when we know the value of the country variable—so how can we avoid the concrete dependency? We can use a factory.

```csharp
public interface IWeatherDataAccess
{
    string GetCurrentWeather();
}
public interface IWeatherDataAccessFactory
{
    IWeatherDataAccess Create(string country);
}
public class WeatherDataAccessFactory : IWeatherDataAccessFactory
{
    public IWeatherDataAccess Create(string country)
    {
        return new WeatherDataAccess(country);
    }
}
public class WeatherDataPrinter
{
    private readonly IWeatherDataAccessFactory _factory;
    public WeatherDataPrinter(IWeatherDataAccessFactory factory)
    {
        _factory = factory;
    }
    public void Print()
    {
        Console.WriteLine("Please select a country:");
        var country = Console.ReadLine();
        var weatherDataAccess = _factory.Create(country);
        var weatherData = weatherDataAccess.GetCurrentWeather();
        Console.WriteLine($"The weather in {country} is: {weatherData}");
    }
}
```

Now WeatherDataPrinter depends on IWeatherDataAccessFactory rather than WeatherDataAccess. It can call the factory when the country is known and create the dependency only when it is needed. The factory still depends on the concrete WeatherDataAccess, but this dependency is isolated in one place. The rest of the application can work with the abstractions. This approach also makes the code easier to test. We can provide a mock IWeatherDataAccessFactory and control which IWeatherDataAccess the printer receives.

So, when a dependency cannot be created upfront because it requires runtime data or other conditions, a factory can help us keep the consuming class dependent on an abstraction while creating the concrete object only when needed. Refactoring a concrete data-provider dependency Let's see another example. PopulationStatsPrinter creates a TextFilePopulationDataProvider itself. That ties the two classes together tightly. There is no way to hand the printer a different data source, whether because the requirements change or because a test needs one. And the printer has to know how the provider is built, down to what its constructor expects:

```csharp
public class PopulationStatsPrinter
{
    public void PrintAverageAge()
    {
        List<Person> people =
            new TextFilePopulationDataProvider("people.txt").GetAll();
        var averageAge = people.Average(person => person.Age);
        Console.WriteLine($"The average age is {averageAge}.");
    }
}
```

A better approach would be to introduce an abstraction and inject it:

```csharp
public interface IPopulationDataProvider
{
    List<Person> GetAll();
}
public class TextFilePopulationDataProvider : IPopulationDataProvider
{
    private readonly string _filePath;
    public TextFilePopulationDataProvider(string filePath)
    {
        _filePath = filePath;
    }
    public List<Person> GetAll()
    {
        // Read and process the file.
    }
}
public class PopulationStatsPrinter
{
    private readonly IPopulationDataProvider _populationDataProvider;
    public PopulationStatsPrinter(
        IPopulationDataProvider populationDataProvider)
    {
        _populationDataProvider = populationDataProvider;
    }
    public void PrintAverageAge()
    {
        var people = _populationDataProvider.GetAll();
        var averageAge = people.Average(person => person.Age);
        Console.WriteLine($"The average age is {averageAge}.");
    }
}
```

Let's summarize what changed and why it made the code better. 

Previously, PopulationStatsPrinter depended directly on TextFilePopulationDataProvider and created it inside the PrintAverageAge method. This made it difficult to switch to another data source or use a mock without modifying PopulationStatsPrinter.

Now, the class depends on the IPopulationDataProvider abstraction, and the concrete implementation is injected through the constructor. We can easily provide another implementation, such as one that reads data from a SQL database or a cloud service, without changing PopulationStatsPrinter. Unit testing is also easier because we can inject a mock of IPopulationDataProvider.

The classes are now loosely coupled. The interface connects them, making the code easier to maintain and modify. There is one more dependency here that we haven't addressed: PopulationStatsPrinter uses the static Console class to communicate with the user. This also goes against the Dependency Inversion Principle because the class is tightly coupled to a specific way of communicating with the user. If we wanted to use a different way of communicating with the user, or mock it for testing, we would not be able to do so without modifying PopulationStatsPrinter. We will not address this problem now. In Chapter 10, we will take a closer look at static methods and the problems they can cause, including how they can break the Dependency Inversion Principle.

# Chapter 10: Static methods and dependencies

Static methods are tempting. A static method belongs to the class itself rather than to any of its instances, so there is nothing to create and nothing to pass around. Reach for the class name and the method is there. Static fields and properties work the same way, except that they hold state shared by the whole application. Sometimes using them is the right choice. Sometimes it costs us more than it saves. This chapter is about telling the two cases apart. A static call is a dependency that never shows up in a constructor or a signature. Nothing declares it, so nothing can replace it. When the behavior behind that call needs to change, or needs to behave differently in a test, we find that we have no way in.

In this chapter, we will cover the following topics:

- Deciding when a method should be static
- Distinguishing private helpers from public dependencies
- Understanding why public static methods can weaken substitution and testability
- Wrapping static framework APIs when behavior must be controlled
- Recognizing hidden dependencies and global state
- Making the dependency graph explicit through constructors

By the end of this chapter, you will be able to decide when static methods are appropriate, recognize public static members that hide replaceable dependencies, wrap static framework APIs when tests require control, identify obscured dependency graphs and global state, and refactor classes so that required collaborators are explicit and substitutable.

## Static methods at a glance

A static method belongs to the type rather than to any particular object. Since there is no instance behind the call, a static method cannot reach the instance fields or properties of its class. Whatever it needs has to come in through its parameters, or from static fields, which belong to the type as well. An operation such as Min depends only on the values passed to it. It uses no state from the class it lives in, so nothing stops it from being static:

```csharp
public static class Math
{
    public static int Min(int a, int b)
    {
        return a < b ? a : b;
    }
}
```

The Add method of a list makes a good contrast. It is not static, and it could not be, because it works on the instance's own items and count:

```csharp
class List<T>
{
    private T[] _items = [];
    //Resizing omitted for brevity
    public int Count { get; private set; }
    public void Add(T item)
    {
        _items[Count] = item;
        ++Count;
    }
}
```

## Deciding when a method should be static

Whether a method should be static depends not only on whether it uses instance state, but also on whether callers may need to replace or control its behavior. Private methods We know that a method using none of the class state can be made static. The question is whether it should be. For private methods, the answer is often yes. Making such a method static states plainly that it does not touch instance data, so anyone reading it knows from the signature alone that the object's state is not part of the picture. Everything the method works with is either in its body or in its parameters, and there is no need to go looking at what fields the class happens to have. Why public static methods need more caution Making public methods static may be a bad idea. Let's understand why with the following piece of code.

```csharp
public class DataAccess
{
    public List<int> GetData()
    {
        // connects to a DB and reads the data
    }
}
public class DataProcessor
{
    private readonly DataAccess _dataAccess;
    public DataProcessor(DataAccess dataAccess)
    {
        _dataAccess = dataAccess;
    }
    public int CalculateSum()
    {
        return _dataAccess.GetData().Sum();
    }
}
```

Here is a DataAccess class with a public GetData method. It opens a connection to an SQL database and reads the data from there. The method uses no instance data, so technically it could be made static.

DataProcessor depends on it. It receives a DataAccess object through the constructor and stores it in a field. As we already know, this goes against the Dependency Inversion Principle. DataProcessor should depend on an abstraction rather than a concrete type. As it stands, switching to a different way of reading the data, from a file or an API, would mean changing DataProcessor itself, its constructor at the very least. Testing has the same problem. A unit test should not be opening a real database connection, and right now there is no way to substitute a mock. Depending on an abstraction fixes both. In C#, that means an interface.

```csharp
public interface IDataAccess
{
    List<int> GetData();
}
public class DataAccess : IDataAccess
{
    public List<int> GetData()
    {
        // connects to a DB and reads the data
    }
}
public class DataProcessor
{
    private readonly IDataAccess _dataAccess;
    public DataProcessor(IDataAccess dataAccess)
    {
        _dataAccess = dataAccess;
    }
    public int CalculateSum()
    {
        return _dataAccess.GetData().Sum();
    }
}
```

Now DataAccess implements the IDataAccess interface, and DataProcessor is given an object of that interface rather than a concrete class. It has no idea what it actually received. It might be the DataAccess object talking to an SQL database, or something reading from a file, or a mock used in a test. Any of them can be swapped in without touching DataProcessor, and the two classes now communicate only through the interface. This is a good design. The two classes are no longer coupled to each other, the implementation can be replaced whenever the requirements call for it, and testing DataProcessor is straightforward, since a mock goes in exactly where the real thing would. Now let's go back to static methods. We said earlier that GetData uses no instance state, so it could be made static. Say we decide to do exactly that.

```csharp
public class DataAccess
{
    public static List<int> GetData()
    {
        // connects to a DB and reads the data
    }
}
```

The call site has to change now. A static method is called on the type rather than on an object, so instead of _dataAccess.GetData() we write DataAccess.GetData(). The interface reference is gone, and with it the object that used to be passed in.

```csharp
public class DataProcessor
{
    public int CalculateSum()
    {
        return DataAccess.GetData().Sum();
    }
}
```

With that, everything the Dependency Inversion Principle gave us is gone. There is no way to switch the implementation to something else, and no way to substitute a mock in a test. The code is bound to this one class. There is more. DataAccess can no longer implement IDataAccess at all. Methods implementing an interface are implicitly virtual, and a virtual method cannot be static. The runtime uses the type of an object to decide which implementation of a virtual method to invoke, and a static method is not invoked on an object in the first place. It is invoked on the type. So a method can be virtual or static, never both. Which means DataAccess can no longer be used polymorphically. That is the reason to avoid making public methods static. A static method always behaves the same way, and there is no object to call it on, so there is no way to substitute different behavior. The code gets rigid, and testing gets hard, because static methods are difficult to replace through ordinary interface-based mocking. So a public static method that represents replaceable behavior deserves caution. If there is any chance the implementation will need to be swapped or mocked, making it static takes that option away. Figure 10.1: Comparison between runtime dispatch for virtual and static method calls Let's see the few cases where a public static method is the right call.

When public static methods make sense A public method can safely be made static when we always want the same implementation and will never replace it with another one. That includes replacing it with a mock. If there is any chance we will want to mock the method, it should not be static. Simple as that sounds, it rules out most methods. Anything implementing a business requirement may need a different implementation eventually. Methods that provide data are the clearest case: reading from a database can become reading from a file or from cloud storage, and a console application can become one with a graphical interface. On top of that, methods that fetch data have to be mocked in unit tests. We do not want tests hitting a real data source or a real user interface, because then we no longer control what the test does. So which methods will never need different behavior and never need mocking? The Math class is a good example. Basic mathematical operations do not have alternative implementations, because mathematics does not change, and there is no reason to mock them in a test. Running the real implementation is exactly what we want. The same goes for simple text processing. A method that strips whitespace from a string takes a value, transforms it, and returns the result. There is no second way of doing it that we might want to swap in later, and a test has no reason to fake it, since running the real thing is fast and gives the same answer every time.

Math is a built-in .NET type that is static and should be. Not every static member of the standard library is such a good decision, though. Let's see how to deal with that. Wrapping static framework APIs Sometimes a static method we need comes from the standard library or an external package, and we have no say in the matter. DateTime.Now in C#, which returns the current date and time, is the classic example. It is static, so it cannot be replaced through ordinary interface- based mocking, and that becomes our problem as soon as we write a method that depends on it. Consider a method that describes the current day:

```csharp
string GetCurrentDayDescription()
{
    DateTime today = DateTime.Now;
    return $"Today is {today.DayOfWeek}";
}
```

The output of this method changes with the clock. Run it on Monday and it says one thing, run it on Tuesday and it says another. A unit test has to produce the same result every time it runs, so a test for this method would need to fix what the current date is. That means replacing  DateTime.Now with something we control, and we cannot do it, because a static property cannot be replaced through ordinary interface-based mocking. The usual way out is a wrapper. We define our own IDateTime interface and a class implementing it, whose job is to provide the same value the static property does, only in a non- static way that can be mocked. Here are the interface and the wrapper:

```csharp
interface IDateTime
{
    DateTime Now { get; }
}
class DateTimeWrapper : IDateTime
{
    public DateTime Now
    {
        get
        {
            return DateTime.Now;
        }
    }
}
```

With the wrapper in place, a class that needs the current time takes an IDateTime in its constructor instead of reaching for DateTime.Now directly. In production it gets the real wrapper and behaves exactly as before. In a test it gets a mock returning a fixed date, so the result is the same on every run. The dependency on the clock is also visible now. It sits in the constructor, where anyone reading the class can see it, rather than hiding inside a method body.

TimeProvider, introduced in .NET 8, offers a built-in, testable alternative to DateTime.Now for newer projects. That said, DateTime.Now is likely to remain common in existing codebases for a long time. It is also only one example of a static dependency that needs wrapping. File and Console raise the same problem, and most static dependencies have no framework-provided alternative, so knowing how to wrap them yourself is a practical skill.

## Keeping the dependency graph visible

We saw how a static method can lead to breaking the Dependency Inversion Principle. That is part of a larger problem, sometimes called obscuring the dependency graph. A dependency graph shows how the classes in a system depend on one another. It sounds abstract, but it is a simple idea and a useful one, and it matters more than it might seem that we can see the full graph for a class without missing any part of it. Imagine joining a project and trying to find your way around the code. There is a BankAccount class that looks complicated, and it is not obvious how it works. To see it in action, you write a simple unit test.

```csharp
public class BankAccountTests
{
    [Test]
    public void TransferTo_ShallRemoveAmountFromOneAccount_AndAddItToAnother()
    {
        var bankAccount1 = new BankAccount();
        bankAccount1.AddFunds(1000);
        var bankAccount2 = new BankAccount();
        bankAccount1.TransferTo(bankAccount2, 200);
        Assert.That(bankAccount1.Balance, Is.EqualTo(800));
        Assert.That(bankAccount2.Balance, Is.EqualTo(200));
    }
}
```

You expect this test to pass, as nothing seems suspicious in the code. However, when you run the test, it fails with a complicated error message. After some investigation and asking a senior team member, you learn that before calling the TransferTo method, you must initialize a TransferServiceManager class.

You update your test to include this initialization:

```csharp
public class BankAccountTests
{
    [Test]
    public void TransferTo_ShallRemoveAmountFromOneAccount_AndAddItToAnother()
    {
        TransferServiceManager.Initialize();
        var bankAccount1 = new BankAccount();
        bankAccount1.AddFunds(1000);
        var bankAccount2 = new BankAccount();
        bankAccount1.TransferTo(bankAccount2, 200);
        Assert.That(bankAccount1.Balance, Is.EqualTo(800));
        Assert.That(bankAccount2.Balance, Is.EqualTo(200));
    }
}
```

But running the test again results in another exception. After another round of questions, you are told that you must also initialize InternalServiceQueue. Only after adding this line does the test finally pass:

```csharp
public class BankAccountTests
{
    [Test]
    public void TransferTo_ShallRemoveAmountFromOneAccount_AndAddItToAnother()
    {
        InternalServiceQueue.Initialize();
        TransferServiceManager.Initialize();
        var bankAccount1 = new BankAccount();
        bankAccount1.AddFunds(1000);
        var bankAccount2 = new BankAccount();
        bankAccount1.TransferTo(bankAccount2, 200);
        Assert.That(bankAccount1.Balance, Is.EqualTo(800));
        Assert.That(bankAccount2.Balance, Is.EqualTo(200));
    }
}
```

It takes over twenty seconds to run, but a senior colleague tells you that is normal, because this is how long those services take to initialize. Before we get to how bad this design is, one thing is worth saying. The example is simplified, but the problem it shows is not. Code that behaves like this turns up in real projects, and most developers run into it sooner or later.

So what is wrong here? The class lies, or at least it does not tell the whole truth. BankAccount needs those services to work, and it says so nowhere. It presents itself as something we can create and use right away, which is exactly what the first version of the test assumed, and that turned out to be false. Those services are dependencies of this class, and they are not declared in the constructor. That leaves us no way of knowing they exist without reading the implementation. This is what obscuring the dependency graph means. The graph for BankAccount includes those two types, and nothing on the surface of the class admits it. Why hidden dependencies create fragile code Objects should be ready to use immediately after you create them, without requiring any secret initialization steps or special method calls. If you find yourself needing to perform some magic setup or call a particular method to make an object work, your design is flawed. The only setup required before using an object should happen in its constructor. If a type needs certain things to function, it should request them in the constructor and nowhere else. When dependencies are hidden, it becomes easy to introduce serious bugs. For example, if you refactor your code and accidentally swap the order of two initialization lines, your tests may start failing. After spending time diagnosing the issue, you might discover that one dependency must be initialized before the other. This means the actual dependency graph is more complex than it appears in the code, and this lack of clarity can lead to mistakes. But what does it have to do with static members? Well, static members are globally reachable through their type name. That reachability makes it easy for code anywhere in the application to acquire a dependency without declaring it in a constructor or method signature. Look at the class below. It doesn't take anything in its constructor, so from the outside it looks like it depends on nothing at all. Then we open a method body and find InternalServiceQueue being called. The class depends on it, and nothing about its public surface says so:

```csharp
class SomeClass
{
    public void SomeMethod()
    {
        InternalServiceQueue.Initialize();
    }
}
```

If a class exposes a public static method, any code in your project can call this method, creating a hidden dependency. If methods are not static, you need an instance of the type to call them. 

This means you must provide the instance to the dependent class, typically through a constructor or method parameter, making the dependency explicit and ensuring the code will not compile unless the dependency is supplied.

```csharp
class SomeClass
{
    private readonly IInternalServiceQueue _internalServiceQueue;
    public SomeClass(IInternalServiceQueue internalServiceQueue)
    {
        _internalServiceQueue = internalServiceQueue;
    }
    public void SomeMethod()
    {
        _internalServiceQueue.Initialize();
    }
}
```

A class that declares no dependencies may still have one. If some other type exposes an instance in a public static field, any code can reach it, and the dependency exists without ever appearing in a constructor. That is what makes public static fields dangerous. They create global state, meaning data reachable from any point in the application, and anything can come to depend on it without saying so. It is the same problem we saw with static methods, only now it applies to data rather than behavior. The following code demonstrates how a hidden dependency can be introduced through a public static field:

```csharp
class BankAccount
{
    public int Balance { get; private set; }
    public void AddFunds(int amount)
    {
        SomeOtherType.TransferServiceManager.SomeNonStaticMethod();
    }
}
class SomeOtherType
{
    public static ITransferServiceManager TransferServiceManager;
}
```

If you use a public static field like TransferServiceManager, any code can access it at any time, creating a hidden dependency that is not declared in the constructor or interface of your class. The point to remember is that public static methods and public static fields can both hide dependencies, and in many cases the code is clearer when those dependencies are explicit.

## Making dependencies explicit

To solve the problem of static methods obscuring the dependency graph, declare dependencies explicitly. If BankAccount needs TransferServiceManager, it should require it as a constructor parameter. If TransferServiceManager needs InternalServiceQueue, it should require it too. If you forget to provide a dependency, you will get a compilation error, not a runtime failure or mysterious test failure. You won't need to rely on secret knowledge or special lines of code. Initialization methods that must be called before an object becomes usable are another form of hidden prerequisite. Prefer constructing objects in a valid, ready-to-use state and require essential collaborators through constructors. Constructor injection also creates a natural testing seam. Instead of initializing real infrastructure, a unit test can pass controlled test doubles and exercise BankAccount in isolation. After removing the static initialization methods and making all dependencies explicit, the code becomes easier to understand and maintain. The following code shows the improved approach:

```csharp
class BankAccount
{
    private readonly ITransferServiceManager _transferServiceManager;
    public BankAccount(ITransferServiceManager transferServiceManager)
    {
        _transferServiceManager = transferServiceManager;
    }
    public int Balance { get; private set; }
    public void AddFunds(int amount)
    {
        // imagine a lot of complicated code
    }
    public void TransferTo(BankAccount other, int amount)
    {
        // imagine a lot of complicated code
    }
}
class TransferServiceManager : ITransferServiceManager
{
    private readonly IInternalServiceQueue _internalServiceQueue;
    public TransferServiceManager(IInternalServiceQueue internalServiceQueue)
    {
        _internalServiceQueue = internalServiceQueue;
    }
}
```

Now BankAccount states that it needs an ITransferServiceManager, which in turn states that it needs an IInternalServiceQueue. Nothing is hidden. Passing dependencies through the constructor brings another benefit: we can hand the class whatever we like, including a mock. Let's see how the test could look now:

```csharp
using NUnit.Framework;
using Moq;
[TestFixture]
public class BankAccountTests
{
    [Test]
    public void TransferTo_ShallRemoveAmountFromOneAccount_AndAddItToAnother()
    {
        var bankAccount1 = new BankAccount(
            new Mock<ITransferServiceManager>().Object);
        bankAccount1.AddFunds(1000);
        var bankAccount2 = new BankAccount(
            new Mock<ITransferServiceManager>().Object);
        bankAccount1.TransferTo(bankAccount2, 200);
        Assert.That(bankAccount1.Balance, Is.EqualTo(800));
        Assert.That(bankAccount2.Balance, Is.EqualTo(200));
    }
}
```

Now the test uses mocks instead of real infrastructure. Remember that earlier, this test took twenty seconds to pass? That was the real services initializing. With a mock in their place, the test finishes immediately. Unit tests should generally avoid real external dependencies. A unit test tests one class in isolation, and once the real dependencies are in play, they are being tested too. At that point it is no longer a unit test. It also makes the tests slow, as with a real database connection. And it can cost money. It is not unheard of for a test suite to connect to real cloud services instead of mocking them, and every run adds to the bill. With the current code, there are no Initialize methods to remember. No test performs real initialization, so nothing takes twenty seconds. A BankAccount object works as soon as it is created, and it cannot be created without its dependencies, because the code would not compile. This code no longer lies. It tells us the truth, the whole truth, and nothing but the truth.

The BankAccount example demonstrated how global initialization obscures the dependency graph and how constructor injection makes required collaborators visible and mockable. # Chapter 11: Designing smaller classes

A class can begin as a convenient home for a small amount of related behavior and slowly become the place where every new requirement is added. Over time it accumulates unrelated data, dependencies, business rules, low-level utilities, and special cases, until even a small change requires understanding code that has nothing to do with the task. That is why smaller classes are worth aiming for. A class that fits in one's head can be read, changed, and tested without dragging everything around it into the picture. But not at any cost. A large class is a warning sign, not an automatic failure, and splitting one apart to get under some line limit does more harm than leaving it alone. The goal is to find the cohesive responsibilities inside it and give each of them a home of its own. This chapter shows how to recognize those boundaries and refactor toward smaller classes without inventing abstractions that do not need to exist.

In this chapter, we will cover the following topics:

- Reviewing class-design fundamentals
- Understanding the problems caused by oversized classes
- Recognizing when a large class is nevertheless cohesive
- Avoiding superficial techniques for making code look shorter
- Finding class boundaries through data usage and dependencies
- Grouping behavior that changes together
- Separating high-level and low-level responsibilities
- Avoiding unnecessary class proliferation

By the end of this chapter, you will be able to recognize when a class has accumulated too many responsibilities, distinguish justified size from god-class design, use naming, data usage, change patterns, and abstraction levels to identify natural class boundaries, and refactor a larger class into focused, testable, reusable collaborators.

## Reviewing class-design fundamentals

Before going further, a quick reminder of the terms we will be using. In object-oriented programming, an object combines data with the behavior that operates on that data. A Person object may hold a name and a date of birth, and know how to calculate its own age. An Address object may hold a street, a number, and a city, and format them into a single line for a label. A Person can in turn hold a collection of Address objects. Building an application out of smaller concepts like these is what lets us avoid writing it as one large block of code. A class is the definition from which those objects are created. It describes what data and what methods the instances will have. Person is the class, and the objects created from it are its instances, so John and Jane are two Person instances with different names and different dates of birth, sharing the same structure and the same behavior. Some classes represent things from the real world, such as people, addresses, or orders. Others represent technical concepts, such as a database connector, a repository, a text reader, or a randomizer. Public and private members Classes also control which parts of themselves are visible to other code. Public members are the surface that other objects can use. Private members are implementation details, reachable only from inside the class. Keeping data and helper methods private stops unrelated code from touching details it has no business knowing about.

Fields and properties Fields hold the state of an object. A Person object storing a name and a date of birth keeps them in fields. Some languages, C# among them, also have properties. A property is a method for reading or setting a value, dressed up to look like a field. From the outside it is read and assigned the same way a field would be, but each access runs code the class controls. That lets the class decide what happens when someone reads or changes the value, or expose a value that can be read but not written. In languages without properties, the same thing is done with plain getter and setter methods. Inheritance Inheritance lets one class build on another. The derived class takes on the fields and methods of the base class, and it can override some of them to behave differently. This is how two types can share most of their behavior and differ only where it matters. Interfaces work differently. An interface declares a set of operations without providing any implementation, and a class implementing it must supply the code. There is nothing to inherit, only a contract to satisfy. A class can implement as many interfaces as it needs, while in most languages it can inherit from only one base class.

## Understanding the dangers of large classes: the God class antipattern

Of all the properties that affect the quality of a class, size is arguably the one that matters most. Even when everything else is a mess, short code can usually be figured out. So let's start with why small classes beat large ones, and with the antipattern known as the god class. A god class, sometimes called a god object, is a class that does too many things. These classes can be enormous. They carry multiple responsibilities and hold dozens or hundreds of fields, properties, and methods, and they seem to have a hand in everything the application does. A good indicator is when every functionality change, whatever it concerns, ends up touching this one class. Classes like this reach thousands of lines, sometimes more than ten thousand. Nobody understands what such a class does, and nobody can. Testing it thoroughly is close to impossible, and changing it without breaking something is just as hard. In practice, people modify small parts of it and hope for the best. The god class is one of the most dangerous antipatterns there is, and the problems it causes are the same as those of any large class. 

The most obvious one is that reading the whole thing takes a long time, so nobody does. At best, programmers end up with a vague sense of a few fragments. That is not to say we should read every line of a codebase to understand an application. Driving a car does not require understanding the engine. The same goes for classes: normally we read at a higher level of abstraction and get a rough idea of what the code does. But when everything is piled into one class, there is no way to tell a detail from something important, so there is no way to tell what is worth reading. Maintenance is the next problem. A class with that many responsibilities touches so much of the application that any change to it can affect code somewhere else entirely. Testing is where this hurts most. Classes like this are hard or impossible to test, so their tests are usually poor or missing. Without them, every change is a gamble, since nothing will warn us when something breaks. The risk of introducing a bug is far higher than with small classes. Debugging is torture. Finding which of several thousand lines caused a problem can take a very long time. Large classes are also difficult to reuse. Say one of a hundred methods reads data from a database, and we want that method elsewhere. It comes with the whole god object attached, and calling it means constructing something that probably takes dozens of constructor parameters and a complicated setup. So how do we end up with small, readable classes? The main tool is the Single Responsibility Principle, since large classes almost always handle more than one responsibility.

## Recognizing when a large class is acceptable

So far the message has been that large classes are a problem. But what about a class that follows the Single Responsibility Principle and is still large? This happens most often with data structures. Take the List class from the C# standard library, which provides a collection that can grow and shrink as items are added and removed. Its source code runs to more than 1,200 lines. Is that a lot? Yes. Is it too much? Not necessarily, and it is worth going through why. Start with the Single Responsibility Principle. List does not break it. Its responsibility is to provide a dynamic structure holding multiple items of one type, and that requires methods for manipulating those items, such as Add and Remove. There are many more methods than those two, and they are what make the class large, but they all serve the same responsibility. Splitting it would feel forced. One class for adding items and another for removing them makes little sense. And those classes would need access to the List's private data, which would mean the data could no longer be private. If a ListAdder and a ListDeleter could reach inside the List, so could anything else.

So List is large, and it has good reasons to be. Its size comes from the number of operations a collection has to support, not from a mix of unrelated jobs that drifted into one place. That is the distinction worth making whenever we look at a big class: the question is not how many lines it has, but whether they all serve one purpose. Avoiding helper classes that only hide size Extracting a helper class is not a bad move in itself. It is usually a good one, especially when the extracted class represents a concept of its own. But extracting a class only to reduce the number of methods in another one rarely helps. If the methods we move still belong with the ones we left behind, the split is arbitrary. We have not separated two responsibilities, we have cut one in half, and now it takes two files to understand something that used to take one. Naming gives this away. If we have a class called Abc and the best name we can find for the extracted one is AbcHelper, the split is probably forced. Clean code needs the bigger picture. Focusing too hard on one measure, such as class size, tends to cost us somewhere else. A large class is a good reason to stop and consider whether something should be extracted from it. But if an honest look, ideally with a colleague or two, says the class has one responsibility, it can stay as it is. One caveat before moving on. Large classes are sometimes justified, but rarely. The point here is not that large classes are fine, because in the vast majority of cases they are not. The point is that a class of more than two hundred lines is not automatically a failure to be shortened at any cost, and that forced shortening can do more damage than the length ever would.

## Avoiding superficial ways of making code shorter

Short code beats long code, but not at any cost. Clarity comes first. If making a class or a method shorter also makes it harder to follow, the change is not worth it. Refactoring toward better code often makes a codebase longer overall. We add classes, extract methods, and replace short names with descriptive ones. All of those are improvements, and the extra space they take in the source files is not a problem. One thing that goes wrong when developers set out to shorten their code is what could be called a clever hack. Simple code that happens to take a few lines gets rewritten into something  more compact, which does the same job in fewer characters and takes far longer to understand. Here is an example.

```csharp
int CalculateSumOfEvenNumbers(int n)
{
    int sum = 0;
    for (int i = 2; i <= n; i += 2)
    {
        sum += i;
    }
    return sum;
}
```

The same behavior can be compressed into a single expression:

```csharp
int CalculateSumOfEvenNumbers(int n)
{
    return Enumerable.Range(2, n - 1)
        .Where(x => x % 2 == 0)
        .Sum();
}
```

The shorter version is not automatically cleaner. Different teams may prefer different idioms, but the decision should be based on how easily the intended readers can understand the code, not on the number of physical lines. Code review is a better guide than a contest to minimize line count.

## Using class names to identify responsibilities

A class name is one of the most practical diagnostic tools for class design. A focused class is usually easy to name because its responsibility is clear. A class with several unrelated responsibilities often forces the developer into one of three naming mistakes: a very long compound name, an incomplete name that hides behavior, or a vague catch-all name. Compound names reveal multiple jobs Imagine a class that both confirms medical appointments and sends visit notifications. A literal name such as AppointmentsConfirmerAndPatientNotificationsSender accurately describes the implementation, but the word "And" exposes the design problem: the class contains two responsibilities.

```csharp
public class AppointmentsConfirmerAndPatientNotificationsSender
{
    public void ConfirmAppointment(
        DateTime appointmentDate,
        Patient patient,
        Doctor doctor)
    {
        // Implementation
    }
    public void NotifyAboutVisit(
        DateTime appointmentDate,
        Patient patient,
        Doctor doctor)
    {
        // Implementation
    }
}
```

A better design separates the responsibilities into AppointmentsConfirmer and PatientNotificationSender. Each class can then be named honestly and changed independently. Incomplete names hide responsibilities Renaming the same class PatientNotificationSender without removing appointment confirmation is worse. The name now suggests a narrower responsibility than the class actually has. Such names often appear when a class begins with one purpose and later accumulates new behavior without being restructured. Vague names are a warning sign Names such as Manager, Handler, Helper, Service, Utility, Utils, or Processor are not inherently wrong, but they deserve scrutiny when they are the only way to describe a class. A name such as AppointmentsManager may mean that the class confirms appointments, sends notifications, persists data, performs validation, and handles anything else related to appointments. The vagueness can be a symptom of a catch-all design. 

Another warning sign is a name that combines different abstraction levels.

UserInterfaceStringProcessor mixes a high-level user-interface responsibility with low- level string processing. Those concepts can collaborate, but they do not need to live in the same class. ## Finding boundaries through data and dependencies

Names provide an external clue, but the body of the class often contains stronger evidence. Look at which fields and dependencies each method uses. If one group of methods consistently works with one set of data while another group uses a different set, the class may contain two independent concepts.

Separating personal data from account data Consider a simplified UserAccount class that stores both personal information and login- related information:

```csharp
public class UserAccount
{
    private string _firstName;
    private string _lastName;
    private DateTime _dateOfBirth;
    private string _username;
    private string _password;
    private DateTime _lastLogin;
    public string GetFullName()
    {
        return $"{_firstName} {_lastName}";
    }
    public int GetAge()
    {
        // Simplified for this example.
        return DateTime.Now.Year - _dateOfBirth.Year;
    }
    public bool ValidateCredentials(string username, string password)
    {
        return _username == username && _password == password;
    }
    public void UpdateLastLogin()
    {
        _lastLogin = DateTime.Now;
    }
}
```

GetFullName and GetAge operate only on the personal fields. ValidateCredentials and UpdateLastLogin operate only on the account fields. The two clusters are largely independent.

Rearranging the members so that these groups sit together makes the separation visible and  suggests two classes: one representing a person and another representing account credentials and login state. This technique is useful because it relies on actual dependencies rather than intuition. If two groups of methods do not share state or collaborators, ask why they belong to the same class.

## Grouping behavior that changes together

Another way to discover responsibilities is to examine the history of change. When a particular group of methods is repeatedly modified for the same business reasons, those methods may represent a cohesive responsibility that deserves its own class. Extracting billing behavior from customer data Suppose a CustomerService class stores a customer's contact information and orders, but also calculates billing.

```csharp
class CustomerService(
    string firstName,
    string lastName,
    string email,
    string phoneNumber)
{
    private string _phoneNumber = phoneNumber;
    private List<Order> _orders = new List<Order>();
    public void AddOrder(Order order)
    {
        _orders.Add(order);
    }
    public void UpdatePhoneNumber(string phoneNumber)
    {
        _phoneNumber = phoneNumber;
    }
    //changes happen frequently in this method
    //it would be better to have it in a separate class
    public decimal CalculateBilling()
    {
        //a complex algorithm using _orders
    }
}
```

The class may look reasonable at first, since billing works with the customer's orders. The change history says otherwise. Tax rules, discount thresholds, and billing policies all change often, while the customer data itself rarely does. If product owners keep asking for changes that only touch the billing logic, then billing has a reason to change of its own. Extracting a BillingCalculator makes that responsibility explicit:

```csharp
public class BillingCalculator
{
    public decimal Calculate(IEnumerable<Order> orders)
    {
        //billing calculation
    }
}
```

Once billing is extracted, the remaining class can be renamed from the vague CustomerService to Customer because its role is simply to represent customer data and orders. The name becomes simpler because the responsibility became simpler.

## Separating levels of abstraction

A class can also reveal multiple responsibilities when its methods operate at very different levels of abstraction. High-level methods describe what the application is trying to accomplish; low-level methods describe how individual technical operations are performed. Mixing the two can bury intent beneath implementation detail. Moving string-cleaning details out of blog-post storage Consider a BlogPostsStorage class with a high-level SaveBlogPost method. A reader can understand its intent from the method body: clean the content and save it. However, the private Clean method uses a regular expression to normalize repeated spaces. That is low- level string-processing logic.

```csharp
public class BlogPostsStorage
{
    private readonly Regex _regex = new Regex("[ ]{2,}", RegexOptions.None);
    private readonly IPostsRepository _postsRepository;
    public BlogPostsStorage(IPostsRepository postsRepository)
    {
        _postsRepository = postsRepository;
    }
    public void SaveBlogPost(string content, DateTime createdDate)
    {
        var cleanedContent = Clean(content);
        _postsRepository.Save(cleanedContent, createdDate);
    }
    private string Clean(string content)
    {
        return _regex.Replace(content, " ");
    }
}
```

String normalization is not specific to blog-post storage and can be extracted into a lower-level string-processing component.

```csharp
public static class StringExtensions
{
    private static readonly Regex Regex = new Regex("[ ]{2,}", RegexOptions.None);
    public static string RemoveExcessiveSpaces(this string content)
    {
        return Regex.Replace(content, " ");
    }
}
```

The high-level class can now read almost like a description of the use case:

```csharp
public void SaveBlogPost(string content, DateTime createdDate)
{
    var cleanedContent = content.RemoveExcessiveSpaces();
    _postsRepository.Save(cleanedContent, createdDate);
}
```

The benefit goes beyond having fewer lines in BlogPostsStorage. The storage class now stays at one level of abstraction. And the string operation, which had nothing to do with storage in the first place, can now be called from anywhere in the application that needs it.

## Avoiding unnecessary class proliferation

Refactoring toward smaller classes leaves us with more classes than we started with, and often with more lines of code in the project overall. That is expected, and it is a good trade. What we get in return is granularity. A codebase made of small, well-named pieces can be read at a high level, without opening any of them. Consider an AccountStorage class working with ICredentialsValidator, IUsersRepository, and IUserCommunication. The workflow reads off the names alone: validate the credentials, save the account, tell the user what happened. Nothing stops us from opening any of those implementations if we want the details. The point is that it becomes a choice rather than a requirement.

```csharp
public class AccountStorage
{
    private readonly ICredentialsValidator _credentialsValidator;
    private readonly IUsersRepository _usersRepository;
    private readonly IUserCommunication _userCommunication;
    public void CreateNewAccount(string username, string password)
    {
        if (_credentialsValidator.IsValidUsername(username) &&
            _credentialsValidator.IsValidPassword(password))
        {
            _usersRepository.Save(username, password);
            _userCommunication.ShowMessage("Account created successfully.");
        }
        else
        {
            _userCommunication.ShowWarning("Invalid user credentials.");
        }
    }
}
```

The goal is therefore not "as many classes as possible." Extract only when the new type expresses a coherent responsibility or abstraction. Avoid both extremes: one class that owns everything and dozens of tiny types that have no independent meaning.

# Chapter 12: Organizing classes and projects

A codebase can be full of perfectly reasonable classes and still be hard to find your way around. The problem is not how those classes behave. It is where things are. Members turn up in a different order in every class, one file holds several types, and the folder structure gives no clue about how the application is organized. All of that is fixable, and it comes down to putting things where people will look for them. Inside a class, the public methods and the dependencies should be easy to spot. Across a project, the files and folders should tell us what the application is made of. And the team should agree on how it does these things, so that reading someone else's code holds no surprises. That is what this chapter is about.

## Ordering class members for readability

The compiler may not care whether a field appears above or below a method, but the reader does. A predictable member order reduces the amount of searching required to understand what a class exposes, how it is created, what it depends on, and where its implementation details live. The guiding question is simple: what will a reader look for first? Put that information where it can be found quickly. Public members normally deserve a prominent position because they describe the class from the outside. Constructors show how objects are created, and public methods reveal what the class can do. Fields are a separate case: they usually come first regardless of visibility, because they describe what the class is made of, and the reader needs the state before the behavior that acts on it. Private methods are implementation detail, so they can go further down. Anyone who wants them will scroll, but what a reader wants to see first is what the class offers. Method order can also communicate flow. If one method calls another, placing the caller above the method it uses lets a reader move from high-level intent to lower-level detail. These are recommendations rather than rigid rules. A team convention that is applied consistently is more valuable than repeatedly rearranging code to satisfy a personal preference. ## Organizing classes into separate files

A useful default is one type per file, with the file named after the type. A DatabaseConnector is easier to locate when it lives in DatabaseConnector.cs than when it is one of several unrelated types hidden in a general-purpose file. This convention improves both navigation and the ability to understand a project from its file list. Separate files also make version-control history more informative. When a commit changes three class files, the changed file list immediately tells a reviewer which types were affected. If twenty classes live in one large file, version control can only report that the single file changed. Smaller files also reduce merge conflicts because teammates are less likely to edit the same physical file at the same time. The rule should not become dogma. Very small types that clearly belong together can sometimes share a file without making anything harder to find. Suppose an application defines its own enums for days of the week, months, and seasons. Each one is a handful of lines, and none of  them will change; anyone looking for one of them would think to look for the others in the same place. Putting all three in a DateEnums.cs file does no harm.

## Maintaining consistency within classes

Organization is not only physical. A class also forms a small API, and its methods should behave in ways that do not surprise callers. Consider a PersonalDataAccess class in which three lookup methods report a missing person in three different ways.

**The inconsistent behavior can be summarized by the following example:**

```csharp
public Person GetById(int id)
{
    var person = _peopleRepository.GetById(id);
    if (person is null)
    {
        throw new KeyNotFoundException($"No person with id {id} was found.");
    }
    return person;
}
public Person GetByNames(string firstName, string lastName)
{
    var person = _peopleRepository.GetByNames(firstName, lastName);
    if (person is null)
    {
        Console.WriteLine("Person not found.");
    }
    return person;
}
public bool GetByDateOfBirth(DateTime dateOfBirth, out Person result)
{
    result = _peopleRepository.GetByDateOfBirth(dateOfBirth);
    return result is not null;
}
```

All three methods deal with the same situation, a person who is not in the repository, and each of them handles it differently. The first throws an exception, the second prints to the console and returns null, and the third returns false and passes the result through an output parameter. That is a problem for whoever calls this class. Having learned how GetById behaves, they have every reason to assume the other two work the same way, and they are wrong. So each method has to be looked up separately, and each call site handles the same situation differently: a try‑catch here, a null check there, and a bool check somewhere else. The inconsistency inside this one class turns into scattered complexity in every class that uses it. The fix is to pick one convention that suits the application and apply it consistently within a type. The same goes for naming: Get and Fetch should not be used interchangeably for the same kind of operation unless the difference means something. ## Refactoring project and class structure

When an existing project has become hard to navigate, reorganize it in small steps that can be reviewed on their own, rather than mixing structural moves with changes to behavior. Start inside the classes. Put the members in a predictable order: fields and properties first, since they describe what the class holds, then the constructors that set them up, then public methods, and the private implementation details further down. Do the same in every class, so that reading a new one holds no surprises. Then look at the files. One type per file, named after the type it holds, so that finding a class means guessing its file name correctly on the first try. At the project level, choose a folder model that matches the way the team thinks about the application, whether that is by technical concern, by feature, or by whatever the framework expects, and apply it consistently. Split a folder into subfolders once it grows crowded or starts holding unrelated things. Keep the test project separate and mirror the production structure inside it. Remember to keep commits that move files separate from commits that contain code changes, so that the version-control history stays readable. Finally, compare the classes in the area you touched. Similar operations should act the same way, and the same kind of operation should carry the same name across classes rather than being a Get in one and a Fetch in another. Where a convention keeps settling the same recurring question, write it down.

# Chapter 13: Balancing coupling, cohesion, and reuse

A system can be built from small, well-organized classes and still resist every attempt to change it. Classes end up knowing too much about each other. Things that have nothing in common get grouped together. And in the effort to remove every repeated line, we sometimes build abstractions harder to follow than the duplication they were meant to replace. The solution is to balance these relationships deliberately. Loose coupling limits what one class needs to know about another. High cohesion keeps related behavior together. DRY stops the same business knowledge from having two competing representations in the code. All three need judgment in how far they are taken. Duplication is sometimes safer than an abstraction introduced too early, before we know whether the two pieces of code will really change together. Reuse is a separate question. When behavior needs to be shared, composition is usually the better choice, because it does not lock that behavior into an inheritance hierarchy.

In this chapter, we will cover the following topics:

- Understanding coupling and learning how to reduce it
- Designing classes for high cohesion
- Applying the Law of Demeter
- Applying the DRY principle
- Recognizing when duplication is justified
- Understanding the BDUF, YAGNI, and KISS acronyms
- Understanding the "Composition over inheritance" guideline

By the end of this chapter, you will be able to identify tight coupling and low cohesion, distinguish duplicated business knowledge from merely similar code, avoid speculative abstractions, recognize rigid inheritance hierarchies, and refactor toward composition when interchangeable collaborators provide a cleaner design.

## Understanding and reducing coupling between classes

Coupling is the degree to which one class depends on another class. It describes how much one piece of code needs to know about another in order to work with it, and it shows up as a measure of how much a change on one side forces changes on the other. Some dependency is unavoidable, since useful classes collaborate. The design problem is not that a class depends on another one. It is that the consumer knows details that should have stayed private, or depends on a concrete type where an interface would do. When a small implementation change in one type forces edits in several unrelated consumers, those types are tightly coupled. Consider a newsletter component that receives a Subscribers object. The initial design exposes the internal array directly:

```csharp
public class Subscribers
{
    public Subscriber[] Items { get; }
    public Subscribers(Subscriber[] items)
    {
        Items = items;
    }
}
public class NewsletterSender
{
    private readonly Subscribers _subscribers;
    public NewsletterSender(Subscribers subscribers)
    {
        _subscribers = subscribers;
    }
    public void SendTo(bool premiumSubscribersOnly)
    {
        for (int i = 0; i < _subscribers.Items.Length; i++)
        {
            if (!premiumSubscribersOnly ||
                _subscribers.Items[i].IsPremium)
            {
                Console.WriteLine(
                    $"Newsletter sent to {_subscribers.Items[i].Email}");
            }
        }
    }
}
```

At first glance this looks fine. But notice how much SendTo knows about the inside of Subscribers. It knows the collection is an array, because it uses Length and an index. And since the array elements are reachable through the property, the sender could just as well assign null to one of them:

```csharp
_subscribers.Items[i] = null;
```

If one class can null out the contents of another, those two classes are far too familiar with each other. The fragility shows up as soon as anything changes. Replacing the array inside Subscribers with a HashSet would break SendTo, even though the responsibility of Subscribers has not changed at all. A change to the internals of one class should not reach into another one. Here it does. 

The fix is for Subscribers to hide how it stores the data and expose only what its consumer actually needs, which in this case is the ability to go through the subscribers one by one. In C# that is what IEnumerable<T> describes: a sequence that can be iterated, with no promise about what holds it underneath. An array satisfies it, and so do a list, a set, and anything else the class might switch to later.

```csharp
public class Subscribers
{
    private readonly HashSet<Subscriber> _items;
    public IEnumerable<Subscriber> Items => _items;
    public Subscribers(HashSet<Subscriber> items)
    {
        _items = items;
    }
}
public class NewsletterSender
{
    private readonly Subscribers _subscribers;
    public NewsletterSender(Subscribers subscribers)
    {
        _subscribers = subscribers;
    }
    public void SendTo(bool premiumSubscribersOnly)
    {
        foreach (var subscriber in _subscribers.Items)
        {
            if (!premiumSubscribersOnly || subscriber.IsPremium)
            {
                Console.WriteLine(
                    $"Newsletter sent to {subscriber.Email}");
            }
        }
    }
}
```

NewsletterSender no longer cares whether Subscribers uses an array, list, hash set, or another collection internally. The interface between the two classes is smaller, and the implementation detail can change without forcing a change in the consumer. Exposing IEnumerable also prevents NewsletterSender from replacing an item through index assignment, which protects the collection from inappropriate manipulation. ## Applying the Law of Demeter

The Law of Demeter, often described as the principle of least knowledge, is another practical way to control coupling. A class should collaborate with the objects it directly receives, owns, or creates rather than reaching through one object to navigate a chain of unrelated internals. The following constructor receives an entire application context only to extract one directory string:

```csharp
public class FileAccess
{
    private readonly string _mainDirectory;
    public FileAccess(ApplicationContext context)
    {
        _mainDirectory =
            context.GetAppData().GetDirectory().Main;
    }
    // Other file access methods
}
```

FileAccess now depends not only on ApplicationContext but also on the shape of the

objects returned by GetAppData and GetDirectory. A change anywhere along that chain can break a class that only needed one string. Pass the required value directly instead:

```csharp
public FileAccess(string mainDirectory)
{
    _mainDirectory = mainDirectory;
}
```

The revised constructor exposes the real dependency. It is easier to reuse, easier to test, and unaffected by changes that have nothing to do with it. The general lesson is this: if a class has to walk through a chain of properties and method calls to reach the value it needs, something is wrong. Every link in that chain is a class it now depends on. A class that needs something should ask for that thing, not for something it can dig through to find it.

## Designing for high cohesion

Cohesion describes how strongly the members of a class belong together. In a class with high cohesion, the data and the behavior inside it all serve one clear concept. Low cohesion is usually a sign that separate responsibilities have ended up in the same type. Cohesion is not really something we actively achieve. It is something we should avoid breaking.

**A small collection class is a useful example of high cohesion:**

```csharp
class PetsCollection
{
    private readonly List<Pet> _pets = new();
    public int Count => _pets.Count;
    public void Add(Pet pet)
    {
        _pets.Add(pet);
    }
    public IEnumerable<PetType> GetCurrentlyStoredTypes()
    {
        return _pets
            .Select(pet => pet.PetType)
            .Distinct();
    }
    public bool Contains(PetType petType)
    {
        return GetCurrentlyStoredTypes()
            .Any(type => type == petType);
    }
}
```

Every member either works with the same _pets collection or builds on another operation in the class. There is no obvious boundary along which the type should be divided. By contrast, imagine a HousePricer that calculates property prices and also sends those prices to the owners. The pricing part works with the area, the number of floors, and a price per square meter. The notification part needs a database of owners and something to send messages with. Neither half uses anything belonging to the other. They meet at exactly one point, where one of them hands over a number, and that is the seam this class should be split along.

```csharp
public class HousePricer
{
    private IOwnersDatabase _ownersDatabase;
    private decimal _dollarsPerSquareMeter;
    public HousePricer(
        decimal dollarsPerSquareMeter,
        IOwnersDatabase ownersDatabase)
    {
        _dollarsPerSquareMeter = dollarsPerSquareMeter;
        _ownersDatabase = ownersDatabase;
    }
    public decimal GetPrice(House house)
    {
        return
            _dollarsPerSquareMeter *
                (decimal)house.Area *
                    GetPriceMultiplierBasedOnFloors(house.Floors);
    }
    private decimal GetPriceMultiplierBasedOnFloors(int floors)
    {
        return floors switch { 1 => 1m, 2 => 1.5m, _ => 1.6m };
    }
    public void SendPriceToOwner(House house)
    {
        Console.WriteLine($"Sending price {GetPrice(house)}" +
            $" to {FindOwnerEmail(house.Address)}");
    }
    private string FindOwnerEmail(string address)
    {
        return _ownersDatabase.GetEmailByAddress(address);
    }
}
```

Refactoring this would give us two independent classes, each of them highly cohesive:

```csharp
public class HousePricer
{
    public decimal GetPrice(House house) { ... }
}
public class OwnerNotifier
{
    public void SendPriceToOwner(decimal price, string address) { ... }
}
```

The refactored types are easier to name, because each name describes one cohesive purpose. High cohesion and the Single Responsibility Principle are closely related, but they are not the same thing. Splitting every method into a class of its own would satisfy an overly literal reading of one responsibility, and it would destroy cohesion in the process. The List class we looked at earlier is the clearest case. It is large, well past a thousand lines, and it still has one responsibility: providing a collection that grows and shrinks as items are added and removed. It is also highly cohesive, precisely because every one of its methods works on the same data and serves that same concept, whether it adds an item, removes one, or sorts them all. Separating Add, Remove, Clear, and Sort into four classes would leave each of them with nothing to hold on to. ## Applying the DRY principle to knowledge

The Don't Repeat Yourself (DRY) principle is often reduced to the instruction not to copy and paste code. Its more useful design meaning is broader: a piece of knowledge should have one authoritative representation in the system. Business rules, algorithms, and other decisions should not be independently encoded in several places that can drift apart. Suppose an online store allows a product to be returned within 30 days of purchase. If the number 30 is embedded independently in several methods, the same business policy has several representations.

```csharp
public DateTime GetReturnDateDeadline(DateTime purchaseDate)
{
    return purchaseDate.AddDays(30);
}
public bool IsAfterReturnDateDeadline(DateTime purchaseDate)
{
    return (DateTime.Now - purchaseDate).TotalDays > 30;
}
```

If the policy changes, every copy must be found and changed correctly. Represent the rule once instead:

```csharp
private const int DaysForReturn = 30;
public DateTime GetReturnDateDeadline(DateTime purchaseDate)
{
    return purchaseDate.AddDays(DaysForReturn);
}
public bool IsAfterReturnDateDeadline(DateTime purchaseDate)
{
    return GetReturnDateDeadline(purchaseDate) < DateTime.Now;
}
```

Mechanical code duplication is related but not identical. For example, two validations may repeat the same null-or-empty check even though the business rule itself is not duplicated.

```csharp
public void CommitOrder(Order order)
{
    if (string.IsNullOrEmpty(order.CustomerId))
    {
        throw new ArgumentException($"CustomerId must not be empty.");
    }
    if (string.IsNullOrEmpty(order.ProductId))
    {
        throw new ArgumentException($"ProductId must not be empty.");
    }
    //saving to database here...
    Console.WriteLine("Order committed and saved to database.");
}
```

In that case, extracting a small validation method can reduce maintenance work without changing the domain model.

```csharp
private void Validate(string idToBeValidated, string propertyName)
{
    if (string.IsNullOrEmpty(idToBeValidated))
    {
        throw new ArgumentException(
            $"{propertyName} must not be empty.");
    }
}
public void CommitOrder(Order order)
{
    Validate(order.CustomerId, nameof(order.CustomerId));
    Validate(order.ProductId, nameof(order.ProductId));
    // Save to the database.
    Console.WriteLine("Order committed and saved to database.");
}
```

## Knowing when duplication is justified

Removing every visual similarity can be as dangerous as copy-pasting indiscriminately. Two pieces of code can look the same today while representing different business rules that are likely to change independently tomorrow. Back to the e-commerce example. Customers have 30 days to return the goods they bought. Now a new requirement arrives: once the goods come back, customer service has 30 days to issue the refund. We need to calculate the refund deadline and check whether it has passed.

```csharp
private const int DaysForReturn = 30;
private const int DaysForRefund = 30;
public DateTime GetReturnDateDeadline(DateTime purchaseDate) =>
    purchaseDate.AddDays(DaysForReturn);
public DateTime GetRefundDateDeadline(DateTime returnDate) =>
    returnDate.AddDays(DaysForRefund);
public bool IsAfterReturnDateDeadline(DateTime purchaseDate) =>
    IsBeforeNow(GetReturnDateDeadline(purchaseDate));
public bool IsAfterRefundDateDeadline(DateTime returnDate) =>
    IsBeforeNow(GetRefundDateDeadline(returnDate));
private bool IsBeforeNow(DateTime dateTime) =>
    dateTime < DateTime.Now;
```

The code for that looks almost exactly like the code for the return deadline, only with a different starting date. Copy-pasting is something we have all been told not to do, so the tempting move is to have the refund methods call the return ones. The duplication would be gone and the code would still work. This is how such refactor could look like:

```csharp
public DateTime GetRefundDateDeadline(DateTime returnDate) =>
    GetReturnDateDeadline(returnDate);
public bool IsAfterRefundDateDeadline(DateTime returnDate) =>
    IsAfterReturnDateDeadline(returnDate);
```

But it is the wrong call. Those two deadlines have nothing to do with each other. Returns and refunds are separate business areas, and the 30 days match by coincidence, not for any shared reason. Sooner or later one of them changes. The return window gets extended to 100 days, or it starts depending on the customer's status, and now we have to pull apart code that was written as if the two rules were one. In a small project that is annoying. In a real application it can be very hard. So we keep them apart from the start. Two separate constants, even though they hold the same number for now. This leaves a little duplication in the code. In exchange, two things that should stay separate for business reasons are separate, and when one of them changes, nothing has to be untangled first. Deferring design decisions behind abstractions Sometimes the uncertainty is about infrastructure rather than about an algorithm. ## Composition and inheritance

Two common ways to share behavior between classes are inheritance and composition. Although both can help us avoid duplication, they create different relationships between types. Understanding how each mechanism works will make it easier to see why one may be a better fit than the other. Understanding both mechanisms Inheritance is a mechanism that lets a class take on the properties and behavior of another class, with the ability to override some of them. It helps when we need several things that share most of their behavior and differ only in places. We create two types derived from the same base type, and each of them redefines only the part that should be different. The shared behavior is written once, in the base class.

Composition is a different approach. Instead of deriving from a base class, a class is given objects that provide the functionality it needs. It can serve a similar purpose to inheritance. When two functionalities are mostly the same but differ in one place, we can write one class that handles the shared part and hand it an object that handles the part that varies. Changing the behavior then means passing in a different object implementing the same interface. Either mechanism gets us to a similar result, so which one to choose? The composition over inheritance principle says composition is usually the better choice, and the reason is that inheritance brings a lot of design problems with it. Let's understand them. Issues of inheritance To understand the issues inheritance brings, let's consider the following class:

```csharp
class PersonalDataFormatter
{
    public string Format()
    {
        var people = ReadPeople();
        return string.Join(Environment.NewLine,
            people.Select(p => $"{p.Name} born in" +
                $" {p.Country} on {p.YearOfBirth}"));
    }
    private IEnumerable<Person> ReadPeople()
    {
        //Database-sourced implementation
    }
}
```

This class reads people's data from a database and formats it as a single string. It clearly breaks the Single Responsibility Principle, but let's set that aside for now. One day the business requirements change. Sometimes the data will be read from the database, and sometimes from an Excel file, and the user decides which one at runtime. There are two ways to approach this change: inheritance or composition. Let's start with inheritance, by making the PersonalDataFormatter class abstract. We will also make the ReadPeople method abstract, as it will be overridden in inheritors.

```csharp
abstract class PersonalDataFormatter
{
    public string Format()
    {
        var people = ReadPeople();
        return string.Join(Environment.NewLine,
            people.Select(p => $"{p.Name} born in" +
                $" {p.Country} on {p.YearOfBirth}"));
    }
    public abstract IEnumerable<Person> ReadPeople();
}
```

We can now create two new classes derived from the PersonalDataFormatter. Each will override the ReadPeople method in its own way.

```csharp
class DatabaseSourcedPersonalDataFormatter : PersonalDataFormatter
{
    public override IEnumerable<Person> ReadPeople()
    {
        //Database-sourced implementation
    }
}
class ExcelSourcedPersonalDataFormatter : PersonalDataFormatter
{
    public override IEnumerable<Person> ReadPeople()
    {
        //Excel-sourced implementation
    }
}
```

Now, switching between the data sources is just a matter of creating a proper DataFormatter type:

```csharp
bool shallReadFromDatabase = false;
PersonalDataFormatter personalDataFormatter = shallReadFromDatabase ?
    new DatabaseSourcedPersonalDataFormatter() :
        new ExcelSourcedPersonalDataFormatter();
Console.WriteLine(personalDataFormatter.Format());
```

We got what we wanted. Personal data can now be formatted whether it comes from a database or from an Excel file, and there is no duplication, since the shared part lives in the base class. Let's use this example to look at the problems inheritance brings. First, PersonalDataFormatter is now tightly coupled to the classes that derive from it. Any change to the base class affects them. Adding a constructor to the base class, for instance, means adding the same constructor to every derived class. The ReadPeople method is also stuck where it is. If we needed it elsewhere, we would have to reach for one of the PersonalDataFormatter classes, which makes little sense when what we need is reading data, not formatting it. The relationship between these three classes is rigid. It was fixed at compile time, the moment we declared that the concrete classes derive from PersonalDataFormatter. A more flexible arrangement, one we could change without hardcoding it into the type declarations, would serve us better. There is more. In C# and many other languages, a class can only inherit from one base class. There are good reasons for that restriction, but it is a restriction all the same. Derived types also tend to inherit more than they need, since the base class exposes its implementation details to everything below it. Inheritance also makes class hierarchies grow fast. Suppose these classes need to differ not only in where the data comes from but also in how it is formatted, so that we can pick a short or a full format independently of the Excel or database source. The hierarchy jumps from three classes to five:

```csharp
PersonalDataFormatter
DatabaseSourcedPersonalDataShortFormatter
DatabaseSourcedPersonalDataFullFormatter
ExcelSourcedPersonalDataShortFormatter
ExcelSourcedPersonalDataFullFormatter.
```

Every new aspect that varies multiplies the hierarchy again, and it becomes unmanageable quickly. Unit testing is the next problem. We have one abstract class and two concrete inheritors, and abstract classes cannot be instantiated, so there is no way to create a PersonalDataFormatter object for a test. That leaves two approaches, both flawed. 

The first is to test both inheritors and accept that each test fixture also covers the shared logic from the base class. The tests end up partly duplicated, and a change in the base class means adjusting two fixtures. The second is to test the inheritors while avoiding the base class logic as far as possible, then test that logic separately through a concrete type created only for testing. This is worse. Those tests exercise a type that does not exist in the application, so they prove less than they appear to. And even with the best intentions, it is hard to avoid touching the base class while testing its inheritors, so a change there is still likely to mean adjusting three fixtures. One more reason, unrelated to the classes we have here but worth mentioning: inheritance is awkward with Object-Relational Mapping tools such as Entity Framework. These tools map objects to relational databases, letting us read records as objects and save objects back, and generating the SQL underneath. The tables typically mirror the types we defined in code. Databases do not have a natural equivalent of inheritance, so mapping a C# hierarchy onto flat tables is tricky and tends to produce a more complicated schema than we want. All those issues can be solved by using composition instead of inheritance. Composition over inheritance Now let's refactor this code to use composition instead of inheritance. The change is simple. Instead of an abstract method, PersonalDataFormatter takes a dependency on an object that can read the data. That object implements an IPersonalDataReader interface, and the class holds it in a field.

```csharp
interface IPersonalDataReader
{
    IEnumerable<Person> ReadPeople();
}
class PersonalDataFormatter
{
    private readonly IPersonalDataReader _personalDataReader;
    public PersonalDataFormatter(IPersonalDataReader personalDataReader)
    {
        _personalDataReader = personalDataReader;
    }
    public string Format()
    {
        var people = _personalDataReader.ReadPeople();
        return string.Join("\n",
            people.Select(p => $"{p.Name} born in" +
                $" {p.Country} on {p.YearOfBirth}"));
    }
}
class DatabaseSourcedPersonalDataReader : IPersonalDataReader
{
    public IEnumerable<Person> ReadPeople()
    {
        //Database-sourced implementation
    }
}
class ExcelSourcedPersonalDataReader : IPersonalDataReader
{
    public IEnumerable<Person> ReadPeople()
    {
        //Excel-sourced implementation
    }
}
```

This is what composition is. We put PersonalDataFormatter and IPersonalDataReader together, and working as a pair they give us exactly what we need. There is no code duplication, and the code can be extended easily. Let's go through the problems inheritance caused, one by one, and see how composition deals with them. Tight coupling. A minor change in the base class could force changes in the derived ones, which made the code brittle. Now PersonalDataFormatter and the reader classes know nothing about each other. They communicate through an interface, and interfaces change far less often than implementation details do. Reusability. The people-reading logic used to live in an abstract method and its overrides, so reusing it meant dragging along a PersonalDataFormatter. The reader classes can now be composed with anything, including types that have nothing to do with formatting. Rigid relationships. The link between the formatter and its subclasses was fixed at compile time. With composition, the formatter receives a reader through its constructor, so the choice  of reader can be made at runtime. It can depend on configuration or user input, and the formatter's code doesn't change. One base type. Classes implementing IPersonalDataReader can implement as many other interfaces as they need. Inheriting too much. With inheritance gone, the only point of contact between these classes is the interface, so there are no implementation details to leak. Growing hierarchy. Adding short and long formatting used to mean multiplying the number of classes. Now it means one more interface with two implementations. However many traits we add, the structure stays flat: a set of interfaces with types implementing them, and nothing deeper than one level. Unit testing. Testing PersonalDataFormatter is a matter of mocking the reader, and the reader classes can be tested on their own. A change in any of them affects one test fixture. Object-Relational Mapping. With composition, one object holds another inside it, and that is something databases handle without trouble. Every problem we identified with inheritance is gone. So whenever inheritance is tempting, the question worth asking is whether composition would serve better. Most of the time it will. None of this means inheritance should never be used. Frameworks often require it, and deriving from a base class is simply how we tell the framework what kind of object we are building. Custom exceptions are another case, since a new exception type is defined by inheriting from an existing one, and the resulting hierarchy is what lets callers catch errors at the level of detail they need. Inheritance also works well for small, data-focused families of types where the variants are known upfront and unlikely to grow. What it does not do well is serve as a general tool for sharing behavior, which composition handles better.

# Chapter 14: Using comments effectively

We sometimes hear that the more comments a codebase has, the better. It sounds reasonable. Comments explain, and explanation helps. But it does not hold up in practice. A comment can help a reader understand something the code cannot express on its own. It can also become a second description of the program, running alongside the first one and agreeing with it only for a while. A comment that restates obvious code adds noise. A comment that has fallen out of date is worse, because it tells the reader something that is no longer true. The practical approach is to let the code carry as much of the intent as it can, and to reserve comments for what truly belongs outside the implementation. This chapter looks at comment patterns that do harm, shows when refactoring or version control solves the problem better, and points out the cases where a short, precise comment earns its place.

In this chapter, we will cover the following topics:

- Removing comments that merely restate the code
- Replacing navigation and block-description comments with clearer structure
- Why change history and commented-out code do not belong in comments
- Documenting complex algorithms and regular expressions
- Explaining temporary workarounds
- Using TO-DO comments carefully
- Using XML documentation comments for shared APIs
- Keeping required copyright comments concise

By the end of this chapter, you will be able to distinguish comments that add information from comments that repeat or contradict the code, refactor code to remove unnecessary explanations, use version control instead of changelist or commented-out code, and write focused comments for algorithms, regular expressions, workarounds, TO-DOs, and public API documentation.

## Why comments should not replace clear code

Comments are often added with good intentions, but they should not compensate for unclear code. If a variable or method needs a comment merely to explain what it means, improve the name. If a method is too complex to understand without a running commentary, refactor the method before adding more prose. A high comment count is not a quality metric. The code and the comments must be maintained separately, so every explanation creates another artifact that can drift away from the behavior it describes. Prefer clear names and structure whenever they can carry the same information more reliably. When your first response to confusing code is to add a comment, ask whether refactoring would remove the need for that comment. A good comment adds information that the code cannot express cleanly; it should not serve as a translation layer for poor names or tangled control flow. Outdated and misleading comments Comments become dangerous when they no longer match the implementation. An IDE can rename symbols and detect many syntax problems, but it cannot reliably know that a prose explanation has become false after a behavior change. Treat the code as the source of truth and keep comments only where their additional information justifies the maintenance cost.

A comment that merely duplicates the code adds little value, while a comment that contradicts the code can send a maintainer in the wrong direction. The safest comment is one that explains information beyond the obvious mechanics of the implementation. The following quote summarizes this idea: "Don't comment bad code, rewrite it." — Brian W. Kernighan and P. J. Plauger Several recurring comment patterns are useful warning signs because they either restate visible code or preserve information that belongs elsewhere. Removing comments that restate the code A "Captain Obvious" comment restates what the code already says. Consider the following code:

```csharp

public Person(string name, int yearOfBirth)
{
    Name = name;
    YearOfBirth = yearOfBirth;
}
//save file name
string saveFileName = "game";
//calculates the distance between points in kilometers
double CalculateDistanceInKilometers(
    Point point1, Point point2)
{
    // method body
}
```

Those comments add no information, as the identifiers already express what the code does. Remove such comments and let the code speak for itself. Removing navigation comments Another category of useless comments is navigation comments. Consider this for loop:

```csharp
for (int i = 0; i < iterations; i++)
{
    decimal x = i;
    decimal y = x * i;
    z += y;
} //end of for loop
```

Navigation comments such as this one usually indicate that formatting or method size is making the structure hard to see. Align the code consistently and extract oversized blocks rather than marking their boundaries with prose. Replacing block-description comments with methods Block-description comments often name a responsibility that should itself become a method.

**Let's see some examples:**

```csharp

    var ids = txt.Split(',');
    foreach(var fileId in ids)

{
    //read the IDs from JSON file
```

Those comments show that the developer noticed the separate responsibilities in those blocks of code but stopped short of acting on it. A better approach is to extract the logic into methods with descriptive names, eliminating the need for comments:

```csharp

{
    numbers = ReadIdsFromText(fileContent);
}
else if (ex == "json")
```

```csharp
{
    numbers = ReadIdsFromJson(fileContent);
}
```

There is another advantage to this. A method name travels with the method. Wherever it is called, the name is right there, explaining what happens at that point. A comment stays where someone wrote it, and it appears again only if someone remembers to write it again. That makes a good name the more reliable documentation of the two. Keeping change history in version control Changelist comments store information that modern version-control systems already track more accurately. Dates, authors, renames, and cleanup history belong in repository history and commit messages rather than at the top of a source file.

**Here is an example of changelist comments at the top of a file:**

```csharp

```

Instead, use your version control system to track changes. Removing commented-out code Commented-out code creates uncertainty because readers cannot tell whether it is obsolete, temporarily disabled, or still required. Delete code that is no longer used and rely on version- control history if an earlier implementation ever needs to be recovered. Now that you have seen the worst examples of comments, you are ready to learn about scenarios where using comments may actually be appropriate.

## When comments add value

Comments are justified when they carry context that the code itself cannot express, such as the reason behind a workaround, the description of an algorithm being implemented, or what a regular expression is actually matching. When a comment is necessary, make it precise, complete, brief, and easy for another developer to maintain. Before writing it, confirm that the same intent cannot be expressed more reliably through a better name, smaller method, or clearer type. 

Prefer code that explains its own mechanics, and use comments for the additional context that remains. Documenting complex algorithms For example, if you implement a complex algorithm like adaptive heap sort, even the best variable naming may not help a developer unfamiliar with the algorithm understand your code. In this case, it is helpful to leave a short comment with a link to the algorithm's description, such as a Wikipedia article. This allows anyone reading your code to quickly find out what algorithm is being used. The following code demonstrates how you might document the use of a complex algorithm with a comment and a reference link:

```csharp
// Implements the Adaptive Heap Sort algorithm
// https://en.wikipedia.org/wiki/Adaptive_heap_sort
public static void Sort(int[] input)
{
    int length = input.Length;
    // Build the initial max-heap
    for (int i = length / 2 - 1; i >= 0; i--)
    {
        Heapify(input, length, i);
    }
    for (int i = length - 1; i > 0; i--)
    {
        // Swap the root element (maximum) with the last element
        int temp = input[0];
        input[0] = input[i];
        input[i] = temp;
        // Heapify the reduced heap
        Heapify(input, i, 0);
    }
}
```

Remember, this does not excuse you from keeping the code itself as clean as possible. Explaining regular expressions Another scenario where comments are appropriate is when you use regular expressions (regexes). Regular expressions are patterns for matching and manipulating strings, and they can be difficult to read and understand. You should not force readers of your code to decipher regexes on their own. Instead, leave a comment that describes what the regex does and provides examples of matching and non-matching strings. Here is an example of how to document a regex with a descriptive comment and examples:

```csharp
public static bool IsValidEmail(string email)
{
    // Simple email validation pattern
    // This pattern checks for valid characters,
    // the "@" symbol, domain names, and top-level domains (TLDs).
    //
    // Examples of matching strings:
    // somebody@gmail.com
    // someone@yahoo.fr
    //
    // Examples of non-matching strings:
    // somebody@gmail
    // @yahoo.fr
    string pattern = @"^[\w-]+(\.[\w-]+)*@([\w-]+\.)+[a-zA-Z]{2,7}$";
    return Regex.IsMatch(email, pattern);
}
```

Documenting temporary workarounds Sometimes code has to include a workaround for a problem that cannot be fixed right away. One real example from the author's experience: a library that threw an exception the first time an object was instantiated, but worked on the second attempt. With a deadline approaching and no time to investigate properly, the object was created twice, and a comment was left explaining why. The following code shows how to document such a workaround with a clear comment:

```csharp

{
    someObject = new SomeClass(); // this will fail
}

    // SomeClass constructor is called for the first time.
    // This is a temporary workaround - to be addressed.
    // (12-09-2025, contact John Smith in case of questions)
}

```

Using TO-DO comments carefully Another reasonable use of comments is for to-do notes that describe what still needs to be done in the code. These are acceptable as long as you follow a few important conditions. Larger work items usually belong in a dedicated issue tracker rather than in source comments. Use TO-DO comments only for small, short-lived tasks; keep their format consistent, make ownership and date visible when that helps the team, and use analyzers or repository searches so TO-DOs do not disappear indefinitely. The following code demonstrates a properly formatted to-do comment, including the responsible person and date:

```csharp

{
}
```

In contrast, the next example shows inconsistent and less effective to-do comment formats:

```csharp

//TO DO: fix bug when length < 0
//To-do add error handling
```

A consistent format, as shown below, is preferred, as it will enable easy search by automated tools:

```csharp

//to-do fix bug when length < 0
//to-do add error handling
```

Using structured documentation comments Most languages have a convention for documenting a public API in a structured form that tools can read: XML documentation comments in C#, Javadoc in Java, docstrings in Python. IDEs display them to whoever calls the method, so the documentation reaches the reader at the moment they need it.

This kind of documentation has to be kept in step with the API it describes. That is worth doing where the audience justifies it, which usually means shared libraries and public interfaces. For code used only inside one project, the maintenance cost is rarely repaid. The following code shows how to write summary comments in C#:


## Understanding unit testing

A unit test is an automated check of one small piece of functionality. In practice that usually means calling one method on one class with a fixed set of inputs and verifying the result. "Automated" means we do not run them by hand. The whole suite should run from a button or a single command, and it should finish fast, within seconds for a small project. That is not something we get for free. It is something the tests have to be written and kept fit for, because a suite that takes ten minutes is a suite people stop running. The same goes for isolation. A test for one class should only fail when that class changes. Modifying class A and watching the tests for class B go red is a sign that the two are more entangled than they should be, and it is worth stopping to look at the design rather than at the test. Isolation is something we design for, mostly by keeping dependencies explicit and substituting them in tests.

**Let's consider this simple mathematical example:**

```csharp
class Math
{
    public static int Multiply(int a, int b)
    {
        return a * b;
    }
    public static int Add(int a, int b)
    {
        return a + b;
    }
}
```

Here is what a sample test for the Add method could look like. When we run the tests for the whole project, the framework finds them on its own and executes them, then reports which ones passed and which did not.

```csharp
[TestFixture]
class MathTests
{
    [Test]
    public void Add_ShallGive_8_ForArguments_3_And_5()
    {
        var sum = Math.Add(3, 5);
        Assert.That(sum, Is.EqualTo(8));
    }
}
```

One test does not prove that the whole Math class is correct. Other inputs and other behaviors need tests of their own. What this example does show is the shape every unit test takes: arrange the data the test needs, execute one behavior, and verify the result, all without anyone clicking anything. There are many testing frameworks, and the examples here use NUnit. The details differ between them, but the structure above is the same everywhere, so switching from one framework to another is mostly a matter of learning new names for the same things. Using mocks for isolated tests Isolation becomes more interesting when the class under test depends on another component. Consider PersonalDataProcessor, which asks a repository for people and returns the greatest age:

```csharp
class PersonalDataProcessor
{
    private readonly IPeopleRepository _peopleRepository;
    public PersonalDataProcessor(IPeopleRepository peopleRepository)
    {
        _peopleRepository = peopleRepository;
    }
    public int FindMaxAge()
    {
        var allPeople = _peopleRepository.GetAll();
        return allPeople.Max(person => person.Age);
    }
}
```

A unit test should not need a real database holding a particular set of records. That would make the test slower, harder to run on another machine, and dependent on what happens to be in the database. It would also mean the test exercises the repository as well as PersonalDataProcessor.

This is what mocks are for. A mock is an object that replaces a real dependency in a test. We decide how it behaves, so the test doesn't depend on the real implementation. It has no real logic behind it. We simply state what its methods should return when the code under test calls them. Most languages have mocking libraries that create these classes for us, so we rarely write them by hand. Here the mock stands in for the repository, and the test decides exactly what GetAll returns:

```csharp
[TestFixture]
public class PersonalDataProcessorTests
{
    [Test]
    public void FindMaxAge_ReturnsTheAgeOfOldestPerson()
    {
        var peopleRepositoryMock = new Mock<IPeopleRepository>();
        peopleRepositoryMock
            .Setup(repo => repo.GetAll())
            .Returns(new List<Person>
            {
                new Person("John", "Doe", 25),
                new Person("Jane", "Doe", 80),
                new Person("Max", "Smith", 30)
            });
        var processor = new PersonalDataProcessor(
            peopleRepositoryMock.Object);
        var result = processor.FindMaxAge();
        Assert.That(result, Is.EqualTo(80));
    }
}
```

The test is now independent of the real repository and its database. Mocks are also useful when the collaborator performs an action rather than returning a value. For example, a mock user- communication object can verify that ShowMessage was called with the expected argument even when the method under test has no useful return value. 

What unit tests do and do not prove Automated unit tests are the first line of defense after a change. When the covered behaviors still pass, we know those pieces work as they did before, and we know it in seconds rather than after repeating the same checks by hand. A good test suite also works as documentation. Opening the tests for a class is often the fastest way to understand what it does, since each test states one behavior in isolation, along with the inputs it applies to and the result it produces. And unlike a comment or a wiki page, this description cannot quietly fall out of date. If the class stops behaving the way a test says it does, the test fails. Unit tests do not prove the whole application works. Because unit tests deliberately isolate classes from one another, they say nothing about how those classes behave together. That is what integration and end-to-end tests are for. The role of a unit test suite is narrower: fast feedback about small pieces of behavior, and a way of making design problems visible whenever isolation turns out to be difficult. Much of what this chapter says about writing tests well applies to those other kinds too. A clear name, one reason to fail, no logic in the test body, no dependence on the order tests run in: none of that is specific to unit tests. An integration test that nobody can read is as much of a liability as an unreadable unit test, and probably more, since it usually takes longer to run.

## Using tests to protect and improve code quality

Unit tests do not make production code clean by themselves. A bad design can be covered by a large test suite and stay exactly as bad as it was. What tests do is make changing that code safer, so the design can be improved without fear. And when writing them turns out to be hard, they point at the parts of the design that resist isolation, which is usually where the improving needs to start. Using tests as a safety net for refactoring Getting from working code to clean code rarely happens in one go. First, we make the code work. Then we improve it through a series of small refactoring steps: renaming a variable, extracting a method, moving a responsibility to another class. Each step is easy on its own. What stops people from taking these steps is the risk. Every one of them changes code that currently works, and nobody wants to be the one who broke it. This is where tests work as a safety net. After each step, we run them and know within seconds whether the code still behaves as before. If something broke, the fix is easy, because only one small thing changed.

Without tests, teams tend to leave working code alone, and it keeps getting worse because nobody dares to touch it. With tests, refactoring becomes an ordinary part of the day rather than something to schedule and worry about. Clean tests support safe refactoring, and safe refactoring supports clean production code. Messy tests make changes expensive, while having no tests at all makes developers much less likely to refactor. Using testability as design feedback A class can look perfectly clean, with good names and a tidy structure, and still have a design that causes trouble. Usually we find out much later, when a new requirement arrives and the change turns out to be painful. But there is an earlier warning, and it comes when we sit down to write a test. To test a class in isolation, its design has to include seams: boundaries along which the class can be cut out of the rest of the project. Without them the test drags half the application in with it, and whatever we end up writing is not really a unit test, because its result no longer depends on the class alone. So the difficulty of writing a test is information in itself, and it arrives before the test has run even once. A class creating its own dependencies is the classic case. There is no way to test it without engaging everything it builds inside itself, and that struggle points straight at what needs to change. That is not a coincidence, and it is the more interesting point. A class that a test can separate from the rest of the code is a class that anything can separate from the rest of the code. It can be swapped for a different implementation when the requirements change, even at runtime. Interfaces and constructor injection create these seams, and a mock passed into a constructor in a test is the same mechanism as a different implementation passed in for real.

## Using test-driven development

Test-driven development (TDD) changes the order in which code is written. Instead of implementing a whole feature and then adding tests, we start with a test for one small behavior that does not exist yet. Then we write just enough production code to make that test pass, improve the result while keeping it passing, and move on to the next behavior.

Say we are writing a Divide method. The first test states that dividing 8 by 4 gives 2, and we write the code that makes it true. The next test requires an exception when the divisor is zero, and only then does that case get implemented. Each requirement shows up as a test before it shows up as code. This connects directly to clean code design. Writing the test first means describing how the class will be used before deciding how it works inside, so the signature, the parameter order, the return value, and the dependencies are all settled from the caller's point of view. And if the class needs data from a database, the question of how a test would control that data comes up immediately, which pushes us toward an abstraction and an injected dependency without having to think about it separately. None of this happens because tests magically produce good code. It happens because the feedback arrives constantly. Every behavior gets a check as soon as it exists, and every implementation step ends with the safety net already in place, which is exactly the moment when improving the design costs the least.

## Treating test code as production code

A test suite is part of the codebase and changes alongside the production code. If the tests are difficult to read or modify, developers spend more time maintaining them, and eventually they may start disabling tests that fail too often. Once that happens, the safety net loses its value. Test code therefore deserves the same attention to naming, structure, duplication, and readability as production code. Writing readable and well-named tests A test should say what it checks at a glance. Short tests do that. Long ones make the reader work for it. One way to keep them short is to move repeated setup out of the test bodies. Most frameworks let us mark a method that runs automatically before each test in a class, and that is where the objects and configurations the tests share can be created:

```csharp
[TestFixture]
class MathTests
{
    [SetUp]
    public void SetUp()
    {
        // Code here runs before every test.
    }
}
```

Test names are especially important because the name is often the first information you see when a test fails. A useful name communicates what is being tested, the expected behavior, and the scenario. The exact order of those parts is a team convention; consistency matters more than choosing one universal pattern. Long names are acceptable when they make the failed behavior immediately understandable. For example, a test checking that dividing 8 by 4 gives 2 could be called Divide_ShallGive_2_WhenDividing_8_By_4. The name has three parts: the method being tested, the expected result, and the scenario it applies to. Notice the underscores. They go against how methods are normally named, and that is fine here. Test names are read in a report rather than called from code, so separating the parts makes them easier to pick out at a glance. Separating arrange, act, and assert Most unit tests contain three conceptual steps. Arrange prepares objects and data, Act executes the behavior under test, and Assert verifies the outcome. Keeping those steps visually distinct makes the test easier to follow. Empty lines are often enough; explicit Arrange, Act, and Assert comments are optional and should be used consistently if a team prefers them.

```csharp
[Test]
public void FindMaxAge_ReturnsTheAgeOfOldestPerson()
{
    var peopleRepositoryMock = new Mock<IPeopleRepository>();
    peopleRepositoryMock.Setup(repo => repo.GetAll()).Returns(
        new List<Person>
        {
            new Person("John", "Doe", 25),
            new Person("Jane", "Doe", 80),
            new Person("Max", "Smith", 30)
        });
    var processor = new PersonalDataProcessor(
        peopleRepositoryMock.Object);
    var result = processor.FindMaxAge();
    Assert.That(result, Is.EqualTo(80));
}
```

Keeping tests focused Each test should verify one coherent behavior. A test that creates a collection, reverses it, orders it, filters it, and then checks a final value does not make it clear which operation failed. Split unrelated behaviors into separate tests so that a failure points to one responsibility. Loops, conditionals, and exception-handling logic inside tests are warning signs because they introduce additional behavior into the test itself. A small loop can occasionally be reasonable, for example when making the same assertion for every item in a collection, but complicated control flow usually means the test should be simplified or divided. Removing duplication with parameterized tests Say we write a test checking that dividing 8 by 4 gives 2. Then we want the same check for another pair of numbers. The tempting move is to copy the test and change the values, which leaves two methods with identical bodies and different arguments. It works, but every fix to that test now has to be made twice. Testing frameworks solve this with parameterized tests. We write the test body once, with the values as parameters, and then declare the sets of values it should run with. The framework runs the method once per set and reports each run separately, so a failure still tells us which case broke. Each framework has its own syntax for this, and NUnit uses TestCase attributes:

```csharp
[TestCase(8, 4, 2)]
[TestCase(20, 5, 4)]
public void Divide_ShallGiveCorrectResult_ForValidInput(
    int dividend, int divisor, float expectedResult)
{
    var result = Math.Divide(dividend, divisor);
    Assert.That(result, Is.EqualTo(expectedResult));
}
```

Writing meaningful assertions Assertions determine whether the test passes or fails, so they should verify the facts that matter to the behavior under test. As a practical default, keep a test centered on one logical outcome. Multiple assertions are reasonable when they describe one tightly connected result, such as the size and contents of a collection.

```csharp
[Test]
public void Reverse_ShallFlipTheCollectionOrder()
{
    var input = new List<int> { 1, 2, 3 };
    input.Reverse();
    Assert.That(input.Count, Is.EqualTo(3));
    Assert.That(input[0], Is.EqualTo(3));
    Assert.That(input[1], Is.EqualTo(2));
    Assert.That(input[2], Is.EqualTo(1));
}
```

Do not assert details that the tested behavior does not promise. If a method is responsible only for selecting a day in a given year, asserting unrelated time components makes the test more brittle without increasing confidence in the intended behavior. ## Designing production code for testability

Testability is a property of the production code. When a class is hard to test, the fix belongs there rather than in the test. Let's look at the design problems that cause it most often.

Avoiding static dependencies that must be replaced Chapter 10 examined static methods and hidden dependency graphs in detail. Here, the focus is narrower: what happens to a unit test when the behavior it needs to control is locked behind a static call. A class that receives an IPeopleRepository can be tested with a mock. If the same class calls a static repository method directly, the test loses that substitution point:

```csharp
class PersonalDataProcessor_Static
{
    public int FindMaxAge()
    {
        var allPeople = PeopleRepository.GetAll(); //we can't substitute this in
        tests
            return allPeople.Max(person => person.Age);
    }
}
```

This does not make every static call a problem. Plenty of them are fine, because there is nothing we would ever want to substitute. A mathematical operation returns the same answer for the same arguments and has no alternative implementation. The same goes for simple text processing, such as trimming whitespace or changing case. Calls like these are fast, predictable, and have no reason to be replaced in a test, so letting the real code run is exactly right. The problem appears when a static call reaches something we would want to control: a database, a file, the network, or the system clock. Depending on abstractions rather than concrete types Chapter 9 introduced the Dependency Inversion Principle as a design rule. In a test, the same abstraction becomes a substitution seam: the production collaborator can be replaced with a controlled test double. The class below depends on PeopleRepository, a concrete type. Nothing about that signature invites a substitute, so a test for this class runs against a real repository, and through it against a real database. That makes the test slow, dependent on what the database happens to contain, and no longer a test of this class alone. Depending on an IPeopleRepository interface instead  would remove the problem, since the test could then pass in a mock and decide for itself what the repository returns.

```csharp
class PersonalDataProcessor
{
    private readonly PeopleRepository _peopleRepository;
    public PersonalDataProcessor(PeopleRepository peopleRepository)
    {
        _peopleRepository = peopleRepository;
    }
}
```

Change the dependency to an abstraction when the collaborator is intended to vary or be replaced in tests:

```csharp
class PersonalDataProcessor
{
    private readonly IPeopleRepository _peopleRepository;
    public PersonalDataProcessor(IPeopleRepository peopleRepository)
    {
        _peopleRepository = peopleRepository;
    }
}
```

The production class now states the capability it requires without committing to one implementation. The test can supply a mock, while the application can supply the real repository. Some mocking libraries can fake a concrete class by generating a subclass at runtime, so it might look as though the interface is unnecessary. In practice, it only works for members the language allows to be overridden. For members the language does not allow to be overridden, the behavior depends on the mocking library. Some refuse outright, others accept the setup and never use it, leaving the real method to run while the test appears to be working with a mock. Mocking a class also ties the test to one particular implementation rather than to a contract, which is how a change inside one class ends up breaking the tests of another. Interfaces avoid both problems, and that is why mocking against them is the default approach.

Injecting dependencies instead of creating them internally An interface is not enough if the class constructs the concrete implementation itself. The following constructor still prevents a test from supplying a mock:

```csharp
class PersonalDataProcessor
{
    private readonly IPeopleRepository _peopleRepository;
    public PersonalDataProcessor()
    {
        _peopleRepository = new PeopleRepository();
    }
}
```

Constructor injection exposes the dependency and ensures that every valid instance receives it when the object is created. Making dependency fields publicly settable would also permit replacement, but it weakens encapsulation and allows the dependency to be changed to an invalid value later. Constructor injection keeps the object valid after construction. Keeping constructors simple One of the most common testability pitfalls is a constructor that does actual work. Creating an object should be cheap and predictable, and once it stops being either, every test that needs that object pays the price. Here is a method that updates the owner of a house in a repository. It looks straightforward, and in production it works. Now we want a unit test for the UpdateHouseOwner method. The test would be simple enough: call the method and verify that Save was called on the repository mock with the right arguments.

```csharp
public class HousesStateUpdater
{
    private readonly IHousesRepository _housesRepository;
    public HousesStateUpdater(IHousesRepository housesRepository)
    {
        _housesRepository = housesRepository;
    }
    public void UpdateHouseOwner(int houseId, Owner owner)
    {
        var house = new House(houseId, owner);
        _housesRepository.Save(house);
    }
}
```

But as it turns out, the test fails with some complicated message about a failed database connection, which makes no sense at first. The test uses a mock of the houses repository, so nothing here should be connecting to anything. Tracking it down leads to the line where a House is constructed. The constructor turns out to do more than construct. It creates a HousesRepository object, which opens a database connection, which in turn expects global configuration that does not exist in the test environment. Hence the exception.

```csharp
public class House
{
    public int HouseId { get; }
    public Owner Owner { get; }
    public House(int houseId, Owner owner)
    {
        var housesRepository = new HousesRepository();
        if (!housesRepository.DoesHouseExist(houseId))
        {
            throw new ArgumentException(
                $"A house with ID {houseId} does not exist.");
        }
        if (!housesRepository.DoesOwnerExist(owner))
        {
            throw new ArgumentException(
                $"An owner named {owner.Name} does not exist.");
        }
        HouseId = houseId;
        Owner = owner;
    }
}
```

A constructor doing this kind of work is wrong on several levels.

The first is expectation. Seeing a constructor call, nobody expects a database connection or a dependency on global configuration. Work like that should be visible, not hidden behind what looks like an ordinary constructor call. The second is performance. Imagine a loop creating 1000 House objects. The constructor runs on every pass, and every time it builds a repository and opens a connection. The third is that constructors run in places we do not always notice. Some types create objects on our behalf rather than when we ask for them. For example, C# has a type called Lazy<T>, a wrapper that holds an object of type T but does not create it until something first uses it. At that point the constructor of T runs, at a place in the program where no new appears anywhere nearby. If that constructor opens a database connection, both the cost and any resulting test failure are hard to trace back to their source. The fourth brings us back to tests. A base class constructor also runs when we create an object of a derived type. This matters when we mock a concrete class, which is possible, although not recommended. A common way for mocking libraries to do this is to create a subclass of that class. In that case, creating the mock runs the base constructor. If that constructor does real work, such as opening a database connection, the mock does it too, and the test suddenly needs a working database. All we wanted was a simple stand-in. The same problem appears wherever derived types are involved, but tests are where it hurts most. It is one more reason to mock interfaces rather than classes. A constructor doing complex work causes problems that are hard to trace, because they start at the moment an object is created and nobody thinks to look there. So what belongs in a constructor? Very little. Assigning the arguments to fields, creating simple structures the object owns, such as an empty list, and rejecting arguments that are plainly invalid, like a null dependency. The goal is a valid object and nothing more. What does not belong there is anything with a cost or a consequence. No database connections, no file reads, no calls to web services. No loops or branching business logic. And nothing expensive enough that we would want to see it happening in the code rather than have it triggered by a new. If an operation is worth thinking about when it runs, it should be a method call somebody makes deliberately, not a side effect of creating an object. This chapter connected testability with clean design and clean tests.
