# C# Delegates, Events, Event Handlers, Async Behavior, Domain Events & Integration Events

## A practical tutorial for understanding DDD (Domain-Driven Design) and implementing event-driven .NET applications

---

# 1. Why Events?

Imagine an order application:

```csharp
public async Task CreateOrderAsync(CreateOrderRequest request)
{
    var order = new Order(request.CustomerId);

    await _orderRepository.AddAsync(order);

    await _emailService.SendOrderCreatedEmailAsync(order);
    await _inventoryService.ReserveStockAsync(order);
    await _notificationService.NotifyCustomerAsync(order);
    await _auditService.WriteAuditLogAsync(order);

    await _orderRepository.SaveChangesAsync();
}
```

Assumes `_orderRepository`, `_emailService`, `_inventoryService`, `_notificationService` and `_auditService` are injected dependencies of the class.

This method knows about:

- Order persistence
- Email
- Inventory
- Notification
- Audit
- Other side effects

As the application grows, the method becomes tightly coupled: every new reaction ("also award loyalty points") means editing this method, and a failure in any one call (say the email server is down) breaks order creation as a whole.

A better design is:

```text
Order Created
     |
     +----> Update Customer
     |
     +----> Send Notification
     |
     +----> Publish Integration Event
     |
     +----> Write Audit
```

The order does not need to know who is interested in the fact that it was created.

This is the foundation of event-driven design.

# 2. Delegate

A **delegate is a type-safe reference to a method**.

Example:

```csharp
public void SendEmail(string email)
{
    Console.WriteLine($"Sending email to {email}");
}
```

Define a delegate:

```csharp
public delegate void EmailSender(string email);
```

Assign the method:

```csharp
EmailSender sender = SendEmail;

sender("khairul@example.com");
```

Conceptually:

```text
EmailSender
     |
     v
SendEmail()
```

The delegate defines a contract:

```text
Return type: void
Parameter:   string
```

Therefore this works:

```csharp
void HandleMessage(string message)   // void + (string): matches EmailSender
{
}
```

But these do not match:

```csharp
int HandleMessage(string message)    // wrong return type: int, not void
{
    return 10;
}
```

or:

```csharp
void HandleMessage(int message)      // wrong parameter type: int, not string
{
}
```

Assigning either one (`EmailSender s = HandleMessage;`) is a compile error.

---

# 3. Delegate as a Callback

A delegate allows one piece of code to say:

> "I don't know exactly what method will run. I only know what signature it must have."

Example:

```csharp
public delegate void MessageHandler(string message);

void LogMessage(string message)
{
    Console.WriteLine(message);
}

MessageHandler handler = LogMessage;

handler("Hello");
```

Flow:

```text
Caller
  |
  v
MessageHandler
  |
  v
LogMessage()
```

This callback concept is the foundation for events.

---

# 4. Multicast Delegates

A delegate can reference multiple methods.

```csharp
public delegate void OrderHandler(Order order);
```

Methods:

```csharp
void SendEmail(Order order)
{
    Console.WriteLine("Email");
}

void WriteAudit(Order order)
{
    Console.WriteLine("Audit");
}

void UpdateAnalytics(Order order)
{
    Console.WriteLine("Analytics");
}
```

Combine them:

```csharp
OrderHandler handler = SendEmail;   // list: [SendEmail]

handler += WriteAudit;              // list: [SendEmail, WriteAudit]
handler += UpdateAnalytics;         // list: [SendEmail, WriteAudit, UpdateAnalytics]
// handler -= WriteAudit;           // would remove WriteAudit from the list
```

Invoke (`order` is any existing `Order` instance):

```csharp
handler(order);   // runs the three methods in the order they were added
```

Caveat: if the delegate returns a value, the caller only receives the **last** method's result (see section 13.6). If one method throws, the methods after it do not run.

Execution:

```text
handler(order)
       |
       +----> SendEmail()
       |
       +----> WriteAudit()
       |
       +----> UpdateAnalytics()
```

This is called a **multicast delegate**.

This idea is very important because .NET events are built on delegates.

# 5. What Is an Event?

An event is a controlled notification mechanism built around a delegate.

Example:

```csharp
public class Order
{
    public event EventHandler? OrderCreated;
}
```

A subscriber can listen:

```csharp
order.OrderCreated += OnOrderCreated;
```

Handler:

```csharp
void OnOrderCreated(object? sender, EventArgs e)
{
    Console.WriteLine("Order created");
}
```

The owner of the event raises it:

```csharp
OrderCreated?.Invoke(this, EventArgs.Empty);   // "?." = only invoke if at least one subscriber exists
```

The important difference is:

### Delegate

External code can invoke the delegate.

### Event

External code can subscribe/unsubscribe, but only the class that owns the event can raise it.

This gives encapsulation.

---

# 6. Why `event` Exists

Without `event`:

```csharp
public EventHandler? OrderCreated;
```

Another class could do:

```csharp
order.OrderCreated?.Invoke(
    order,
    EventArgs.Empty);
```

That means external code could pretend the order was created (all subscribers would run for an order that was never created). It could also wipe everyone's subscriptions with `order.OrderCreated = null;`.

With:

```csharp
public event EventHandler? OrderCreated;
```

external code can only:

```csharp
order.OrderCreated += Handler;
order.OrderCreated -= Handler;
```

It cannot raise the event.

Only `Order` can do:

```csharp
OrderCreated?.Invoke(
    this,
    EventArgs.Empty);
```

Mental model:

```text
                  Order
                    |
              owns event
                    |
        +-----------+-----------+
        |           |           |
     Handler A   Handler B   Handler C

Subscribers can listen.
Only Order can raise.
```

# 8. Complete C# Event Example

```csharp
public class Order
```

```csharp

```

```csharp

        $"Order {e.OrderId} was created.");
```

```text

      v
```

```csharp
}
```

# 10. Observer Pattern

Events implement a variation of the **Observer Pattern**.

```text
                  Publisher
                     |
                  Order
                     |
                 OrderCreated
                     |
        +------------+------------+
        |            |            |
        v            v            v
      Email       Audit       Analytics
      Handler     Handler       Handler
```

The publisher does not need to know the implementation details of its subscribers.

This is the foundation of event-driven architecture.

# 11. Async Event Handling

This is where many C# developers become confused.

A normal event uses:

```csharp
EventHandler
```

which returns:

```csharp
void
```

But asynchronous code normally uses:

```csharp
Task
```

Example:

```csharp
async Task HandleOrderCreated(...)
{
    await SendEmailAsync();
}
```

The signatures are different.

```text
EventHandler
    |
    +----> void

async method
    |
    +----> Task
```

Therefore, do not casually convert an asynchronous handler into `async void`.

---

# 12. The `async void` Problem

You might write:

```csharp
async void HandleOrderCreated(
    object? sender,
    OrderCreatedEventArgs e)
{
    await SendEmailAsync();
}
```

It compiles because traditional .NET event handlers use `void`.

But `async void` has an important limitation:

> The caller cannot await it.

Example (`Created` is a normal `EventHandler<...>` event, `args` its event data):

```csharp
Created?.Invoke(this, args);   // returns as soon as the handler hits its first await

Console.WriteLine("DONE");
```

Handler:

```csharp
async void Handle(object? sender, OrderCreatedEventArgs e)
{
    await Task.Delay(2000);

    Console.WriteLine("EMAIL SENT");
}
```

Possible execution:

```text
Raise event
   |
   +----> Handler starts
   |
   +----> await
   |
   +----> control returns immediately
   |
   +----> "DONE"
   |
   |
   2 seconds later
   |
   +----> "EMAIL SENT"
```

The publisher has no `Task` representing the asynchronous work. That has two consequences:

1. It cannot wait: it reports "done" while the email is still being sent.
2. It cannot catch failures. An exception thrown after the first `await` has no caller to travel back to, so it is re-thrown on the thread pool (or UI context) and, if unhandled, can crash the whole process:

```csharp
// Bad: the try/catch never sees the exception
try { Created?.Invoke(this, args); }          // handler is async void
catch (Exception) { /* never runs for errors after the first await */ }

// Good: a Task-returning handler (section 13) lets the caller await and catch
try { await handler(@event, ct); }
catch (Exception ex) { /* runs */ }
```

Therefore:

> Avoid `async void` for application/domain event infrastructure unless the framework's event contract specifically requires it.

---

# 13. Better Async Event Handler Abstraction

The idea in one line:

> Make the handler return a `Task` instead of `void`, so the code that raises the event can `await` each handler and know when it finishes, whether it failed, and how to cancel it.

## 13.1 The Event Data and the Delegate

If you are designing your own event infrastructure, use a `Task`-returning abstraction:

```csharp
public sealed record OrderCreatedEvent(
    int OrderId,
    string CustomerEmail);

// "Any method that takes (TEvent, CancellationToken) and returns Task"
public delegate Task AsyncEventHandler<TEvent>(
    TEvent @event,
    CancellationToken cancellationToken);
```

## 13.2 The Publisher Keeps a List of Handlers and Awaits Each One

```csharp
public sealed class Order
{
    private readonly List<AsyncEventHandler<OrderCreatedEvent>> _createdHandlers = [];

    public int Id { get; }

    public Order(int id) => Id = id;

    // Subscribe (plays the role of "+=")
    public void OnCreated(
        AsyncEventHandler<OrderCreatedEvent> handler)
        => _createdHandlers.Add(handler);

    public async Task CreateAsync(
        CancellationToken cancellationToken = default)
    {
        Console.WriteLine($"Creating order {Id}...");

        var @event = new OrderCreatedEvent(
            Id,
            "customer@example.com");

        foreach (var handler in _createdHandlers)
        {
            // Invoke the delegate and wait for it
            await handler(
                @event,
                cancellationToken);
        }

        Console.WriteLine($"Order {Id}: all handlers finished");
    }
}
```

Note: a delegate is invoked like a method — `handler(@event, ct)` — not with `handler.HandleAsync(...)`. `HandleAsync` is the interface style shown in section 13.7.

## 13.3 Handlers Are Ordinary `async Task` Methods

Any method matching the delegate signature can subscribe:

```csharp
static async Task SendEmailAsync(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(2000, ct);   // simulate SMTP call

    Console.WriteLine($"Email sent to {e.CustomerEmail}");
}

static async Task WriteAuditAsync(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(500, ct);    // simulate DB write

    Console.WriteLine($"Audit written for order {e.OrderId}");
}
```

Usage:

```csharp
var order = new Order(100);

order.OnCreated(SendEmailAsync);
order.OnCreated(WriteAuditAsync);

await order.CreateAsync();

Console.WriteLine("DONE");
```

Output:

```text
Creating order 100...
Email sent to customer@example.com      (after 2 s)
Audit written for order 100             (after 0.5 s more)
Order 100: all handlers finished
DONE
```

`DONE` prints last because the publisher actually waited for the handlers.

## 13.4 Compare With `async void`

With `event EventHandler<...>` and `async void` handlers (section 12), the same program prints:

```text
Creating order 100...
Order 100: all handlers finished    <-- false: nothing has finished yet
DONE
Audit written for order 100         (0.5 s later)
Email sent to customer@example.com  (2 s later)
```

| Concern | `async void` handler | `Task`-returning handler |
|---|---|---|
| Publisher knows when the handler is done | No | Yes (`await`) |
| Handler exception | Can't be caught by the publisher; may crash the process | Comes back through `await`, so `try/catch` works |
| Cancellation | No way to pass a token | `CancellationToken` parameter |
| Sequential or parallel | Always fire-and-forget | Your choice (`foreach await` or `Task.WhenAll`) |

## 13.5 Exceptions and Cancellation

Exceptions flow back to the publisher:

```csharp
static async Task FailingHandler(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(100, ct);

    throw new InvalidOperationException("SMTP server down");
}

order.OnCreated(FailingHandler);

try
{
    await order.CreateAsync();
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"Handler failed: {ex.Message}");   // this runs
}
```

With `async void`, this `catch` would never run.

Cancellation reaches every handler:

```csharp
using var cts = new CancellationTokenSource(
    TimeSpan.FromSeconds(1));

// After 1 s the token is cancelled: SendEmailAsync's 2 s delay is aborted
// and throws TaskCanceledException, which propagates out of CreateAsync
// (wrap in try/catch (OperationCanceledException) if cancellation is expected).
await order.CreateAsync(cts.Token);
```

## 13.6 Trap: `event` With a `Task`-Returning Delegate

You might try:

```csharp
public event AsyncEventHandler<OrderCreatedEvent>? Created;

await Created?.Invoke(@event, ct);   // wrong
```

This compiles, but when a multicast delegate returns a value, **only the last subscriber's return value is returned**. You would await only the last handler's `Task`; the others become fire-and-forget again (they start, but nobody waits for them or sees their exceptions). Also, with zero subscribers `Created?.Invoke(...)` is `null`, and `await null` throws `NullReferenceException`.

That is why the example keeps its own `List<...>` and awaits each item. If you do use `event`, iterate the invocation list:

```csharp
if (Created is not null)
{
    foreach (AsyncEventHandler<OrderCreatedEvent> handler
        in Created.GetInvocationList())
    {
        await handler(@event, ct);
    }
}
```

## 13.7 From Delegate to Interface

The same contract — take the event and a token, return a `Task` — can be expressed as an interface:

```csharp
public interface IDomainEventHandler<TEvent>
{
    Task HandleAsync(
        TEvent @event,
        CancellationToken cancellationToken);
}
```

The dispatcher then awaits it:

```csharp
await handler.HandleAsync(
    @event,
    cancellationToken);
```

| | Delegate style | Interface style |
|---|---|---|
| Handler is | a method | a class |
| Invoke with | `await handler(e, ct)` | `await handler.HandleAsync(e, ct)` |
| Dependencies (DbContext, email service) | captured in a closure | constructor injection |
| Registration | `order.OnCreated(...)` | DI (dependency injection) container (`services.AddScoped<IDomainEventHandler<...>, ...>()`) |

Real DDD applications usually use the interface style (see section 23), because handlers need injected services. The delegate style is the simplest way to see why returning `Task` matters.

# 14. Synchronous vs Asynchronous Event Handlers

Synchronous (illustrative shape only; the built-in `System.EventHandler<T>` has a different signature, so use another name if you define your own):

```csharp
public delegate void SyncEventHandler<T>(T eventData);
```

Flow:

```text
Event
  |
  v
Handler
  |
  v
void
```

Asynchronous:

```csharp
public delegate Task AsyncEventHandler<T>(
    T eventData,
    CancellationToken cancellationToken);
```

Flow:

```text
Event
  |
  v
Handler
  |
  v
Task
  |
  v
await
```

The second approach is much more useful for DDD application infrastructure.

# 15. Async Does Not Mean Distributed

This distinction is extremely important.

This:

```csharp
await handler.HandleAsync();
```

is asynchronous programming.

It does NOT automatically mean:

```text
another service
```

`await` just means "do not block this thread while waiting". The awaited work can be an in-memory method, a database call, or a message to another service. For example, `await handler.HandleAsync(...)` where the handler only updates an object in the same process involves no network and no other service.

You can have:

```text
Same process
     |
     +---- async
```

Or:

```text
Different processes
     |
     +---- async messaging
```

These are different concepts.

Remember:

```text
async ≠ distributed
```

# 17. Why DDD Uses Domain Events

Suppose an order is placed.

Several things may need to happen:

```text
Order placed
   |
   +----> Update customer statistics
   |
   +----> Apply loyalty points
   |
   +----> Create notification
   |
   +----> Create integration message
```

If the `Order` aggregate directly calls all of these services, it becomes tightly coupled.

Instead:

```text
Order Aggregate
       |
       v
OrderPlacedDomainEvent
       |
       v
Domain Event Dispatcher
       |
       +----> Handler A
       +----> Handler B
       +----> Handler C
```

The aggregate only knows the business fact.

# 18. Domain Event Is Not the Same as a C# Event

A C# event:

```csharp
public event EventHandler<OrderCreatedEventArgs>? Created;
```

is a language/runtime mechanism for notifying subscribers.

A DDD domain event:

```csharp
public sealed record OrderPlacedDomainEvent(
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount
) : IDomainEvent;
```

is a business fact.

The domain event says:

> "An order was placed."

This is why DDD events are often explicit objects rather than C# events.

# 19. Define the Domain Event Contract

A simple contract:

```csharp
public interface IDomainEvent
{
}
```

Then:

```csharp
public sealed record OrderPlacedDomainEvent(

```

The event is just data.

It does not execute anything.

Think:

```text
Domain Event

     +---- data
     |
     +---- business fact
     |
     +---- no infrastructure dependency
```

# 20. Aggregate Root

A common aggregate-root implementation stores domain events.

```csharp
public abstract class AggregateRoot
{
    private readonly List<IDomainEvent> _domainEvents = [];   // [] = empty list (C# 12 collection expression)

    public IReadOnlyCollection<IDomainEvent> DomainEvents
        => _domainEvents.AsReadOnly();

    protected void AddDomainEvent(
        IDomainEvent domainEvent)
    {
        _domainEvents.Add(domainEvent);
    }

    public void ClearDomainEvents()
    {
        _domainEvents.Clear();
    }
}
```

The aggregate records events rather than immediately dispatching them.

---

# 21. Why Store the Event Instead of Immediately Dispatching It?

Avoid this:

```csharp
public void Place()
{
    // Change state

    DomainEventDispatcher.Dispatch(          // handlers run RIGHT NOW, mid-method
        new OrderPlacedDomainEvent(...));
}
```

Problems: handlers run before the order is saved (they may react to a change that is later rolled back), the domain class is welded to a static dispatcher, and unit tests of `Place()` trigger real handlers.

Prefer:

```csharp
public void Place()
{
    // Change state

    AddDomainEvent(                          // just remembers the event in a list
        new OrderPlacedDomainEvent(...));
}
```

(`...` stands for the constructor arguments, as in section 22.)

Why?

Because the domain model should not suddenly start performing infrastructure/application work.

The aggregate says:

> "This happened."

The application infrastructure decides when and how to process it.

This is often called the **deferred domain-event approach**.

# 22. Example Order Aggregate

Assumes `AggregateRoot` from section 20 and `OrderPlacedDomainEvent` from section 19; `Id`, `CustomerId` and `TotalAmount` are set elsewhere (constructor or other methods, omitted here).

```csharp
public sealed class Order : AggregateRoot
{
    public Guid Id { get; private set; }

    public Guid CustomerId { get; private set; }

    public decimal TotalAmount { get; private set; }

    public void Place()
    {
        // Business rules

        // Change state
        // ...

        AddDomainEvent(
            new OrderPlacedDomainEvent(
                Id,
                CustomerId,
                TotalAmount));
    }
}
```

Notice what `Order` does NOT know about:

```text
Email
RabbitMQ
Kafka
Azure Service Bus
HTTP
SQL
MediatR
```

It only knows:

```text
OrderPlacedDomainEvent happened.
```

That is good domain isolation.

# 23. Domain Event Handler

Define:

```csharp
public interface IDomainEventHandler<TEvent>
    where TEvent : IDomainEvent
{
    Task HandleAsync(
        TEvent domainEvent,
        CancellationToken cancellationToken);

```

Handler:

```csharp
public sealed class SendOrderConfirmationHandler
    : IDomainEventHandler<OrderPlacedDomainEvent>
{
    public async Task HandleAsync(
        OrderPlacedDomainEvent domainEvent,
        CancellationToken cancellationToken)
    {
        // Send confirmation

        await Task.CompletedTask;
    }
}
```

Another handler:

```csharp
public sealed class UpdateCustomerStatisticsHandler
    : IDomainEventHandler<OrderPlacedDomainEvent>
{
    public async Task HandleAsync(
        OrderPlacedDomainEvent domainEvent,

    {
        // Update statistics

        await Task.CompletedTask;
    }
}
```

Now:

```text
OrderPlacedDomainEvent
          |
          +----> SendOrderConfirmationHandler
          |
          +----> UpdateCustomerStatisticsHandler
```

The aggregate does not know about either handler.

# 24. Domain Event Dispatcher

Define:

```csharp
public interface IDomainEventDispatcher
{
    Task DispatchAsync(
        IEnumerable<IDomainEvent> events,
        CancellationToken cancellationToken);
}
```

Conceptual implementation:

```csharp
public async Task DispatchAsync(
    IEnumerable<IDomainEvent> events,
    CancellationToken cancellationToken)
{
    foreach (var domainEvent in events)
    {
        // Pseudocode: look up every IDomainEventHandler<TheEventsConcreteType>
        // in the DI container (usually via reflection or MakeGenericType).
        var handlers = ResolveHandlers(domainEvent);

        foreach (var handler in handlers)
        {
            await handler.HandleAsync(
                domainEvent,
                cancellationToken);
        }
    }
}
```

Now the flow is:

```text
Domain Event
     |
     v
Dispatcher
     |
     +----> Handler A
     |
     +----> Handler B
     |
     +----> Handler C
```

You have now built the basic mechanics of a DDD event system.

---

# 25. Sequential Event Handlers

A simple dispatcher can process handlers sequentially:

```csharp
foreach (var handler in handlers)
{
    await handler.HandleAsync(
        domainEvent,
        cancellationToken);
}
```

Flow:

```text
Handler A
   |
   v
Handler B
   |
   v
Handler C
```

If each takes approximately one second:

```text
Total ≈ 3 seconds
```

This approach is easy to reason about and can be appropriate when:

- handlers have dependencies: B needs what A produced (e.g. A creates the customer record, B sends mail to it)
- handlers share transactional state: they all must commit or roll back together
- ordering matters: "apply discount" must run before "calculate loyalty points"
- the same DbContext (EF Core's unit of work) is involved: a `DbContext` is not thread-safe, so handlers must use it one at a time

# 26. Parallel Event Handlers

If handlers are truly independent:

```csharp
var tasks = handlers.Select(
    handler => handler.HandleAsync(
        domainEvent,
        cancellationToken));

await Task.WhenAll(tasks);
```

Flow:

```text
Handler A ───────>
Handler B ───────>
Handler C ───────>
                  |
                  v
              Task.WhenAll
```

Potentially, three one-second handlers can finish in approximately one second rather than three.

But do not blindly parallelize handlers.

Consider:

- database concurrency: two handlers updating the same row at once can overwrite each other
- shared `DbContext`: it is not thread-safe, so two handlers using the same injected instance concurrently throws errors such as "A second operation was started on this context instance" (fix: each handler gets its own scope/context, or run sequentially)
- transaction boundaries: parallel handlers cannot easily share one transaction
- ordering requirements: parallel handlers have no guaranteed order
- resource limits: 50 handlers at once can exhaust connection pools or hit API rate limits
- handler dependencies: B cannot start before A finishes if it needs A's result

Concurrency is an architectural decision.

---

# 27. `Task.WhenAll` and Exceptions

Suppose:

```text
Handler A → success
Handler B → exception
Handler C → success
```

With:

```csharp
await Task.WhenAll(tasks);
```

all handlers may already have started.

Therefore:

```text
B failed
```

does not necessarily mean:

```text
C never ran
```

They were concurrent. `Task.WhenAll` always waits for every task to finish, then `await` re-throws only the **first** exception (the others stay on the `Task.WhenAll` task's `Exception.InnerExceptions`). So if B failed, A and C may have already completed their side effects (an email was sent), and you only see B's error.

This is important when designing failure handling: make handlers idempotent or retry-safe (section 38).

# 28. Domain Event Lifecycle

A typical lifecycle:

```text
1. Business operation
       ↓
2. Aggregate changes state
       ↓
3. Aggregate raises domain event
       ↓
4. Event is stored in aggregate
       ↓
5. Unit of Work saves transaction
       ↓
6. Domain event dispatcher runs
       ↓
7. Domain event handlers execute
       ↓
8. Some handler may create integration event
```

This is the core DDD event flow. (A Unit of Work tracks all changes made during one business operation and saves them together; in EF Core, `DbContext.SaveChanges` plays this role. This lifecycle is the "after commit" ordering of section 29; for "before commit", swap steps 5 and 6. Either way, clear the aggregate's event list after dispatching so events are not processed twice.)

# 29. Where Should Domain Events Be Dispatched?

There are two common choices.

## Option A: Before Commit

```text
Command
  |
  v
Aggregate
  |
  v
Domain Event
  |
  v
Domain Handlers
  |
  v
SaveChanges
  |
  v
Commit
```

If a handler fails, the database transaction can fail/rollback depending on how the transaction is configured.

This can be useful when the handler's work must participate in the same transaction. Example: placing an order must also decrement stock; if the stock handler throws, the order is not saved either (all or nothing). The cost: a slow or failing handler now blocks and can undo the main operation.

---

## Option B: After Commit

```text
Command
  |
  v
Aggregate
  |
  v
SaveChanges
  |
  v
COMMIT
  |
  v
Domain Event
  |
  v
Handlers
```

Now:

```text
Database = success
Handler = failure
```

The order still exists, but the confirmation email was never sent and nobody was told. The caller may even receive an error for an order that was in fact saved.

Therefore, handler failure needs:

- retries (try the handler again, e.g. 3 times with a delay)
- eventual consistency (accept that the side effect may happen slightly later, not atomically with the order)
- monitoring (alerts when a handler keeps failing)
- durable messaging when necessary (store the work in an outbox/queue so a crash cannot lose it)

# 30. Domain Event vs Integration Event

This distinction is essential.

| | Domain Event | Integration Event |
|---|---|---|
| Scope | Same bounded context/application | Across service/system boundaries |
| Communication | In-process | Network/message broker |
| Typical mechanism | Dispatcher/Mediator | RabbitMQ/Kafka/Azure Service Bus |
| Persistence | Usually local (lives in memory for the request) | Usually durable (stored by the broker/outbox so it survives crashes) |
| Reliability | Process-local (if the process dies, the event is gone, but so is the whole operation) | Retry/idempotency required (the network can fail or deliver twice; see section 38) |
| Example | `OrderPlacedDomainEvent` | `OrderPlacedIntegrationEvent` |

Mental model:

```text
Domain Event
     |
     v
Inside application
```

versus:

```text
Integration Event
     |
     v
Message Broker
     |
     v
Other application/service
```

# 33. Integration Event Handler Example

Assumes `IIntegrationEventPublisher` is your own abstraction over the broker (it has `PublishAsync`). Despite its name, this is a **domain** event handler: it reacts to the domain event and produces the integration event.

```csharp
public sealed class OrderPlacedIntegrationEventHandler
    : IDomainEventHandler<OrderPlacedDomainEvent>
{
    private readonly IIntegrationEventPublisher _publisher;

    public OrderPlacedIntegrationEventHandler(
        IIntegrationEventPublisher publisher)
    {
        _publisher = publisher;
    }

    public async Task HandleAsync(
        OrderPlacedDomainEvent domainEvent,
        CancellationToken cancellationToken)
    {
        var integrationEvent =
            new OrderPlacedIntegrationEvent(
                Guid.NewGuid(),
                domainEvent.OrderId,
                domainEvent.CustomerId,
                domainEvent.TotalAmount,
                DateTime.UtcNow);

        await _publisher.PublishAsync(
            integrationEvent,
            cancellationToken);
    }
}
```

Conceptually:

```text
Domain Event
     |
     v
Handler
     |
     v
Integration Event
     |
     v
Broker
```

However, there is a reliability problem.

# 34. The Database vs Broker Problem

Suppose:

```text
Save database
     |
     v
Publish message
```

What if:

```text
Database = SUCCESS
Broker = FAILURE
```

Then:

```text
Order exists
BUT
Payment Service never receives OrderPlaced
```

This is a classic distributed-systems consistency problem.

The solution is often the **Outbox Pattern**.

# 35. Outbox Pattern

Store both the business change and the outgoing message in the same database transaction.

```text
BEGIN TRANSACTION

INSERT Order

INSERT OutboxMessage

COMMIT
```

Conceptually:

```text
Database Transaction
       |
       +---- Order
       |
       +---- Outbox Message
```

Then a background worker reads the outbox:

```text
Outbox Table
    |
    v
Background Worker
    |
    v
Message Broker
```

If the application crashes after commit:

```text
Order exists
Outbox message exists
```

The worker can retry publishing.

Where does the `OutboxMessage` row come from? A domain event handler (section 46) or a `SaveChanges` override serializes the event into an `OutboxMessage` and adds it to the same `DbContext`, so one `SaveChanges` commits the order and the message together. Nothing is sent to the broker inside the transaction.

# 37. Outbox Table Example

A simplified entity:

```csharp
public class OutboxMessage
{
    public Guid Id { get; set; }

    public string Type { get; set; } = null!;

    public string Payload { get; set; } = null!;

    public DateTime OccurredOnUtc { get; set; }

    public DateTime? ProcessedOnUtc { get; set; }

    public string? Error { get; set; }
}
```

Typical states:

```text
ProcessedOnUtc = null
        |
        v
Pending
        |
        v
Publish
        |
        v
ProcessedOnUtc = timestamp
```

If publishing fails:

```text
Pending
   |
   v
Failure
   |
   v
Retry
```

A minimal worker loop (assumes `db` is a `DbContext` with `DbSet<OutboxMessage> OutboxMessages`, `broker` publishes a raw message):

```csharp
var pending = await db.OutboxMessages
    .Where(m => m.ProcessedOnUtc == null)      // not yet published
    .OrderBy(m => m.OccurredOnUtc)
    .Take(20)
    .ToListAsync(ct);

foreach (var m in pending)
{
    try
    {
        await broker.PublishAsync(m.Type, m.Payload, ct);
        m.ProcessedOnUtc = DateTime.UtcNow;     // success: never picked up again
    }
    catch (Exception ex)
    {
        m.Error = ex.Message;                   // stays pending; next loop retries it
    }
}
await db.SaveChangesAsync(ct);
```

If the worker crashes after publishing but before saving, the message is published again on restart. This is why consumers must be idempotent (next section).

---

# 38. Idempotency

Distributed messaging can produce duplicate delivery.

Example:

```text
OrderPlaced
     |
     v
Payment Service
```

Payment succeeds.

But the consumer crashes before acknowledging the message.

The broker retries:

```text
OrderPlaced
     |
     v
Payment Service
```

again.

Without idempotency, payment could happen twice.

Therefore consumers should usually be idempotent.

---

# 39. Event ID

An integration event should have a unique ID (this is the same event as section 32, written with `init` properties instead of a positional record; both are equivalent for this purpose):

```csharp
public record OrderPlacedIntegrationEvent
{
    public Guid EventId { get; init; }

    public Guid OrderId { get; init; }

    public Guid CustomerId { get; init; }

    public decimal TotalAmount { get; init; }

    public DateTime OccurredOnUtc { get; init; }
}
```

The consumer can keep a processed-message table:

```text
ProcessedMessages
-----------------
EventId
ProcessedOnUtc
```

Before processing:

```text
Have I processed EventId?
       |
   +---+---+
   |       |
  Yes      No
   |       |
Ignore    Process
            |
            v
       Mark processed
```

Make `EventId` the primary key (or unique) and insert it in the same transaction as the business change. Otherwise two copies arriving at the same moment can both pass the "have I processed it?" check. This is the basic idea of idempotent consumers.

---

# 40. Integration Event Versioning

Integration events are external contracts.

For example, version 1:

```csharp
OrderPlacedIntegrationEvent
{
    OrderId
    CustomerId
}
```

Later you need:

```csharp
OrderPlacedIntegrationEvent
{
    OrderId
    CustomerId
    Currency
    TotalAmount
}
```

Other services may still depend on the old contract. Adding a field is usually safe (old consumers ignore it). Renaming or removing one (e.g. dropping `CustomerId`) makes old consumers fail to deserialize or read a null, while their code is still deployed. (The blocks above are pseudo-notation for the fields, not compilable C#.)

Therefore, integration events should be designed and versioned carefully.

Possible approaches:

```text
OrderPlacedIntegrationEventV1
OrderPlacedIntegrationEventV2
```

or compatible additive changes, depending on the messaging ecosystem.

```text

```

with:

```text

```

```text

       |
       v
MediatR
       |
       +---- Handler
```

```text
      |
```

# 45. When Should Domain Logic Be Synchronous?

Inside the aggregate, business invariants should normally be handled locally and synchronously.

For example:

```csharp
order.AddItem(item);
order.CalculateTotal();
order.Validate();
```

Avoid making the aggregate depend directly on:

```text
HTTP
Database
RabbitMQ
Kafka
Email
External API
```

The aggregate should be able to make its business decision from its own state and domain rules.

# 46. What Should Domain Event Handlers Do?

Domain event handlers can perform application-level side effects such as:

```text
Update another aggregate
Update read-side information
Create an outbox message
Trigger internal application processing
Record audit information
```

Be careful about direct external calls:

```csharp
await httpClient.PostAsync(...);
```

inside a transaction. Two things can go wrong: the HTTP call succeeds but the database transaction then rolls back (the other system was told about an order that does not exist), or the call is slow/fails and holds database locks open or fails the whole request. You cannot roll back an HTTP call.

A more reliable approach is often:

```text
Domain Event
    |
    v
Create Outbox Record
    |
    v
Commit
    |
    v
Background Worker
    |
    v
HTTP / Broker / External Service
```

# 47. Common Mistake: Infrastructure in the Domain

Avoid:

```csharp
public class Order
{
    private readonly EmailService _emailService;

    public async Task PlaceAsync()
    {
        // Business logic

        await _emailService.SendAsync();   // domain now calls infrastructure
    }
}
```

The domain entity now depends on infrastructure. Consequences: you cannot unit test `Place` without an email service (or a mock), an email outage makes placing an order fail, and the domain layer must reference infrastructure code.

Prefer:

```csharp
public void Place()
{
    // Business rules

    AddDomainEvent(                        // same helper as section 20
        new OrderPlacedDomainEvent(...));
}
```

Then the application layer handles side effects (a handler sends the email).

---

# 48. Common Mistake: `async void`

Avoid:

```csharp
async void Handle(...)
{
    await DoSomethingAsync();
}
```

for your own event infrastructure.

Prefer:

```csharp
async Task HandleAsync(
    ...,
    CancellationToken cancellationToken)
{
    await DoSomethingAsync();
}
```

This allows:

```csharp
await handler.HandleAsync(...);
```

and gives proper:

- exception propagation
- cancellation
- completion tracking
- composition

---

# 49. Common Mistake: `Task.Run` as Event Architecture

Do not use:

```csharp
Task.Run(() => HandleEvent());   // starts work on a thread-pool thread, then forgets it
```

as a replacement for reliable event infrastructure.

`Task.Run()` only moves work to another thread in the same process. It does not solve:

- persistence: the work lives only in memory
- retries: a failure is swallowed or lost, nobody re-runs it
- transaction boundaries: it may run before the order is committed, or after the scope/`DbContext` was disposed
- process crashes / durability: if the app restarts right after returning HTTP 200, the work is silently lost
- idempotency: nothing prevents it running twice if you add naive retries
- message delivery: no other service is reached
- dead-letter handling (a dead-letter queue, DLQ, parks messages that keep failing so you can inspect them)

Scenario: `Task.Run(() => SendEmail(order))`, the API returns 200, the pod restarts, the email is never sent and nothing records that it was owed. With an outbox row written in the same transaction as the order, the worker sends it after restart.

Use proper messaging/outbox infrastructure for those requirements.

---

# 50. Common Mistake: Publishing Before Persistence

Be careful with:

```text
Publish message
     |
     v
Save database
```

If the broker succeeds and the database fails:

```text
Broker = success
Database = failure
```

Consumers received a fact that did not actually persist (e.g. Payment Service charges a customer for an order that does not exist in the Order database).

A transactional outbox is a common solution.

---

# 51. Common Mistake: Treating Every Operation as an Event

Not every method deserves an event.

Bad examples:

```text
GetCustomer
GetOrder
CalculatePrice
ValidateEmail
```

Good business facts:

```text
OrderPlaced
OrderCancelled
PaymentReceived
CustomerRegistered
InvoiceGenerated
ShipmentDispatched
```

Queries (`Get...`) change nothing, and `CalculatePrice`/`ValidateEmail` are internal steps, not business facts anyone else needs to react to. Turning them into events floods handlers and the broker with noise and couples consumers to your internals. An event should normally represent something meaningful that happened.

# 58. The One Sentence to Remember

> **A delegate gives you a callback contract; an event uses that mechanism to notify subscribers; an event handler reacts to the notification; a domain event represents a business fact inside a bounded context; an integration event carries a fact across a system boundary; and an outbox plus message broker makes that cross-boundary communication reliable.**

The complete mental model is:

```text
C# LANGUAGE LEVEL

Delegate
   ↓
Event
   ↓
Event Handler
   ↓
Async Task


DDD LEVEL

Command
   ↓
Aggregate
   ↓
Domain Event
   ↓
Domain Event Handler


DISTRIBUTED SYSTEM LEVEL

Domain Event
   ↓
Outbox
   ↓
Integration Event
   ↓
Message Broker
   ↓
Consumer
   ↓
Idempotency + Retry + DLQ
```

Once this hierarchy is clear, **DDD Domain Events, Integration Events, CQRS (Command Query Responsibility Segregation: separate models for writes and reads), MediatR, RabbitMQ/Kafka/Azure Service Bus, Outbox Pattern, and eventual consistency all become much easier to reason about.**
