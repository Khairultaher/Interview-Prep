# C# Delegates, Events, Event Handlers, Async Behavior, Domain Events & Integration Events

## A practical tutorial for understanding DDD and implementing event-driven .NET applications

---

# 1. Why Events?

Imagine an order application:

```csharp
public async Task CreateOrderAsync(CreateOrderRequest request)
{
    var order = new Order(request.CustomerId);

    await _orderRepository.AddAsync(order);

    await _emailService.SendOrderCreatedEmailAsync(order);
    await _inventoryService.ReserveStockAsync(order);
    await _notificationService.NotifyCustomerAsync(order);
    await _auditService.WriteAuditLogAsync(order);

    await _repository.SaveChangesAsync();
}
```

This method knows about:

- Order persistence
- Email
- Inventory
- Notification
- Audit
- Other side effects

As the application grows, the method becomes tightly coupled.

A better design is:

```text
Order Created
     |
     +----> Update Customer
     |
     +----> Send Notification
     |
     +----> Publish Integration Event
     |
     +----> Write Audit
```

The order does not need to know who is interested in the fact that it was created.

This is the foundation of event-driven design.

---

# 2. Delegate

A **delegate is a type-safe reference to a method**.

Example:

```csharp
public void SendEmail(string email)
{
    Console.WriteLine($"Sending email to {email}");
}
```

Define a delegate:

```csharp
public delegate void EmailSender(string email);
```

Assign the method:

```csharp
EmailSender sender = SendEmail;

sender("khairul@example.com");
```

Conceptually:

```text
EmailSender
     |
     v
SendEmail()
```

The delegate defines a contract:

```text
Return type: void
Parameter:   string
```

Therefore this works:

```csharp
void HandleMessage(string message)
{
}
```

But these do not match:

```csharp
int HandleMessage(string message)
{
    return 10;
}
```

or:

```csharp
void HandleMessage(int message)
{
}
```

---

# 3. Delegate as a Callback

A delegate allows one piece of code to say:

> "I don't know exactly what method will run. I only know what signature it must have."

Example:

```csharp
public delegate void MessageHandler(string message);

void LogMessage(string message)
{
    Console.WriteLine(message);
}

MessageHandler handler = LogMessage;

handler("Hello");
```

Flow:

```text
Caller
  |
  v
MessageHandler
  |
  v
LogMessage()
```

This callback concept is the foundation for events.

---

# 4. Multicast Delegates

A delegate can reference multiple methods.

```csharp
public delegate void OrderHandler(Order order);
```

Methods:

```csharp
void SendEmail(Order order)
{
    Console.WriteLine("Email");
}

void WriteAudit(Order order)
{
    Console.WriteLine("Audit");
}

void UpdateAnalytics(Order order)
{
    Console.WriteLine("Analytics");
}
```

Combine them:

```csharp
OrderHandler handler = SendEmail;

handler += WriteAudit;
handler += UpdateAnalytics;
```

Invoke:

```csharp
handler(order);
```

Execution:

```text
handler(order)
       |
       +----> SendEmail()
       |
       +----> WriteAudit()
       |
       +----> UpdateAnalytics()
```

This is called a **multicast delegate**.

This idea is very important because .NET events are built on delegates.

---

# 5. What Is an Event?

An event is a controlled notification mechanism built around a delegate.

Example:

```csharp
public class Order
{
    public event EventHandler? OrderCreated;
}
```

A subscriber can listen:

```csharp
order.OrderCreated += OnOrderCreated;
```

Handler:

```csharp
void OnOrderCreated(object? sender, EventArgs e)
{
    Console.WriteLine("Order created");
}
```

The owner of the event raises it:

```csharp
OrderCreated?.Invoke(this, EventArgs.Empty);
```

The important difference is:

### Delegate

External code can invoke the delegate.

### Event

External code can subscribe/unsubscribe, but only the class that owns the event can raise it.

This gives encapsulation.

---

# 6. Why `event` Exists

Without `event`:

```csharp
public EventHandler? OrderCreated;
```

Another class could do:

```csharp
order.OrderCreated?.Invoke(
    order,
    EventArgs.Empty);
```

That means external code could pretend the order was created.

With:

```csharp
public event EventHandler? OrderCreated;
```

external code can only:

```csharp
order.OrderCreated += Handler;
order.OrderCreated -= Handler;
```

It cannot raise the event.

Only `Order` can do:

```csharp
OrderCreated?.Invoke(
    this,
    EventArgs.Empty);
```

Mental model:

```text
                  Order
                    |
              owns event
                    |
        +-----------+-----------+
        |           |           |
     Handler A   Handler B   Handler C

Subscribers can listen.
Only Order can raise.
```

# 7. EventHandler

.NET provides the standard:

```csharp
EventHandler
```

Conceptually:

```csharp
void EventHandler(
    object? sender,
    EventArgs e);
```

For custom event data:

```csharp
EventHandler<TEventArgs>
```

Example:

```csharp
public class OrderCreatedEventArgs : EventArgs

    public int OrderId { get; }

    public OrderCreatedEventArgs(int orderId)
    {
        OrderId = orderId;
    }

```

```csharp
public event EventHandler<OrderCreatedEventArgs>? OrderCreated;
```

```csharp
order.OrderCreated += HandleOrderCreated;
```

```csharp

    object? sender,
    OrderCreatedEventArgs e)

    Console.WriteLine($"Order: {e.OrderId}");
}
```

```csharp
public class Order
```

```csharp

```



|---|---|

| Publisher | Object that raises an event |
| Subscriber | Object that listens to an event |

```csharp

```

```text
OrderHandler
     |
     v
method signature
```

```csharp

```

```csharp

{
}
```

```csharp

```

```csharp

```

# 10. Observer Pattern

Events implement a variation of the **Observer Pattern**.

```text
                  Publisher
                     |
                  Order
                     |
                 OrderCreated
                     |
        +------------+------------+
        |            |            |
        v            v            v
      Email       Audit       Analytics
      Handler     Handler       Handler
```

The publisher does not need to know the implementation details of its subscribers.

This is the foundation of event-driven architecture.

---

# 11. Async Event Handling

This is where many C# developers become confused.

A normal event uses:

```csharp
EventHandler
```

which returns:

```csharp
void
```

But asynchronous code normally uses:

```csharp
Task
```

Example:

```csharp
async Task HandleOrderCreated(...)
{
    await SendEmailAsync();
}
```

The signatures are different.

```text
EventHandler
    |
    +----> void

async method
    |
    +----> Task
```

Therefore, do not casually convert an asynchronous handler into `async void`.

---

# 12. The `async void` Problem

You might write:

```csharp
async void HandleOrderCreated(
    object? sender,
    OrderCreatedEventArgs e)
{
    await SendEmailAsync();
}
```

It compiles because traditional .NET event handlers use `void`.

But `async void` has an important limitation:

> The caller cannot await it.

Example:

```csharp
Created?.Invoke(this, args);

Console.WriteLine("DONE");
```

Handler:

```csharp
async void Handle(...)
{
    await Task.Delay(2000);

    Console.WriteLine("EMAIL SENT");
}
```

Possible execution:

```text
Raise event
   |
   +----> Handler starts
   |
   +----> await
   |
   +----> control returns immediately
   |
   +----> "DONE"
   |
   |
   2 seconds later
   |
   +----> "EMAIL SENT"
```

The publisher has no `Task` representing the asynchronous work.

Therefore:

> Avoid `async void` for application/domain event infrastructure unless the framework's event contract specifically requires it.

---

# 13. Better Async Event Handler Abstraction

The idea in one line:

> Make the handler return a `Task` instead of `void`, so the code that raises the event can `await` each handler and know when it finishes, whether it failed, and how to cancel it.

## 13.1 The Event Data and the Delegate

If you are designing your own event infrastructure, use a `Task`-returning abstraction:

```csharp
public sealed record OrderCreatedEvent(
    int OrderId,
    string CustomerEmail);

// "Any method that takes (TEvent, CancellationToken) and returns Task"
public delegate Task AsyncEventHandler<TEvent>(
    TEvent @event,
    CancellationToken cancellationToken);
```

## 13.2 The Publisher Keeps a List of Handlers and Awaits Each One

```csharp
public sealed class Order
{
    private readonly List<AsyncEventHandler<OrderCreatedEvent>> _createdHandlers = [];

    public int Id { get; }

    public Order(int id) => Id = id;

    // Subscribe (plays the role of "+=")
    public void OnCreated(
        AsyncEventHandler<OrderCreatedEvent> handler)
        => _createdHandlers.Add(handler);

    public async Task CreateAsync(
        CancellationToken cancellationToken = default)
    {
        Console.WriteLine($"Creating order {Id}...");

        var @event = new OrderCreatedEvent(
            Id,
            "customer@example.com");

        foreach (var handler in _createdHandlers)
        {
            // Invoke the delegate and wait for it
            await handler(
                @event,
                cancellationToken);
        }

        Console.WriteLine($"Order {Id}: all handlers finished");
    }
}
```

Note: a delegate is invoked like a method — `handler(@event, ct)` — not with `handler.HandleAsync(...)`. `HandleAsync` is the interface style shown in section 13.7.

## 13.3 Handlers Are Ordinary `async Task` Methods

Any method matching the delegate signature can subscribe:

```csharp
static async Task SendEmailAsync(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(2000, ct);   // simulate SMTP call

    Console.WriteLine($"Email sent to {e.CustomerEmail}");
}

static async Task WriteAuditAsync(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(500, ct);    // simulate DB write

    Console.WriteLine($"Audit written for order {e.OrderId}");
}
```

Usage:

```csharp
var order = new Order(100);

order.OnCreated(SendEmailAsync);
order.OnCreated(WriteAuditAsync);

await order.CreateAsync();

Console.WriteLine("DONE");
```

Output:

```text
Creating order 100...
Email sent to customer@example.com      (after 2 s)
Audit written for order 100             (after 0.5 s more)
Order 100: all handlers finished
DONE
```

`DONE` prints last because the publisher actually waited for the handlers.

## 13.4 Compare With `async void`

With `event EventHandler<...>` and `async void` handlers (section 12), the same program prints:

```text
Creating order 100...
Order 100: all handlers finished    <-- false: nothing has finished yet
DONE
Audit written for order 100         (0.5 s later)
Email sent to customer@example.com  (2 s later)
```

| Concern | `async void` handler | `Task`-returning handler |
|---|---|---|
| Publisher knows when the handler is done | No | Yes (`await`) |
| Handler exception | Can't be caught by the publisher; may crash the process | Comes back through `await`, so `try/catch` works |
| Cancellation | No way to pass a token | `CancellationToken` parameter |
| Sequential or parallel | Always fire-and-forget | Your choice (`foreach await` or `Task.WhenAll`) |

## 13.5 Exceptions and Cancellation

Exceptions flow back to the publisher:

```csharp
static async Task FailingHandler(
    OrderCreatedEvent e,
    CancellationToken ct)
{
    await Task.Delay(100, ct);

    throw new InvalidOperationException("SMTP server down");
}

order.OnCreated(FailingHandler);

try
{
    await order.CreateAsync();
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"Handler failed: {ex.Message}");   // this runs
}
```

With `async void`, this `catch` would never run.

Cancellation reaches every handler:

```csharp
using var cts = new CancellationTokenSource(
    TimeSpan.FromSeconds(1));

// SendEmailAsync's 2 s delay is cancelled
// and throws TaskCanceledException
await order.CreateAsync(cts.Token);
```

## 13.6 Trap: `event` With a `Task`-Returning Delegate

You might try:

```csharp
public event AsyncEventHandler<OrderCreatedEvent>? Created;

await Created?.Invoke(@event, ct);   // wrong
```

This compiles, but when a multicast delegate returns a value, **only the last subscriber's return value is returned**. You would await only the last handler's `Task`; the others become fire-and-forget again.

That is why the example keeps its own `List<...>` and awaits each item. If you do use `event`, iterate the invocation list:

```csharp
if (Created is not null)
{
    foreach (AsyncEventHandler<OrderCreatedEvent> handler
        in Created.GetInvocationList())
    {
        await handler(@event, ct);
    }
}
```

## 13.7 From Delegate to Interface

The same contract — take the event and a token, return a `Task` — can be expressed as an interface:

```csharp
public interface IDomainEventHandler<TEvent>
{
    Task HandleAsync(
        TEvent @event,
        CancellationToken cancellationToken);
}
```

The dispatcher then awaits it:

```csharp
await handler.HandleAsync(
    @event,
    cancellationToken);
```

| | Delegate style | Interface style |
|---|---|---|
| Handler is | a method | a class |
| Invoke with | `await handler(e, ct)` | `await handler.HandleAsync(e, ct)` |
| Dependencies (DbContext, email service) | captured in a closure | constructor injection |
| Registration | `order.OnCreated(...)` | DI container (`services.AddScoped<IDomainEventHandler<...>, ...>()`) |

Real DDD applications usually use the interface style (see section 23), because handlers need injected services. The delegate style is the simplest way to see why returning `Task` matters.

Synchronous:


```text

  |
  v
```

Asynchronous:

# 15. Async Does Not Mean Distributed

This distinction is extremely important.

This:

```csharp
await handler.HandleAsync();
```

is asynchronous programming.

It does NOT automatically mean:

```text
another service
```

You can have:

```text
Same process
     |
     +---- async
```

Or:

```text
Different processes
     |
     +---- async messaging
```

These are different concepts.

Remember:

```text
async ≠ distributed
```

Before DDD events, understand commands.

### Command

A command says:

> Please do this.

Example:

```csharp
PlaceOrderCommand
```

### Event

An event says:

> This happened.

Example:

```csharp
OrderPlacedDomainEvent
```

Mental model:

```text
Command → intent
Event   → fact
```


# 17. Why DDD Uses Domain Events

Suppose an order is placed.

Several things may need to happen:

```text
Order placed
   |
   +----> Update customer statistics
   |
   +----> Apply loyalty points
   |
   +----> Create notification
   |
   +----> Create integration message
```

If the `Order` aggregate directly calls all of these services, it becomes tightly coupled.

Instead:

```text
Order Aggregate
       |
       v
OrderPlacedDomainEvent
       |
       v
Domain Event Dispatcher
       |
       +----> Handler A
       +----> Handler B
       +----> Handler C
```

The aggregate only knows the business fact.

# 18. Domain Event Is Not the Same as a C# Event

A C# event:

```csharp
public event EventHandler<OrderCreatedEventArgs>? Created;
```

is a language/runtime mechanism for notifying subscribers.

A DDD domain event:

```csharp
public sealed record OrderPlacedDomainEvent(
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount
) : IDomainEvent;
```

is a business fact.

The domain event says:

> "An order was placed."

This is why DDD events are often explicit objects rather than C# events.

# 19. Define the Domain Event Contract

A simple contract:

```csharp
public interface IDomainEvent
{
}
```

Then:

```csharp
public sealed record OrderPlacedDomainEvent(

    Guid CustomerId,
    decimal TotalAmount

```

The event is just data.

It does not execute anything.

Think:

```text
Domain Event

     |
     +---- business fact
```

# 20. Aggregate Root

A common aggregate-root implementation stores domain events.

```csharp
public abstract class AggregateRoot
{
    private readonly List<IDomainEvent> _domainEvents = [];

    public IReadOnlyCollection<IDomainEvent> DomainEvents
        => _domainEvents.AsReadOnly();

    protected void AddDomainEvent(
        IDomainEvent domainEvent)
    {
        _domainEvents.Add(domainEvent);
    }

    public void ClearDomainEvents()
    {
        _domainEvents.Clear();
    }
}
```

The aggregate records events rather than immediately dispatching them.

---

# 21. Why Store the Event Instead of Immediately Dispatching It?

Avoid this:

```csharp
public void Place()
{
    // Change state

    DomainEventDispatcher.Dispatch(
        new OrderPlacedDomainEvent(...));
}
```

Prefer:

```csharp
public void Place()
{
    // Change state

    AddDomainEvent(
        new OrderPlacedDomainEvent(...));
}
```

Why?

Because the domain model should not suddenly start performing infrastructure/application work.

The aggregate says:

> "This happened."

The application infrastructure decides when and how to process it.

This is often called the **deferred domain-event approach**.

# 22. Example Order Aggregate

```csharp
public sealed class Order : AggregateRoot
{
    public Guid Id { get; private set; }

    public Guid CustomerId { get; private set; }
```

```text

```

```text

```

That is good domain isolation.

Define:

```csharp
public interface IDomainEventHandler<TEvent>
```

Handler:

```csharp
public sealed class SendOrderConfirmationHandler
```

```csharp
public sealed class UpdateCustomerStatisticsHandler
```

Now:

```text

          |
          +----> SendOrderConfirmationHandler
          |
          +----> UpdateCustomerStatisticsHandler
```

The aggregate does not know about either handler.

# 24. Domain Event Dispatcher

Define:

```csharp
public interface IDomainEventDispatcher
{
    Task DispatchAsync(
        IEnumerable<IDomainEvent> events,
        CancellationToken cancellationToken);
}
```

Conceptual implementation:

```csharp
public async Task DispatchAsync(
    IEnumerable<IDomainEvent> events,
    CancellationToken cancellationToken)
{
    foreach (var domainEvent in events)
    {
        var handlers = ResolveHandlers(domainEvent);

        foreach (var handler in handlers)
        {
            await handler.HandleAsync(
                domainEvent,
                cancellationToken);
        }
    }
}
```

Now the flow is:

```text
Domain Event
     |
     v
Dispatcher
     |
     +----> Handler A
     |
     +----> Handler B
     |
     +----> Handler C
```

You have now built the basic mechanics of a DDD event system.

---

# 25. Sequential Event Handlers

A simple dispatcher can process handlers sequentially:

```csharp
foreach (var handler in handlers)
{
    await handler.HandleAsync(
        domainEvent,
        cancellationToken);
}
```

Flow:

```text
Handler A
   |
   v
Handler B
   |
   v
Handler C
```

If each takes approximately one second:

```text
Total ≈ 3 seconds
```

This approach is easy to reason about and can be appropriate when:

- handlers have dependencies
- handlers share transactional state
- ordering matters
- the same DbContext is involved

---

# 26. Parallel Event Handlers

If handlers are truly independent:

```csharp
var tasks = handlers.Select(
    handler => handler.HandleAsync(
        domainEvent,
        cancellationToken));

await Task.WhenAll(tasks);
```

Flow:

```text
Handler A ───────>
Handler B ───────>
Handler C ───────>
                  |
                  v
              Task.WhenAll
```

Potentially, three one-second handlers can finish in approximately one second rather than three.

But do not blindly parallelize handlers.

Consider:

- database concurrency
- shared `DbContext`
- transaction boundaries
- ordering requirements
- resource limits
- handler dependencies

Concurrency is an architectural decision.

---

# 27. `Task.WhenAll` and Exceptions

Suppose:

```text
Handler A → success
Handler B → exception
Handler C → success
```

With:

```csharp
await Task.WhenAll(tasks);
```

all handlers may already have started.

Therefore:

```text
B failed
```

does not necessarily mean:

```text
C never ran
```

They were concurrent.

This is important when designing failure handling.

---

# 28. Domain Event Lifecycle

A typical lifecycle:

```text
1. Business operation
       ↓
2. Aggregate changes state
       ↓
3. Aggregate raises domain event
       ↓
4. Event is stored in aggregate
       ↓
5. Unit of Work saves transaction
       ↓
6. Domain event dispatcher runs
       ↓
7. Domain event handlers execute
       ↓
8. Some handler may create integration event
```

This is the core DDD event flow.

# 29. Where Should Domain Events Be Dispatched?

There are two common choices.

## Option A: Before Commit

```text
Command
  |
  v
Aggregate
  |
  v
Domain Event
  |
  v
Domain Handlers
  |
  v
SaveChanges
  |
  v
Commit
```

If a handler fails, the database transaction can fail/rollback depending on how the transaction is configured.

This can be useful when the handler's work must participate in the same transaction.

---

## Option B: After Commit

```text
Command
  |
  v
Aggregate
  |
  v
SaveChanges
  |
  v
COMMIT
  |
  v
Domain Event
  |
  v
Handlers
```

Now:

```text
Database = success
Handler = failure
```

The order still exists.

Therefore, handler failure needs:

- retries
- eventual consistency
- monitoring
- durable messaging when necessary

# 30. Domain Event vs Integration Event

This distinction is essential.

| | Domain Event | Integration Event |
|---|---|---|
| Scope | Same bounded context/application | Across service/system boundaries |
| Communication | In-process | Network/message broker |
| Typical mechanism | Dispatcher/Mediator | RabbitMQ/Kafka/Azure Service Bus |
| Persistence | Usually local | Usually durable |
| Reliability | Process-local | Retry/idempotency required |
| Example | `OrderPlacedDomainEvent` | `OrderPlacedIntegrationEvent` |

Mental model:

```text
Domain Event
     |
     v
Inside application
```

versus:

```text
Integration Event
     |
     v
Message Broker
     |
     v
Other application/service
```

# 31. Why Not Use a C# Event Between Microservices?

Because:

```text
Order Service
```

and:

```text
Payment Service
```

may be separate processes/machines/containers.

A C# event only exists inside the process memory.

Instead:

```text
Order Service
     |
     v
Integration Event
     |
     v
Message Broker
     |
     v
Payment Service
```

Typical brokers:

- RabbitMQ
- Apache Kafka
- Azure Service Bus

# 32. Domain Event to Integration Event

Do not automatically expose the internal domain event as your public message contract.

Prefer:

```text
Domain Model
    |
    v
OrderPlacedDomainEvent
    |
    v
Domain Event Handler
    |
    v
OrderPlacedIntegrationEvent
    |
    v
Message Broker
```

Example domain event:

```csharp
public sealed record OrderPlacedDomainEvent(
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount
) : IDomainEvent;
```

Integration event:

```csharp
public sealed record OrderPlacedIntegrationEvent(
    Guid EventId,
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount,
    DateTime OccurredOnUtc
);
```

This separation protects the domain model from external contract concerns.

# 33. Integration Event Handler Example

```csharp
public sealed class OrderPlacedIntegrationEventHandler
    : IDomainEventHandler<OrderPlacedDomainEvent>
{
    private readonly IIntegrationEventPublisher _publisher;

    public OrderPlacedIntegrationEventHandler(
        IIntegrationEventPublisher publisher)
    {
        _publisher = publisher;
    }

    public async Task HandleAsync(
        OrderPlacedDomainEvent domainEvent,
        CancellationToken cancellationToken)
    {
        var integrationEvent =
            new OrderPlacedIntegrationEvent(
                Guid.NewGuid(),
                domainEvent.OrderId,
                domainEvent.CustomerId,
                domainEvent.TotalAmount,
                DateTime.UtcNow);

        await _publisher.PublishAsync(
            integrationEvent,
            cancellationToken);
    }
}
```

Conceptually:

```text
Domain Event
     |
     v
Handler
     |
     v
Integration Event
     |
     v
Broker
```

However, there is a reliability problem.

---

# 34. The Database vs Broker Problem

Suppose:

```text
Save database
     |
     v
Publish message
```

What if:

```text
Database = SUCCESS
Broker = FAILURE
```

Then:

```text
Order exists
BUT
Payment Service never receives OrderPlaced
```

This is a classic distributed-systems consistency problem.

The solution is often the **Outbox Pattern**.

---

# 35. Outbox Pattern

Store both the business change and the outgoing message in the same database transaction.

```text
BEGIN TRANSACTION

INSERT Order

INSERT OutboxMessage

COMMIT
```

Conceptually:

```text
Database Transaction
       |
       +---- Order
       |
       +---- Outbox Message
```

Then a background worker reads the outbox:

```text
Outbox Table
    |
    v
Background Worker
    |
    v
Message Broker
```

If the application crashes after commit:

```text
Order exists
Outbox message exists
```

The worker can retry publishing.


```text

        |
        v

        |
        v

        |
        v

```


# 38. Idempotency

Distributed messaging can produce duplicate delivery.

Example:

```text
OrderPlaced
     |
     v
Payment Service
```

Payment succeeds.

But the consumer crashes before acknowledging the message.

The broker retries:

```text
OrderPlaced
     |
     v
Payment Service
```

again.

Without idempotency, payment could happen twice.

Therefore consumers should usually be idempotent.

---

# 39. Event ID

An integration event should have a unique ID:

```csharp
public record OrderPlacedIntegrationEvent
{
    public Guid EventId { get; init; }

    public Guid OrderId { get; init; }

    public Guid CustomerId { get; init; }

    public decimal TotalAmount { get; init; }

    public DateTime OccurredOnUtc { get; init; }
}
```

The consumer can keep a processed-message table:

```text
ProcessedMessages
-----------------
EventId
ProcessedOnUtc
```

Before processing:

```text
Have I processed EventId?
       |
   +---+---+
   |       |
  Yes      No
   |       |
Ignore    Process
            |
            v
       Mark processed
```

This is the basic idea of idempotent consumers.

---

# 40. Integration Event Versioning

Integration events are external contracts.

For example, version 1:

```csharp
OrderPlacedIntegrationEvent
{
    OrderId
    CustomerId
}
```

Later you need:

```csharp
OrderPlacedIntegrationEvent
{
    OrderId
    CustomerId
    Currency
    TotalAmount
}
```

Other services may still depend on the old contract.

Therefore, integration events should be designed and versioned carefully.

Possible approaches:

```text
OrderPlacedIntegrationEventV1
OrderPlacedIntegrationEventV2
```

or compatible additive changes, depending on the messaging ecosystem.


# 43. MediatR and Domain Events

In real .NET applications, MediatR is often used for in-process dispatching.

Example:

```csharp
public sealed record OrderPlacedDomainEvent(
    Guid OrderId,
    Guid CustomerId,
    decimal TotalAmount
) : INotification;
```

Handler:

```csharp
public sealed class OrderPlacedHandler
    : INotificationHandler<OrderPlacedDomainEvent>
{
    public async Task Handle(
        OrderPlacedDomainEvent notification,
        CancellationToken cancellationToken)
    {
        // Side effect

        await Task.CompletedTask;
    }
}
```

Publishing:

```csharp
await mediator.Publish(
    domainEvent,
    cancellationToken);
```

Conceptually:

```text
mediator.Publish(event)
          |
          +---- Handler A
          |
          +---- Handler B
          |
          +---- Handler C
```

MediatR is an **in-process dispatcher**.

---

# 44. MediatR Is Not a Message Broker

Do not confuse:

```text
MediatR
```

with:

```text
Kafka
RabbitMQ
Azure Service Bus
```

MediatR:

```text
Application Process
       |
       v
MediatR
       |
       +---- Handler
       +---- Handler
```

Message broker:

```text
Application A
      |
      v
Message Broker
      |
      v
Application B
```

Therefore:

```text
MediatR ≠ Kafka
MediatR ≠ RabbitMQ
MediatR ≠ Azure Service Bus
```

MediatR provides in-process dispatching.

A broker provides distributed messaging.

# 45. When Should Domain Logic Be Synchronous?

Inside the aggregate, business invariants should normally be handled locally and synchronously.

For example:

```csharp
order.AddItem(item);
order.CalculateTotal();
order.Validate();
```

Avoid making the aggregate depend directly on:

```text
HTTP
Database
RabbitMQ
Kafka
Email
External API
```

The aggregate should be able to make its business decision from its own state and domain rules.

---

# 46. What Should Domain Event Handlers Do?

Domain event handlers can perform application-level side effects such as:

```text
Update another aggregate
Update read-side information
Create an outbox message
Trigger internal application processing
Record audit information
```

Be careful about direct external calls:

```csharp
await httpClient.PostAsync(...);
```

inside a transaction.

A more reliable approach is often:

```text
Domain Event
    |
    v
Create Outbox Record
    |
    v
Commit
    |
    v
Background Worker
    |
    v
HTTP / Broker / External Service
```

# 47. Common Mistake: Infrastructure in the Domain

Avoid:

```csharp
public class Order
{
    private readonly EmailService _emailService;

    public async Task PlaceAsync()
    {
        // Business logic

        await _emailService.SendAsync();
    }
}
```

The domain entity now depends on infrastructure.

Prefer:

```csharp
public void Place()
{
    // Business rules

    RaiseDomainEvent(
        new OrderPlacedDomainEvent(...));
}
```

Then the application layer handles side effects.

---

# 48. Common Mistake: `async void`

Avoid:

```csharp
async void Handle(...)
{
    await DoSomethingAsync();
}
```

for your own event infrastructure.

Prefer:

```csharp
async Task HandleAsync(
    ...,
    CancellationToken cancellationToken)
{
    await DoSomethingAsync();
}
```

This allows:

```csharp
await handler.HandleAsync(...);
```

and gives proper:

- exception propagation
- cancellation
- completion tracking
- composition

---

# 49. Common Mistake: `Task.Run` as Event Architecture

Do not use:

```csharp
Task.Run(() => HandleEvent());
```

as a replacement for reliable event infrastructure.

`Task.Run()` does not solve:

- persistence
- retries
- transaction boundaries
- process crashes
- durability
- idempotency
- message delivery
- dead-letter handling

Use proper messaging/outbox infrastructure for those requirements.

---

# 50. Common Mistake: Publishing Before Persistence

Be careful with:

```text
Publish message
     |
     v
Save database
```

If the broker succeeds and the database fails:

```text
Broker = success
Database = failure
```

Consumers received a fact that did not actually persist.

A transactional outbox is a common solution.

---

# 51. Common Mistake: Treating Every Operation as an Event

Not every method deserves an event.

Bad examples:

```text
GetCustomer
GetOrder
CalculatePrice
ValidateEmail
```

Good business facts:

```text
OrderPlaced
OrderCancelled
PaymentReceived
CustomerRegistered
InvoiceGenerated
ShipmentDispatched
```

An event should normally represent something meaningful that happened.

# 58. The One Sentence to Remember

> **A delegate gives you a callback contract; an event uses that mechanism to notify subscribers; an event handler reacts to the notification; a domain event represents a business fact inside a bounded context; an integration event carries a fact across a system boundary; and an outbox plus message broker makes that cross-boundary communication reliable.**

The complete mental model is:

```text
C# LANGUAGE LEVEL

Delegate
   ↓
Event
   ↓
Event Handler
   ↓
Async Task


DDD LEVEL

Command
   ↓
Aggregate
   ↓
Domain Event
   ↓
Domain Event Handler


DISTRIBUTED SYSTEM LEVEL

Domain Event
   ↓
Outbox
   ↓
Integration Event
   ↓
Message Broker
   ↓
Consumer
   ↓
Idempotency + Retry + DLQ
```

Once this hierarchy is clear, **DDD Domain Events, Integration Events, CQRS, MediatR, RabbitMQ/Kafka/Azure Service Bus, Outbox Pattern, and eventual consistency all become much easier to reason about.**
